# АСУБК — статистика: физическая схема (PostgreSQL)

> **Статус: v1, 17.09.2026, волна 22.** Поколоночный состав таблиц модуля «Статистика».
> Решения, из которых схема следует, — `docs/adr/0237`…`docs/adr/0245`; логика модуля —
> `ASUBK-statistika-logika.md`; журнал волн — `ASUBK-status-razrabotki.md`.
>
> **История.** Схема разобрана в три круга 16–17.09.2026:
> 1. хранение и прогон;
> 2. служебные таблицы;
> 3. проход по объектам: какие поля хранить и в каком виде.
>
> Каждый объект утверждён пользователем списком колонок. Этот файл записывает утверждённое и
> ничего не решает сам. Уточнения, которые появились при записи, названы в §15.
>
> **Что здесь и чего нет.** Здесь — таблицы, колонки, типы, ключи, индексы, функции и
> триггер. Почему именно так, отвечают ADR. Как величина считается, отвечают соседи. Как
> строится ответ, отвечает спецификация модуля. DDL целиком не приводится: миграции пишут
> разработчики (`ADR-0237` §2), а файл даёт им состав и правила.
>
> **Долг.** Раздел ТЗ 19 и пакет `P22` описывают прежнюю модель с одной «строкой среза» —
> `СС-Д17`. Макет `statistics.html` и смоук — `СС-Д18`.

### 0.3. Типы

| Что | Тип |
|---|---|
| сумма денег | `numeric(20,2)` |
| курс | `numeric(18,6)` |
| ставка, доля, порог | `numeric(9,4)` |
| валюта | `char(3)` |
| число, дни | `integer` |
| порядок значения | `smallint` |
| ссылка | `uuid` + `text` |
| закрытый словарь модели | `text` + `CHECK` |
| признак | `boolean` |
| дата | `date` |
| ответ соседа | перечисление `stat_source_state`: `ok` · `unavailable` · `error` · `timeout` · `denied` · `legacy` |

`jsonb` в схеме нет ни одного (`ADR-0237`, `ADR-0245`).

**Значение в `CHECK`** — то, что отдаёт владелец. У «Программ» и «Погашений» это латинские
коды. У остальных владельцев это русская строка их модели. Свои словари статистики — виды
поправок — латинскими кодами. Новое значение — релиз вместе с правкой модели владельца
(`ADR-0241` §2).

### 0.4. Служебные колонки

| Колонка | Правило |
|---|---|
| `object_id`, `slice_date` | ключ строки. У члена группы вместо `object_id` — `group_id` + `member_id`; у меры — `object_id` + `target_id`; у платежа и поступления в ключ входит `d_corr_kind` |
| `slice_date` | срез на **начало** дня; период строки — месяц даты `slice_date − 1` (`ADR-0238` §2) |
| `run_id` | прогон, последним записавший строку; внешнего ключа нет |
| `src_<сосед>` | по колонке на каждого опрашиваемого соседа; состав — в разделе таблицы |
| `src_detail` | текст ошибки; есть там, где есть `src_*`, кроме члена группы |
| `is_partial` | `GENERATED ALWAYS … STORED`: хоть один `src_*` не `ok` и не `legacy` |
| `now_cols` | `text[] NOT NULL DEFAULT '{}'` — имена величин, собранных «текущими» (`ADR-0242`) |

У залогового договора, программы и поступления все данные приходят от владельца вместе с
множеством, поэтому колонок `src_*`, `src_detail` и `is_partial` у них нет: молчание
владельца означает, что строк нет.

### 0.5. Отсутствие

- Величина молчавшего соседа — `NULL`. Это не ноль и не вчерашнее значение (`ADR-0208` §1).
- `NULL` у признака значит «сосед молчал», а не «нет» (`ADR-0241` §6).
- `NULL` у ссылки значит, что значения на дату не было.
- У легаси-строки несопоставленная ссылка — `_id` пустой, `_lbl` из старой системы
  (`ADR-0245` §9).

### 0.6. Вычисляемые колонки

Дни от хранимой даты — `integer GENERATED ALWAYS AS (…) STORED`: при копировании строки на
следующий день они пересчитываются сами (`ADR-0241` §7). Формула — разность дат, она
неизменяема и допустима в `GENERATED`:

```sql
i_next_survey integer GENERATED ALWAYS AS (d_next_survey - slice_date) STORED,
i_age_days    integer GENERATED ALWAYS AS (coalesce(d_cdate, slice_date) - d_odate) STORED
```

Порядок и стадия фазы требования — `CASE` от `d_phase`. Остальные дни (просрочка, до
ближайшего платежа, до полного погашения, срок отношений) приходят числом от ядра: их правило
у ядра, а не разность двух дат строки.

### 0.7. Ключи, индексы, секции

- **Первичный ключ** — по §0.4. Внешних ключей из таблиц строк нет.
- **Индексы** каждой таблицы строк: первичный ключ, `(slice_date)`, частичный
  `(slice_date) WHERE is_partial` — там, где колонка есть (`ADR-0245` §12).
- **Дополнительные индексы** для join и охвата:
  - `stat_row_claim (d_case_id, slice_date)`;
  - `stat_row_claim (d_credit_id, slice_date)`;
  - `stat_row_credit (d_program_id, slice_date)`;
  - `stat_row_group_member (member_id, slice_date)`;
  - `stat_row_measure (target_id, slice_date)`;
  - `stat_row_repay (d_credit_id, slice_date)`.

  Join к заёмщику идёт по первичному ключу его строки.
- **Программа:** GIN по `d_source_ids`, `d_kind_ids`, `d_purp_ids`, `d_line_ids` — для
  фильтра `@>`.
- **Секции** — `PARTITION BY RANGE (slice_date)`, секция на год плюс `DEFAULT`. Дни закрытого
  месяца удаляются `DELETE` (`ADR-0245` §12).
- **Запрет записи** в закрытый период — триггер §14 на всех одиннадцати таблицах.

### 0.8. Чего нет

- Сводок и хранимых агрегатов: агрегат считается при чтении (`ADR-0147` §2).
- Журнала DDL: колонки ведёт Liquibase (`ADR-0237` §6).
- Строк у событий на каждый день (`ADR-0239`).
- Колонки на тип узла оргструктуры: подразделение — два уровня (`ADR-0241` §4).

### 0.9. Пометки в разделах §1–§11

- **⚑** в графе «Источник» — у соседа этой величины или этого поля пока нет. Это находка для
  соседа, она записана в журнал волны 22.
- **⚠** — утверждённый список расходится с моделью владельца; вопрос вынесен в §15.
- Названия в скобках (`calcDebt`, `LIFECYCLES`) — шов или константа в макете владельца,
  откуда взято значение.

## 13. Функции и представление

Правило «событие на дату» живёт в базе (`ADR-0239` §6). Функции — `LANGUAGE sql STABLE`,
охват не применяют, из JPQL не вызываются. Ниже — эскиз: списки колонок сокращены.

```sql
-- платёж: суммы — сумма строк ≤ D, разрезы и состояние — из последней строки ≤ D
CREATE FUNCTION stat_repay_at(p_date date) RETURNS SETOF stat_row_repay
LANGUAGE sql STABLE AS $$
  WITH r AS (SELECT * FROM stat_row_repay WHERE slice_date <= p_date),
  s AS (SELECT object_id, sum(i_amount_v) AS i_amount_v, sum(i_amount_som) AS i_amount_som, …
        FROM r GROUP BY object_id),
  l AS (SELECT DISTINCT ON (object_id) * FROM r
        ORDER BY object_id, slice_date DESC,
                 array_position(ARRAY['rebind','reversal','original'], d_corr_kind))
  SELECT l.object_id, l.slice_date, …, s.i_amount_v, s.i_amount_som, …
  FROM l JOIN s USING (object_id)
$$;
```

- **Порядок строк одной даты у платежа:** `rebind` › `reversal` › `original`. Перепривязанный
  платёж берёт кредит из строки `rebind`, а сторнированный — состояние из строки `reversal`.
- **`stat_receipt_at(D)`** устроена так же. Суммируются `i_amount`, `i_paid`, `i_ret` и
  `i_pays`; состояния (`d_match`, `d_frozen`, `d_bdate`) берутся из последней строки. Порядок
  строк одной даты — по списку видов поправок §10.
- **`stat_measure_at(D)`** возвращает последнюю строку пары «мера × цель»:

```sql
CREATE FUNCTION stat_measure_at(p_date date) RETURNS SETOF stat_row_measure
LANGUAGE sql STABLE AS $$
  SELECT DISTINCT ON (object_id, target_id) *
  FROM stat_row_measure
  WHERE slice_date <= p_date
  ORDER BY object_id, target_id, slice_date DESC
$$;
```

Для объектов-состояний функции нет: чтение на дату — `WHERE slice_date = D`.

**`v_repay_credit`** — строка платежа рядом со строкой его кредита на первое число месяца,
следующего за месяцем платежа. Через неё платёж получает разрезы, которые он не копирует:
категорию риска, слоты классификаторов, путь к признакам заёмщика.

```sql
CREATE VIEW v_repay_credit AS
SELECT p.*,
       c.d_risk_code, c.d_risk_lbl, c.d_risk_ord,
       c.d_cls1_code, …, c.d_cls10_ord
FROM stat_row_repay p
LEFT JOIN stat_row_credit c
  ON  c.object_id  = p.d_credit_id
  AND c.slice_date = (date_trunc('month', p.slice_date - 1) + interval '1 month')::date;
```

У платежа открытого месяца строки кредита на следующее первое число ещё нет — см. §15, п. 8.

## 14. Триггер запрета записи

Один триггер `BEFORE INSERT OR UPDATE OR DELETE … FOR EACH ROW` на каждой из одиннадцати
таблиц строк (`ADR-0245` §8). Функция одна, список колонок источника таблицы передаётся
аргументом триггера.

```sql
CREATE FUNCTION stat_row_guard() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE
  d   date;
  per period_calendar%ROWTYPE;
BEGIN
  FOREACH d IN ARRAY CASE TG_OP
      WHEN 'INSERT' THEN ARRAY[NEW.slice_date]
      WHEN 'DELETE' THEN ARRAY[OLD.slice_date]
      ELSE ARRAY[OLD.slice_date, NEW.slice_date] END
  LOOP
    SELECT * INTO per FROM period_calendar
     WHERE period = date_trunc('month', d - 1)::date;          -- период строки
    IF per.stat_closed_at IS NOT NULL THEN
      IF current_setting('stat.legacy_fix', true) = 'on'
         AND per.origin = 'legacy'
         AND stat_row_is_legacy(TG_TABLE_NAME, TG_ARGV, NEW, OLD) THEN
        CONTINUE;                                               -- правка легаси миграцией
      END IF;
      RAISE EXCEPTION 'stat: период % закрыт, запись в % запрещена',
                      to_char(d - 1, 'YYYY-MM'), TG_TABLE_NAME;
    END IF;
  END LOOP;
  RETURN CASE TG_OP WHEN 'DELETE' THEN OLD ELSE NEW END;
END $$;

CREATE TRIGGER stat_guard BEFORE INSERT OR UPDATE OR DELETE ON stat_row_credit
  FOR EACH ROW EXECUTE FUNCTION stat_row_guard('src_core', 'src_class');
```

- **Легаси.** Правку пропускает только флаг сессии `stat.legacy_fix`, и только в легаси-период
  и только в строки, у которых все `src_*` равны `legacy`. У таблиц без колонок источника
  (договор, программа, поступление) достаточно признака периода. Каждая правка пишется в
  `stat_rewrite_log` с причиной `legacy` и актором (`ADR-0245` §9).
- **Порядок закрытия** — одна транзакция (`ADR-0245` §7). Сначала удаляются дни, потом
  ставится `stat_closed_at`: триггер не мешает удалению, пока колонка пуста.
- **Поправка события** пишется в открытый месяц и триггер не задевает.
- Ключ `period` в календаре показан как первое число месяца; фактический формат — у
  `ADR-0204`.

## 15. Открытые вопросы и уточнения записи

### 15.1. Расхождения утверждённого с моделью владельца

При записи схема сверена с макетами и спецификациями соседей (17.09.2026). Утверждённые
списки в семи местах расходятся с моделью владельца. Пользователь принял схему как есть:
пп. 1 и 4 закрыты значениями владельца, остальные — открытые вопросы к соседям (журнал
волны 22).

| п. | Колонка | Утверждено | У владельца | Что решить |
|---|---|---|---|---|
| 1 | `stat_row_collateral.d_zstate` | 4 значения | «Залог» `lienStatus`: 6 (+ 'резервируется', 'выбыл'; 'аннулирован' строк не имеет) | **принято 17.09:** все шесть, как у владельца |
| 2 | `stat_row_claim.d_role` | 4 роли, без перечня | макет взыскания: 'госорган'; спецификация взыскания: 'залогодатель' | какая роль верна — вопрос взысканию |
| 3 | `stat_row_program.d_rate_type` | фиксированная · плавающая | «Программы»: `rateType` = 'Фиксированная' · 'Диапазон', плавающая — признак `floatRate` | две колонки по модели или одна |
| 4 | `stat_row_receipt.d_match` | 5 значений | «Погашения» `MATCH`: 6 (+ `none`, «не сопоставлено») | **принято 17.09:** все шесть, как у владельца |
| 5 | `stat_row_credit.d_cov_state` | 4 значения | у ядра перечня нет; заглушка в макете статистики — 5 (+ 'обеспечение в другой валюте') | нужен ли пятый при итогах в сомах |
| 6 | `stat_row_measure.d_instance` | 4 значения, без перечня | перечня нет: инстанция — вид меры (апелляция, кассация) | перечень или колонка из вида меры |
| 7 | `stat_row_zdeal.d_zstatus` | зарегистрирован · закрыт | «Залог»: ещё 'Аннулирован' | бывает ли аннулирование после регистрации |

Перечни состояния портфеля (`d_pstate`) и состояния контроля (`d_ctl`) есть только у
заглушек ядра в макете статистики. У владельца их нет — находка ядру.

### 15.2. Открытые вопросы схемы

8. **`v_repay_credit` в открытом месяце.** Строка кредита на следующее первое число появится
   только после конца месяца. До этого разрезы, которые платёж не копирует, пусты. Вариант
   — пока месяц открыт, брать строку кредита на `slice_date` платежа.
9. **Куратор кредита.** У заёмщика, залога и требования куратор приходит от кураторства и
   имеет колонку `src_curation`. У кредита он утверждён как история модуля «Кредиты», без
   своей колонки источника. Нужно сверить, кто назначает куратора кредита.
10. **Дни числом или от даты.** У кредита (`i_npay_days`, `i_full_days`) и заёмщика
    (`i_npay_days`, `i_tenure_days`) дни приходят числом от ядра. По `ADR-0241` §7 дни от
    хранимой даты вычисляются. Для «срока отношений» дата уже есть (`d_first_cdate`).

### 15.3. Уточнения, сделанные при записи

Это следствия утверждённого, а не новые решения:

- **Фильтр «погашено».** Отбрасываются только исходные строки, сторнированные в открытом
  месяце; строка-поправка `reversal` идёт в итог со своим минусом. Прежняя формулировка
  «`d_pay_state <> 'reversed'`» выбрасывала бы и её (§9).
- **Порядок строк одной даты** в функциях событий (§13).
- **Копия способа хранения в `stat_run_count`** — без неё `CHECK` по способу хранения не
  записать (§12.2).
- **Индексы для join и охвата** (§0.7) и GIN у программы.
- **Суммы — `numeric(20,2)` везде** (`ADR-0240` §1). При разборе у залога, договора и
  программы звучало `numeric(18,2)`.
- **Значения `CHECK` — как у владельца** (§0.3). При разборе примеры писались латинскими
  кодами (`active`, `pending`, `pos`); у владельцев, кроме «Программ» и «Погашений», значения —
  русские строки.
- **Кодов видов поправок поступления** при разборе не было; они заданы здесь (§10).
