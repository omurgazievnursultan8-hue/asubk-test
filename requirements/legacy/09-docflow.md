## 1. Итог

1. **Модулем пользуются как журналом входящих и исходящих.** В базе 74 101 документ:
   - входящих 37 239;
   - исходящих 36 789;
   - внутренних 37;
   - претензий 35;
   - акт сверки 1.

   Внутренним документооборотом (согласование служебных записок, приказов) за 7 лет фактически не пользовались.
2. **Исходящие — это в основном переписка по взысканию.** Уведомления 11,4 тыс., письма 10,5 тыс., извещения 10,1 тыс. Отдельно 2,5 тыс. служебных записок, 1,1 тыс. заявлений, 604 иска, 192 ходатайства и 268 жалоб. При этом документ **никак не связан** с заёмщиком, кредитом или процедурой взыскания (§8).
3. **Процесс движется задачами, а не статусами.** На документ в среднем приходится 3,7 задачи, всего задач 273 тыс. Статус документа часто не отражает, где он на самом деле. Конечный автомат в коде есть, но не вызывается.
4. **Висящие задачи никто не закрывает.** Открыто 85 931 задача, самая старая с января 2019. Срок задан у 15 062 из них, и все 15 062 просрочены. Просрочку система не считает, отчёта по ней нет.
5. **Регистрацией входящих занимается один человек.** У всех 37 239 входящих один и тот же автор. Исходящие создают 135 сотрудников.
6. **Нумерация работает не так, как написано в коде.**
   - Входящие нумеруются с 1 каждый год, хотя сброса в коде нет. Значит, счётчик обнуляют вручную.
   - Исходящие идут одним рядом на всю организацию в пределах года. Код отдела стоит только префиксом.
7. **Прав доступа по сути нет.** В списке человек видит только документы, где он участник. Но по прямой ссылке любой залогиненный открывает, правит, скачивает и удаляет что угодно, включая админский редактор.
8. **Архив, шаблоны, рассылка и уведомления не реализованы.** Таблицы пусты, классы есть, но не вызываются.
9. **Активность падает.**

   | Год | Документов |
   |---|---|
   | 2019 | 10,2 тыс. |
   | 2021 | 11,7 тыс. |
   | 2024 | 9,7 тыс. |
   | 2025 | 7,2 тыс. |
   | 2026 до 07.08 | 1 тыс. |

   В 2026 году исходящих 288 против 3 880 за 2025-й. Причина: работы по взысканию стало меньше, учёт полный (решение §13).

Вывод для ТЗ. Переносить нужно не код, а **то, чем реально пользуются**:
- журнал входящих с резолюцией и исполнителями;

## 3. Модель данных (как есть)

```
df_document ──< cat_dispatch_data      журнал действий: кто, когда, что, примечание (342 тыс.)
   │  └─< df_document_cat_attachments >── cat_attachments → файл на диске /opt/uploads/<uuid>.atach
   │  └─< document_users               участники = кто видит документ (389 тыс., без ролей)
   │  ├── senderResponsible   → cat_responsible → сотрудники | организации | физлица (+ свободный текст)
   │  ├── receiverResponsible → cat_responsible → то же
   │  └── receiverExecutor    → cat_executor    → сотрудники-исполнители
   └── closedWithId → df_document   «входящий закрыт исходящим», без FK (225 случаев)
task (objectType='Document', objectId=df_document.id, без FK)   задачи участникам (273 тыс.)
df_counter (подразделение, вид, тип) → incoming / outgoing       счётчики номеров
```

Главное о модели:
- **Отправитель и получатель — универсальная запись `cat_responsible`.** Она указывает на набор сотрудников, организаций или физлиц плюс свободный текст. Для внутреннего документа это сотрудники, для входящего — внешний отправитель, для исходящего — внешний адресат.
- **У документа два набора реквизитов регистрации:** «у отправителя» (`senderRegisteredNumber/Date`) и «у получателя» (`receiverRegisteredNumber/Date`). Входящий хранит номер корреспондента и наш номер. Исходящий хранит только наш номер. Внутренний получает оба номера: исходящий при утверждении, входящий при приёме.
- **Ролей участника не хранится.** Согласующие, утверждающий, получатели и исполнители восстанавливаются только по задачам и журналу.
- **Резолюция — это текст задачи исполнителю.** Отдельной сущности нет.
- **Статусов 13 (enum `State`), справочник статусов пуст.** В данных встречаются 8 значений:

  | DONE | 8 212 |
  | APPROVED | 750 |
  | NEW | 63 |

Есть таблицы-заготовки: шаблоны документов, шаблоны и типы рассылки, справочник статусов, параметры содержимого, архив. Все пусты, код их не использует.

## 4. Маршруты по видам

Кнопки на форме задаёт таблица «вид × состояние» в коде (`DocumentFlowController.java:84-140`). Состояние берётся **из открытой задачи текущего пользователя**, а не из документа, поэтому каждый участник видит свою ступень. Сервер не проверяет, что у пользователя есть задача и что действие допустимо: состояние приходит скрытым полем формы. Полные таблицы переходов в приложении A, §3.4.

### 4.1 Входящий: так работают 99 % входящих

```
Регистратор: «Зарегистрировать»  → номер ВХ, дата = сегодня; задача себе «Отправить ответственным»
Регистратор: «Утвердить»         → задачи руководителям-получателям (текст = резолюция)
Руководитель: «Отправить на исполнение» → выбирает исполнителей, срок, резолюцию → задачи исполнителям
              «Отклонить»         → задача регистратору «Переназначить»
Исполнитель:  «Завершить»          → закрывает свою задачу; документ DONE, когда открытых задач не осталось
```

Что вводит регистратор:
- отправителя (организация, физлицо или свободный текст);
- исходящий номер и дату отправителя;
- тему;
- получателей (сотрудники);
- срок «КОНТРОЛЬ»;
- скан (PDF).

Поле «Закрыт документом» связывает входящий с ответным исходящим. Заполнено у 225 документов, на статус не влияет.

### 4.2 Исходящий

```
Автор создаёт   → сразу APPROVED (утверждение и согласование пропускаются, любые кнопки игнорируются);
                  задача «Зарегистрировать» всем регистраторам исходящих
Регистратор: «Зарегистрировать» → номер ИД; задача «Завершить»
Регистратор: «Завершить»        → DONE
```

Поле «Согласующие» на форме есть, но согласующим задачи не создаются: они попадают только в журнал и в участники. Отправителем по умолчанию подставляется пользователь `ruk001`, логин зашит в код. Регистраторов задаёт системная константа, а форма её сохранения сломана (§10).

### 4.3 Внутренний: 37 документов за 7 лет

```
Автор → («На согласование» согласующим) + («На рассмотрение» утверждающему, параллельно)
Утверждающий: «Утвердить» → исходящий номер подразделения автора; задачи получателям
                «Отклонить» → задача автору вернуть на доработку
Получатель:   «Принять»   → входящий номер подразделения получателя; «Назначить исполнителя»
              «Отправить на исполнение» → исполнители
Исполнитель:  «Завершить»
```

Согласование не блокирует утверждение. Если согласующий отказывает, автор об этом не узнаёт.

## 5. Регистрация и нумерация

| Вид | Как устроено на деле (база 2019–2026) | Что в коде |
|---|---|---|
| Входящий | Число без префикса. **Каждый год с 1**: 2019 — 1…6 416, 2024 — 1…4 281, 2025 — 1…3 341, 2026 — 1…720 | Единый счётчик `(0,0,0).incoming` без года, сброса нет. Обнуляют вручную в базе |
| Исходящий | `<код отдела>/<номер>`, например `19-03-01/2172`. Номер **сквозной на организацию** в пределах года, а код отдела — только префикс: в 2024 году у разных отделов номера 1…5 274 перемежаются | Единый счётчик `(0,0,0).outgoing`, префикс `{КО}` = описание подразделения |
| Внутренний | `<код отдела>/<номер>`, счётчик на подразделение | `(отдел, вид, 0)` отдельно для исходящего и входящего номера |

Ещё по нумерации:
- **Формат настраивается на уровне вида.** Это строка с токенами `{No} {ВД} {ТД} {КО} {КС} {ДД} {ММ} {ГГ} {ГГГГ}`.
- **Разбор формата с ошибками.** Повторный токен не заменяется, `{ГГ}` путается с `{ГГГГ}`, дополнение нулями падает на нечисловых токенах.
- **Нет блокировки.** В данных есть дубли: 5 номеров входящих и 2 номера исходящих в одном году.
- **Номер присваивается при регистрации и больше не меняется.** Отмены и перерегистрации нет.
- **Дата регистрации исходящего вводится руками, контроля нет.** В 155 документах дата-заглушка (1899, 2008, 2018). В 1 431 документе дата позже даты создания.
- **Номер корреспондента у входящих чаще всего пустой.** 15 451 раз записано «б/н» или «н/ж», у 1 153 номера нет вовсе.

## 6. Сроки, задачи, контроль исполнения

- **Срок у документа один** («КОНТРОЛЬ», `documentDueDate`). Он же становится сроком почти всех задач. Задан только у 1 000 документов (1,3 %).
- **Красный цвет не означает просрочку.** В списках срок выделен красным всегда, когда он задан. Сравнения с сегодняшней датой нет.
- **«Контроль исполнения» (`/doc/report`) — это список задач, которые поручил я.** Статус не фильтруется, просрочка не считается. Автоматические задачи (без автора) в список не попадают.
- **Уведомлений нет: ни почты, ни сообщений.** Сигнал о новой работе — только оранжевая строка в списке, жирная, если задачу ещё не открывали.
- **Задача закрывается кнопкой «Завершить» с текстом результата.** Если у человека две задачи по документу, кнопка закрывает только первую. Документ тогда не перейдёт в DONE никогда.
- **Нет действий с задачей:** продлить срок, переназначить, отозвать, вернуть исполнителю.

Отсюда 86 тыс. открытых задач, в том числе с 2019 года. Это не «работа в процессе»: система не умеет закрывать хвосты, и никто их не видит.

| Что | Как |
|---|---|
| Список | Только документы, где пользователь есть в `document_users`. Фильтр одинаков для всех, **администратор тоже не видит чужое** |
| Подразделение, руководитель, замещение | Не участвуют. Сотрудник видит документ, только если его назначили лично |
| Просмотр, правка, скачивание, удаление файла по прямой ссылке | Любой залогиненный |
| Админский редактор `/doc/admin/edit/{id}` (правит всё: статус, участников, задачи) и `/doc/admin/delete/{id}` (удаляет документ вместе с задачами) | Любой залогиненный, ссылки на них нет в меню |
| Создание входящего | Право `PERM_ADD_INCOMEDOC`, но проверяется только скрытием кнопки |
| Справочники видов и типов | Пункт меню только для ADMIN, сами адреса открыты всем |

Есть и уязвимости:
- поиск и сортировка собирают SQL склейкой строк;
- текст документа выводится без экранирования, а это хранимый XSS;
- удаление и регистрация вызываются запросом GET, защиты от CSRF нет.

## 8. Связь с кредитным ядром

Прямой ссылки «документ → заёмщик, кредит, процедура взыскания» **нет**. Есть три косвенных пути, все односторонние:

1. **Карточки физлица, организации и фазы взыскания** ищут документы, где этот контрагент указан отправителем или адресатом. Поиск идёт сырым SQL по `cat_responsible_*`.
2. **«Информация» по объекту** (кредит, фаза, платёж) хранит список id документов. На практике ссылка идёт через вложение, и код типа объекта (`system_object_type_id = 4`) отсутствует в справочнике. По базе нельзя установить, указывает он на кредит или на физлицо.
3. **Снятие ареста с залога** хранит id документа строкой.

«Список претензий» в меню «Документы» (`/collectionPhaseViews/claim`) — экран модуля взыскания, он не читает `df_document`. Претензии как вид документа (35 штук) живут отдельно от претензий во взыскании. Пакеты документов кредитного решения (`documentPackage`, `entityDocument`) тоже не связаны с документооборотом.

ТЗ требует обратного (п. 4 подсистемы взыскания): «Все направленные документы должны регистрироваться в подсистеме документооборота как исходящий документ». То есть исходящий обязан знать, к какому делу он относится.

## 9. Вложения, журнал, архив

- **Файлы хранятся на диске сервера** (`/opt/uploads/<uuid>.atach`), в базе только имя, MIME и автор.
  - Из 38,7 тыс. вложений 38,6 тыс. — PDF, то есть сканы.
  - Размер файлов нигде не записан.
  - Лимит на файл 100 МБ, хотя в комментарии к коду указано 5 МБ.
  - Белого списка типов нет.
  - Версий нет.
  - Удалить файл может любой: кнопка видна только автору файла, но сервер права не проверяет.
- **В именах файлов есть ФИО людей.** Для новой системы нужно правило именования, этот вопрос относится к ПДн.
- **Журнал действий** (`cat_dispatch_data`) записывает кто, когда, какое действие и примечание. На карточке есть ещё вкладка с историей задач. Это рабочая часть, её стоит сохранить.
- **Рассылки** (способ отправки адресату, отметка о вручении) нет, хотя классы так названы. Дата и способ фактической отправки исходящего не фиксируются.
- **Архив** (`df_archive`: дело, кабинет, полка, ряд, папка) — отдельный реестр, с документами не связан. В нём 0 записей, пункт меню закомментирован, сохранение создаёт дубль.

## 10. Дефекты-кандидаты (→ `notes/qa-findings.md`, префикс `E2E-`/legacy, без `Pn-NN`)

Из кода, на стенде не воспроизводились:

1. **Падение на завершённом документе.** Открытие завершённого внутреннего или входящего документа по `/doc/edit/{id}` даёт ошибку 500 (`ArrayIndexOutOfBounds`).
2. **Исходящий утверждается без утверждения.** Он сразу получает статус APPROVED, согласующим задачи не создаются.
3. **Отказ согласующего теряется.** Отказ не возвращается автору внутреннего документа, согласование не блокирует утверждение.
4. **Документ может навсегда остаться незавершённым.** Если у человека несколько задач по документу, «Завершить» закрывает только первую.
5. **Форма «Константы» не сохраняет.** Она шлёт на `/doc/constants/save`, а обработчик висит на `/doc/task/save`, поэтому список регистраторов исходящих через UI не меняется.
6. **Ошибки нумерации:**
   - нет сброса по году и блокировки;
   - на пустом счётчике создание входящего падает;
   - разбор `{ГГ}`/`{ГГГГ}` и повторных токенов с ошибками;
   - у внутренних затирается числовой индекс.
7. **Права и безопасность:**
   - админские адреса, удаление и скачивание открыты любому;
   - SQL склеивается строкой;
   - хранимый XSS;
   - изменения через GET.
8. **Поле «Примечание» у исходящих не появляется никогда.** Шаблон проверяет переменную `hasReject`, которой нет.
9. **Переименование типа документа меняет его идентификатор** (`internalName`), а по нему строятся ссылки на создание и фильтры.
10. **Архив сломан.** Правка создаёт дубль, после сохранения 404, пункт меню скрыт.
11. **Битые подписи и опечатки в интерфейсе.**
    - Вместо текста выводятся коды: `label.document.executer`, `label.document.pageIndex`, `label.document.pageCount`, `label.documentTypes`, `label.documentSubType.*`.
    - Опечатки: «Входяший/Исходяший», «Испонитель», латинская «K» в «KОНТРОЛЬ».
12. **Фильтр «Получатель» во внутренних — выбор дат вместо текста.** Список по умолчанию отсортирован от старых к новым.
13. **«Красный срок» в списках не означает просрочку,** а «Контроль исполнения» игнорирует фильтр статуса.

## 12. Что из этого следует для ТЗ нового модуля

Это не требования, а выводы, которые нужно решить при написании ТЗ.

**Перенести обязательно** (этим живут пользователи):
1. Журнал входящих: регистрация скана, номер и дата корреспондента, отправитель, наш номер по году, резолюция руководителя, исполнители, срок, отметка об исполнении, ссылка на ответ.
2. Журнал исходящих: тип (24 вида писем, исков, уведомлений), адресат, номер «код отдела / сквозной номер года», дата, скан, регистратор.
3. Журнал действий по документу и история задач.

**Исправить** (в старой системе сломано или отсутствует):
1. **Связь документа с делом:** заёмщик, кредит, процедура и фаза взыскания, залог. Без неё ТЗ п. «все направленные документы — исходящие» не выполнить.
2. **Сроки и просрочка:** вычисляемый статус задачи, отчёт «в работе / просрочено / в срок / с опозданием» (ТЗ :711), напоминания.
3. **Нумерация:** сброс по году в правиле, а не руками; уникальность; блокировка при выдаче номера.
4. **Права:** по участию, подразделению и роли, с проверкой на сервере. Видимость у руководителя и замещающего.
5. **Действия с задачей:** продлить, переназначить, отказаться с основанием (это есть в ТЗ, в подсистеме заданий).
6. **Согласование исходящих и внутренних:** последовательное или параллельное, с возвратом автору.
7. **Дата и способ фактической отправки исходящего.** Это важно для претензий и сроков во взыскании.

**Решено** (§13): внутренний документооборот и архив бумаги делаем; шаблоны живут в модуле «Отчётность».

**Пересечения с решениями нового проекта, которые придётся пересмотреть:**
- **ADR-0161** («модуля документооборота нет и не будет», исходящий номер бланка тратится в отчётности). При появлении модуля номер исходящего должен выдавать журнал исходящих.
- **ADR-0149 §4.** Модуль документооборота отсутствует, но «появится модуль — появится запись реестра» статистики.
- **ADR-0210, ADR-0227, ADR-0228** (модуль «Задания»). Задачи по документу должны быть заданиями этого модуля, а не отдельной таблицей, как в старой системе.
- **ADR-0230** (уведомления), **ADR-0223** (рабочая бумага, окончательность и исходящность), **ADR-0039** (три даты меры: получение, регистрация, штамп).

**Перенос данных:** 74 тыс. документов, 38 тыс. сканов на диске и 273 тыс. задач. Открытые задачи (86 тыс.) переносить как открытые нельзя, нужно правило массового закрытия.

## 15. Решения по устройству модуля (09.10.2026, второй разбор)

Ответы дал пользователь от имени заказчика, по рекомендованным вариантам. Дополняют §13 и вместе с ним служат основой ТЗ. Повторно не обсуждать.

| # | Тема | Решение |
|---|---|---|
| 1 | Статус документа | **Этап хранится** в документе. **Исполнение вычисляется** из заданий модуля «Задания» и показывается сводкой: «поручений 2: исполнено 1, просрочено 1». Отдельного хранимого статуса исполнения нет (как ADR-0227: итог выводится, а не хранится) |
| 2 | Этапы | Одна цепочка для всех видов: **Черновик → Согласование → Подпись → Зарегистрирован → В деле**. Входящий идёт из черновика сразу в «Зарегистрирован». Отказ согласующего или подписанта возвращает документ в «Черновик» с комментарием. «Отправлен» — не этап. Отправка ведётся по каждому адресату, на карточке — сводка «отправлено 2/3: вручено 1, возврат 1» |
| 3 | Ошибочная регистрация | Черновик можно удалить, у него нет номера. Зарегистрированный документ не удаляется. Действие «Аннулировать» с обязательным основанием переводит его в этап «Аннулирован», номер остаётся занятым и виден в журнале с основанием. Аннулировать нельзя, если хотя бы одному адресату уже отправлено. Опечатка в реквизите исправляется действием «Исправить», в журнал пишется «было/стало, кто, когда». Отмены регистрации с возвратом номера нет |
| 4 | Исполнение входящего | В справочнике типов входящих есть флаг **«требует ответа»** (по умолчанию из типа, регистратор может изменить у конкретного документа). Если флаг стоит, поручение гаснет, когда ответный исходящий зарегистрирован и отправлен отправителю входящего. Если не стоит — по отметке исполнителя «Исполнено» с текстом результата. Флаг **«на контроле»** (ставит регистратор, указывает контролёра) добавляет подтверждение контролёра. Один исходящий может закрыть несколько входящих |
| 5 | Резолюция | Отдельная запись: автор, дата, текст (из справочника фраз, можно дописать), **один ответственный**, соисполнители (0 и более), срок. Резолюции идут **каскадом**: исполнитель может дать свою резолюцию ниже, её срок не может быть позже срока родительской. Каждому исполнителю создаётся задание. ### 0. Главное

1. **Документ — это строка `df_document` + журнал `cat_dispatch_data` + задачи в общей таблице `task`.**
   - Процесс двигают не состояния, а **задачи** (`task`, `objectType='Document'`, `objectId=doc.id`).
   - Кому что делать, определяет открытая задача пользователя.
   - Состояние документа для конкретного пользователя берётся из `task.progress` его открытой задачи (`CTL/DocumentFlowController.java:231-234`).
2. **Конечный автомат `State.next()` и `util/FSM.java` мёртвы, их никто не вызывает.** Реальные переходы зашиты в `if (action.equals(..))` в `saveInternalDocument`, `saveIncomingDocument` и `saveOutgoingDocument`. Допустимые действия — статическая матрица `ACTIONS[вид][состояние]` (`:84-140`).
3. **Глобальное состояние `df_document.documentState` часто не отражает процесс.** `SENT`, `STARTED`, `CLOSED`, `REJECTED` в таблицу практически не пишутся. Документ остаётся в `REQUESTED`/`ACCEPTED`, пока не закроются все задачи, затем становится `DONE`.
4. **Ролей на документ нет.** Есть только проверка «залогинен» и один permission `PERM_ADD_INCOMEDOC` (и тот проверяется только в UI). Видимость списка задаёт множество `document_users` (кто участвовал). Просмотр, правка и скачивание по прямому id никак не проверяются (§9).
5. **Рассылка (Dispatch) — это журнал действий, а не рассылка.** `cat_dispatch_data` хранит «дата / кто / действие / примечание». Справочники `DispatchTemplate`, `DispatchType`, `DispatchResult` не используются (§6).
6. **Архив (`df_archive`) полностью отвязан от `df_document`.** Это отдельный реестр «дело + место хранения + файлы», который заполняется вручную (§7).

### 3. Жизненный цикл

#### 3.1 Что есть в коде

- `State` (13 значений, `DOC/model/State.java`): `NEW`(0) Новый, `DRAFT`(1) Создан, `PENDING`(2) Отправлен на согласование, `RECONCILED`(3) Согласован, `REQUESTED`(4) Отправлен на утверждение, `APPROVED`(5) Утвержден, `REJECTED`(6) Отклонен, `REGISTERED`(7) Зарегистрирован, `ACCEPTED`(8) Принят на исполнение, `SENT`(9) Отправлен на исполнение, `STARTED`(10) Начат, `DONE`(11) Завершен, `CLOSED`(12) Закрыт. Строки в файле: NEW:7, DRAFT:35, PENDING:59, RECONCILED:79, REQUESTED:99, APPROVED:123, REJECTED:151, REGISTERED:178, ACCEPTED:206, SENT:219, STARTED:245, DONE:258, CLOSED:271.
- `State.next(Transition)` — «ожидаемая» таблица, где любой непредусмотренный переход молча уходит в ветку `else` (например, `NEW.next(любой)=DRAFT`). **Нигде не вызывается** (поиск `.next(` по Web/Doc/Task пуст).
- `Transition` (`Transition.java`): `NONE`, `CREATE`→DRAFT, `TORECONCILE`→PENDING «На согласование», `RECONCILE`→RECONCILED «Согласовать», `REQUEST`→REQUESTED «На рассмотрение», `APPROVE`→APPROVED «Утвердить», `REJECT`→REJECTED «Отклонить», `REGISTER`→REGISTERED «Зарегистрировать», `ACCEPT`→ACCEPTED «Принять», `SEND`→SENT «Отправить на исполнение», `START`→STARTED «Начать», `DONE`→DONE «Завершить». `Transition.state()` служит «меткой» для журнала и для `new`-веток; `START` и `CREATE` не используются.
- `util/FSM.java` — отдельный черновик, никем не используемый (другие имена состояний: NEW/CREATED/APPROVED/REJECTED/ACCEPTED/STARTED/DONE/PENDING; `next()` в большинстве возвращает null).

#### 3.2 Какие действия доступны: матрица `ACTIONS` (`DocumentFlowController.java:84-140`)

Индекс столбца = `State.ordinal()`. Состояние, по которому смотрится матрица, — **per-user** (см. 3.3). Массивы internal и incoming содержат только 11 элементов (индексы 0-10), outgoing — 12. **Состояние `DONE`(11)/`CLOSED`(12) у internal/incoming даёт `ArrayIndexOutOfBounds` в `getActions`/`hasComment` (:327,341).** Открытие `/doc/edit/{id}` завершённого внутреннего или входящего документа по прямому URL вернёт 500. Из списка ссылка «редактировать» ведёт только на документы с открытой задачей, поэтому в UI это не проявляется.

Кнопки строит `TPL/doc/layout.html` (fragment `documentActions`, :190-200). `TORECONCILE` и `SEND` открывают модальное окно выбора сотрудников (`edit.html:103-120`): для TORECONCILE это «согласующие», для SEND — «исполнители + срок + резолюция».

`hasComment` (:336-347): поле «Примечание» показывается, если у состояния больше одного действия и первое из них REJECT или DONE.

#### 3.3 Как состояние выбирается per-user

В `edit` (:224-235) ищется **открытая задача текущего пользователя** по этому документу (`taskService.getTask(user, {objectId, status=OPEN, objectType=Document})`). Если у задачи заполнен `progress`, то `document.setDocumentState(State.valueOf(task.progress))`. По этому состоянию строятся кнопки и поля. Форма затем **отправляет состояние в скрытом поле** (`TPL/doc/layout.html:14`, `hiddenFields`), и `save` использует его как `document.getDocumentState()`. Следствия:
- согласующий видит `PENDING`, получатель с задачей «Назначить исполнителя» видит `ACCEPTED`, исполнитель — `SENT`, автор после отказа — `DRAFT`; глобальное состояние при этом другое;
- там, где ветка не вызывает `setDocumentState`, `documentService.update(document)` пишет в БД **значение из формы**, то есть per-user состояние инициатора (так, RECONCILE у согласующего записывает в `df_document` значение `PENDING`).

#### 3.5 Побочные эффекты

- **Уведомлений нет.** Нет почты, SMS, WebSocket, push. Слушатель `TaskListener` (`TASK/listener/TaskListener.java`) ничего не делает, `MFNotification` не используется. «Уведомление» = открытая задача и подсвеченная строка в списке (`/doc/tasks/all`, класс `active-document` в `index.html`). ### 4. Регистрация и нумерация

`CounterServiceImpl.generateRegistrationNumber(document, userId)` — `DOC/service/CounterServiceImpl.java:45-140`. Вызовы: `CTL/DocumentFlowController.java:541` (internal APPROVE), `:596` (internal ACCEPT), `:675` (incoming REGISTER), `:830` (outgoing REGISTER).

#### 4.1 Ключ и значение счётчика (`df_counter`)

| Вид | Ключ `(department, documentType, documentSubType)` | Поле | `department` берётся |
|---|---|---|---|
| incoming | `(0,0,0)`, единый для организации | `incoming` | — |
| outgoing | `(0,0,0)` | `outgoing` | — |
| internal, регистрация отправителя (глобальное состояние `REQUESTED`, :71-76) | `(dept(owner), documentType, 0)` | `outgoing` | подразделение **автора** (`document.getOwner().getStaff().getDepartment()`) |
| internal, регистрация получателя (все прочие состояния, :77-82) | `(dept(текущий пользователь), documentType, 0)` | `incoming` | подразделение **принимающего** |

- Подвид в ключ попадает только в ветке «прочие». У internal нумерация общая для всех подвидов (СЗ, З, ПЗ) подразделения.
- `CounterDaoImpl.getCounter` (`:13-36`) читает строку; если её нет, **создаёт с `incoming=1`, `outgoing=1`** (`:32-33`). Нумерация с 1. В номер идёт текущее значение поля, затем `+1` (`updateIncoming/updateOutgoing`, `CounterServiceImpl.java:146-154`).
- **Сброса по году или месяцу нет**: ключ без года, счётчик монотонный. Год появляется только в тексте, если формат содержит `{ГГ}`/`{ГГГГ}`.
- Блокировок нет (ни `FOR UPDATE`, ни `@Version`). Параллельные регистрации могут получить один номер.
- `document.setDocIndex(c)` и `documentService.update(document)` (:90-91) сохраняют число в документ. Для internal контроллер передаёт загруженную копию `doc`, а затем сохраняет форму `document` со старым скрытым `docIndex`, и **числовой индекс затирается** (дефект, §12). Для incoming/outgoing передаётся сама форма, индекс сохраняется.
- `/doc/new` для incoming подставляет `registerService.getIncomingNumber()` (`:188`). `CounterDaoImpl.getIncomingNumber` (`:40-44`) делает `getSingleResult()` по ключу `(0,0,0)`. В чистой БД строки нет, и создание входящего падает с `NoResultException`, пока не зарегистрируют первый документ. Seed строки `(0,0,0)` в `SQL/*.sql` нет.

#### 4.2 Формат

`cat_document_type.regNoFormat` (`DocumentType.java:19`). Сид (`SQL/doc_data.sql:3-5`) для всех трёх видов: **`{No}:{ВД}-{ДД}/{ММ}`**, например `15:ВХ-09/10` (номер 15, код вида «ВХ», день и месяц регистрации).

Подстановки (`CounterServiceImpl.java:93-122`):

| Токен | Значение |
|---|---|
| `{No}` | число из счётчика |
| `{ВД}` | `documentType.code` (ВН / ВХ / ИД) |
| `{ТД}` | `documentSubType.code` (СЗ, З, ПЗ, Д, ПЛ) |
| `{КО}` | `department.description` подразделения (задаётся только в ветках outgoing и internal; для incoming токена нет) |
| `{КС}` | `user.getId()` автора (не код сотрудника) |
| `{ДД}`, `{ММ}` | день, месяц текущей даты (две цифры) |
| `{ГГ}`, `{ГГГГ}` | год двумя или четырьмя цифрами |

Дополнение нулями: `{No5}` — ширина берётся из цифр внутри скобок (`replaceAll("\\D+","")`) и применяется как `%05d` к `Integer.valueOf(значение)`.

Дефекты разбора (`:124-137`):
- для каждого токена обрабатывается **только первое** вхождение (`find()` вызывается один раз);
- шаблон `\{ГГ(.*?)}` совпадает и с `{ГГГГ}`, результат зависит от порядка `HashMap`;
- дополнение нулями у нечисловых токенов (`{ВД2}`, `{КО2}`) даёт `NumberFormatException`;
- если у вида нет `regNoFormat` — `NullPointerException`;
- уникальность номера не проверяется.

#### 4.3 Даты регистрации

- internal: `senderRegisteredDate=now` при APPROVE (:542), `receiverRegisteredDate=now` при ACCEPT (:597).
- incoming: `receiverRegisteredDate=now` при регистрации (:676); номер и дата **отправителя** вводятся вручную.
- outgoing: дата — поле формы `senderRegisteredDate`; для нового исходящего без `docIndex` предзаполняется `new Date()` (:237-240).

### 6. Рассылка (Dispatch)

Название обманчиво. «Dispatch» здесь — **журнал действий над документом**, а не рассылка по адресатам.

- `DispatchData` (`cat_dispatch_data`): `dispatchType` = enum `State` (какое состояние или действие записано), `description` (HTML: имя адресата или «Зарегистрирован. Исходящий №…»), `dispatchInitTime`, `dispatchBy`. Поля `dispatchResponseTime` и `dispatchTo` **нигде не заполняются**.
- Запись добавляет `setDispatchData` (`:348-358`) в каждой ветке. Вкладка «Журнал» (`TPL/doc/layout.html`, fragment `journal`, :176-200) выводит: Дата, Пользователь (`dispatchBy.staff.name`), Действие (`dispatchType.text()`), Примечание.
- API: `GET /dispatchData?id=` и `/dispatchData/{id}` (`CTL/DispatchDataController.java`, без проверок доступа), `POST /dispatchData/save/{id}` (при `id` записи = 0 добавляет запись в документ, иначе обновляет), `GET /doc/dispatchData/{documentId}` (`DocumentFlowController.java:994-1002`); админ-правка записи `/doc/dispatchData/save` (`AdminDocumentController.java:125-134`) — **любой залогиненный**.
- **Способов рассылки (email, почта, нарочно), шаблонов и результатов доставки в коде нет.** `DispatchTemplate`, `DispatchType`, `DispatchResult` — пустые справочники.
- Фактическая «рассылка» — раздача задач нескольким сотрудникам (получатели, исполнители, согласующие), каждому своя строка `task` и запись журнала.

### 13. Что делает старая система (для переноса)

Не требования, а наблюдения: что новому ядру надо повторить, а что осознанно отбросить.

1. Три вида; у каждого свой маршрут (матрица §3.2) и свои поля.
2. Маршрут движется задачами; у каждого участника своя «ступень» (`progress`), определяющая его кнопки.
3. Общее состояние документа вычисляется как «все задачи закрыты → DONE»; промежуточные состояния не нормированы.
4. Согласование параллельно утверждению и его не блокирует.
5. Регистрация: счётчик на (подразделение, вид), общий для входящих и исходящих; формат настраивается на уровне вида; у внутреннего два номера (исходящий и входящий).
6. Журнал действий (кто, когда, что, примечание) и история задач (кому, срок, результат, завершено).
7. Видимость по списку участников; доступ по ссылке не ограничен (риск).
8. Вложения на диск, метаданные в БД; без версий и ограничений типов.
9. Связь документов с кредитным ядром идёт через контрагента-ответственного, через `Information.documentIds` и через строковое поле в залоге. Единой ссылки «документ ↔ заём / заёмщик / процедура» нет.
10. Просрочка, эскалация, напоминания и отчёт по ним **не реализованы**. Это пробел старой системы, а не поведение для сохранения.

### 4. Формат регистрационных номеров

Номер хранится в `senderRegisteredNumber` (исходящая сторона и внутренние) или `receiverRegisteredNumber` (входящие, «наш» номер). Выгрузка: 109 376 непустых номеров, 42 012 уникальных значений.

| Вид | Сторона | Шаблон (9 = цифра, A = буквы) | Строк | Примеры (только номер) |
|---|---|---|---|---|
| Входящий (2) | receiver (наш номер) | `9` (только цифры) | 37 238 | 3165, 4748, 1943 |
| Входящий (2) | sender (номер корреспондента) | `A/A` (плейсхолдер) | 15 074 | `б/н`, `н/ж` (всего 10 значений) |
| Входящий (2) | sender | `9`, `9-9/9`, `9/9`, `A-9/9` и др. | остаток (всего 562 различных шаблона по всем видам и сторонам) | `ГД-174/2011` |
| Исходящий (3) | sender | `NN-NN-NN/N` (`9-9-9/9`) | 34 617 | 19-04-02/117, 19-03-01/2172, 19-03-01/3808 |
| Исходящий (3) | sender | `NN-NN/N` (`9-9/9`) | 1 341 | |
| Внутренний (1) | sender | `NN-NN/N` и `NN-NN-NN/N` | мало (не считалось точно) | 19-07/4, 19-07/2, 19-04-03/5 |
| Претензия (5), АС (4) | sender | `NN-NN-NN/N` / `A-9` | 35 + 1 | |

Вывод по формату:
- Исходящие и внутренние: `{КО}/{No}`, где КО = код-префикс вида `NN-NN-NN` (подразделение / тип), No = порядковый номер. Это соответствует `regNoFormat` в `cat_document_type`.
- Входящие: `{No}`, то есть только цифры по «нашему» номеру. Номер корреспондента — внешний, в произвольном виде.
- Номер в БД хранится целиком, без разбиения на КО и No.
