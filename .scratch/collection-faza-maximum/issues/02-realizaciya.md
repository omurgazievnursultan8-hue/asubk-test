## Question

Внести формулу «фаза — максимум по маршруту» в `mockups/collection/collection.html`,
применяя решения тикета «Точки интеграции» (01) по всем пяти пунктам (включая
найденный при подготовке пробел — вне-маршрутные фазы К2/К5/К6/К7).

**Ранг фазы (общий ключ для максимума).** Новая функция `phaseRank(ph)`, размещается
сразу после `contourOf` (:2225 район, когда `CONTOUR_LEVEL`/`phasesOf`/`contourOfPhase`
уже объявлены) — тот же ключ, что уже читает `sequenceReason` (уровень контура,
затем позиция внутри `phasesOf(контур)`), сведённый в один скаляр:
```js
function phaseRank(ph){
  const c = contourOfPhase(ph);
  if(!c) return -1;
  return (CONTOUR_LEVEL[c] ?? 0) * 100 + phasesOf(c).indexOf(ph);
}
```
Покрывает и маршрутные (К0/К1/К3/К4), и вне-маршрутные (К2/К5/К6/К7) фазы —
пункт 4а точек интеграции (фолбэк на `CONTOUR_LEVEL`+позицию).
`phaseSetter`/`phaseOf` (:1727 район, ссылка вперёд на `phaseRank` — тот же
паттерн, каким `contourOf`, :2225, уже ссылается назад на `phaseOf`; функции
`function`-объявлены и hoist-нутся, обе стороны вызываются только во время
рендера, после полного прохода скрипта — безопасно, прецедент уже есть в файле)
меняются:
```js
function phaseSetter(r){
  const ms = liveMilestones(r);
  if(!ms.length) return null;
  return ms.reduce((best, m) => phaseRank(measureSetsPhase(m)) >= phaseRank(measureSetsPhase(best)) ? m : best);
}
function phaseOf(r){ const m = phaseSetter(r); return m ? measureSetsPhase(m) : OPEN_PHASE; }
```
`>=` (не `>`) — при равенстве ранга выигрывает более поздняя по времени
(`liveMilestones` уже отсортирован по дате события по возрастанию, `reduce`
идёт слева направо) — тот же принцип выбора, что был у старой формулы для
единственного случая, где он ещё имеет значение.

**`ROUTE_ORDER`/`ROUTE_PHASES`** (:2254 район) — пункт 2 точек интеграции:
```js
const ROUTE_ORDER = [...phasesOf('К0'), ...phasesOf('К1'), ...phasesOf('К3'), ...phasesOf('К4')];
const ROUTE_PHASES = new Set(ROUTE_ORDER);
```
Единственная правка блока — было `new Set([...])` напрямую; `routePhaseOf`/
`phasesOfStage`, читающие `ROUTE_PHASES`, не меняются (пункт 3 — «Безакцептное
списание» уже стояло в исходном литерале, участвует на общих основаниях без
правки). `phasesOf('К0'/'К1'/'К3'/'К4')` остаётся собран через `CONTOURS`
(пункт 4 — перевод на новый источник это работа карты 5б).

**Чип «новый иск»** (пункт 1 — землится как есть, недостижим через UI до карты
5б). Новая функция `newClaimBadge(r)`, рядом с `trackBadges` (:1888) —
сиблинг по месту и стилю, не то же семейство функционально (трек — про
незакрытый трек взыскания, это — про живую веху позади текущего максимума):
```js
function newClaimBadge(r){
  const maxRank = phaseRank(phaseOf(r));
  const fresh = liveMeasuresOf(r).find(m => measureSetsPhase(m) === 'Иск' && phaseRank('Иск') < maxRank);
  if(!fresh) return '';
  return ` <span class="pill mid" title="Мера «${escAttr(fresh.num||fresh.kind)}» от ${escAttr((fresh.dates&&fresh.dates.event)||'')} — живая, но дело уже прошло дальше по прежнему решению (§3.2)">новый иск</span>`;
}
```
Ключ по `measureSetsPhase(m) === 'Иск'`, не по «любая веха позади максимума»:
позади максимума лежит вся обычная история продвижения (Претензия перед
Иском и т.п.) — это не аномалия, чип должен ловить именно повторное живое
исковое производство, а не спамить на нормальном пути.

**Найденный по ходу пробел:** «Исковое заявление» (вид, который назвал бы себя
в первом черновике) само фазу не ставит — `outcomes:null`, это обёртка-документ
над актом. Фазу «Иск» ставит «Определение о принятии искового заявления к
производству» (исход «принято к производству», :1476). Ключевать по виду
(`m.kind === 'Исковое заявление'`) значило бы, что предикат никогда не
сработает — у этого вида `measureSetsPhase` всегда `null`. Переключено на ключ
по ФАЗЕ (`measureSetsPhase(m) === 'Иск'`), не по имени вида — заодно не
завязывается и на будущие виды с тем же `setsPhase`. Решение принято при
подготовке тикета (деталь формулы, не архитектурная развилка), рассуждение
зафиксировано здесь для аудита.
Вызывается в тех же двух местах, что `trackBadges` (наряд п.4, прецедент
places):
- :6204/6209 (`trackLine`, строка списка) — добавить `newClaimBadge(r)` к
  тому же `trackLine`, тем же условием `out ? '' : ...` (чип не имеет смысла
  на закрытом требовании).
- :6697 (плитка «Фаза» карточки) — `${trackBadges(r)}${newClaimBadge(r)}`.

**`routePhaseOf`/`effectivePhaseOf`/`stageOfReq`/`phasesOfStage` (:2255-2270)** —
НЕ трогать: разный вопрос (замороженная роут-фаза на время активного состояния

**Готово, когда:**

## Answer

Внесено в `mockups/collection/collection.html`, но формула у `phaseSetter`
отличается от черновика этого тикета — регрессионный смоук на РЕАЛЬНОЙ
затравке (не гипотетика) поймал два расхождения с сегодняшним поведением на
конкретных требованиях (**req 341, 356, 357**), которые голый «максимум по
скалярному рангу» ломал. Оба разобраны и переспрошены отдельным грилингом
(вне исходных пяти пунктов тикета 01 — найдены при проверке, не при
подготовке):

1. **req 356/357** (К5 «Заявление об установлении правопреемника» проигрывало
   К3 «Решение суда» чисто из-за произвольного индекса внутри контура —
   `CONTOUR_LEVEL` у К3 и К5 совпадает, сравнение по позиции внутри контура
   между РАЗНЫМИ ветками бессмысленно). **Правка:** вне-маршрутные фазы
   (К2/К5/К6/К7 — не часть «phase» в целевой модели, §3.3) исключены из
   сравнения рангов; если последняя по времени живая веха вне маршрута, она
   побеждает как раньше, без сравнения.
2. **req 341** (апелляция отменяет решение суда, откатывает на «Иск» — §3.3
   прямо требует этот откат; голый максимум держал «Решение суда», что
   неверно). **Правка:** явное исключение по виду+исходу — если последняя
   живая веха — «Постановление апелляционной инстанции» с исходом,
   начинающимся на «отменено» (`isAppealReversal`), она побеждает без
   сравнения рангов. Без трассировки цепочки `basedOn` (предложена как
   альтернатива, отклонена — новая машина, не предусмотрена нарядом
   отдельно) отличить в общем случае «откат той же ветки» от «новая
   независимая претензия» нельзя, но у отката есть узнаваемый вид+исход, и
   только для него нужно именно исключение.

Итоговая формула — три ветки (см. комментарий у `phaseSetter`, :1726 район):
вне-маршрутная последняя веха побеждает как раньше → апелляционный откат
побеждает явно → иначе максимум по рангу среди МАРШРУТНЫХ живых вех
(единственная ветка, где новая формула вообще отличается от старой —
ровно сценарий §3.2).

**Второй найденный по ходу пробел** — предикат чипа «новый иск» из черновика
(«есть живая веха с фазой «Иск» позади максимума») спамил бы на КАЖДОМ
продвинутом К3/К4-требовании: веха-основание «Иск» всегда остаётся живой
позади текущей фазы при обычном продвижении — это не аномалия, а нормальная
история. Переделано на счётный предикат: **две или более** живых вехи с
фазой «Иск» одновременно (апелляционный откат исключён явно, `!isAppealReversal`
— иначе req 341 ложно считался бы задвоением, у него ровно веха-основание +
один откат). Найдено и проверено регрессионным прогоном `newClaimBadge` по
ВСЕЙ затравке без мутаций (ожидание: чип пуст везде) — первая версия
предиката это ловила бы как провал.

Остальное — как в черновике тикета, без изменений: `phaseRank` (:2225
район, ссылка вперёд из `phaseSetter`, безопасно — hoisting, обе стороны
вызываются только на рендере), `ROUTE_ORDER`/`ROUTE_PHASES` (:2279 район,
один источник), два места вызова чипа (:6250 строка списка, :6743 плитка
«Фаза» карточки), `routePhaseOf`/`effectivePhaseOf`/`stageOfReq` не тронуты.

Проверено throwaway jsdom-смоуком (`_smoke-faza-maximum.mjs`, создан,
прогнан, удалён — в репозитории не остался):
- `phaseRank` — корректный порядок внутри и между контурами, включая К7
  (вне-маршрутные), unknown-фаза → `-1`;
- регрессия: старый алгоритм (последняя по времени) и новый (три ветки)
  выбирают одну и ту же меру на **каждом** требовании затравки — 0
  расхождений (было 3 на голом максимуме, до правки веток 1/2);
- именные проверки req 341/356/357 — держат ожидаемую фазу явно, не только
  агрегатным счётчиком;
- чип «новый иск» пуст на всей затравке без мутаций (спам-проверка);
- synthetic: одна живая веха-основание «Иск» + продвижение до «На
  исполнении» → чипа нет; добавлена вторая независимая живая веха «Иск» →
  чип есть, цитирует именно вторую (более позднюю) меру, максимум остаётся на
  «На исполнении» (не откатывается);
- ни одной console/pageerror ни в одном сценарии.

Destination карты достигнут — с поправкой на найденную по ходу тестирования
более узкую (и более точную) формулировку, зафиксированной здесь и в
map.md. Полный прогон `collection-check.mjs`/`collection-data-audit.mjs`/
`collection-seed-coverage.mjs` не запускался (резерв на конец пятой волны).
