## Question

Пройти по одному вопросы, что destination оставил открытыми (`/grilling`,
рекомендация на каждый, ответ фиксируется здесь же):

1. **Представитель не в целях меры.** `rep[r.credit]` (`tileMoney`, :5900-5904) —
   представитель глобальный по ВСЕМ требованиям кредита, не по целям КОНКРЕТНОЙ
   меры. Если мера присудила только по созаёмщику/поручителю, а представитель
   («заёмщик», если жив среди требований кредита) в её `m.targets` не входит —
   что со слоем? Варианты: (а) слой не рождается — присуждено есть, но не на
   представительской строке, значит по правилу «сумма слоя — по представителю»
   слоя формально нет; (б) фолбэк — слой берёт сумму первой строки из `m.targets`,
   что принадлежит этому кредиту, тем же приоритетом ролей, что и `rep[]`, но
   ограниченным целями ЭТОЙ меры, а не всеми требованиями кредита.

2. **«Поглощает слой меры №X» — источник списка.** В коде нет живого UI-виджета
   «выбрать меру по номеру» (`basedOn` сегодня только SEED/backward-search,
   :3085, не живая форма) — придётся проектировать с нуля. Прецедент фильтрации
   есть: `courtActsOf(r)` (:6302) — живые меры вида «судебный акт» с `basedOn`.
   Предложение: `<select>`, опции — живые (не сторно) меры ЭТОГО дела, что уже
   несут `m.awards` для того же кредита, кроме самой текущей меры; подпись —
   `${m.kind} №${m.num} от ${m.date}`.

3. **Отношение к прежнему слою — обязательное поле?** Когда для кредита ещё нет
   ни одной меры с `m.awards` — предложение: поле не показывается вовсе (жёстко
   `новый слой`, без выбора). Показывать выбор (`новый слой` / `поглощает…`)
   ТОЛЬКО когда для этого кредита уже существует хотя бы одна более ранняя живая
   мера с `awards`.

4. **`layerOf(creditId)` — «последняя по дате» — какое поле даты.** У меры есть
   несколько кандидатов (дата регистрации меры, дата исхода/пометки). Предложение:
   дата исхода (когда `saveAnnotation` пишет `m.outcome`, тогда же пишется и
   `m.awards`) — она и есть момент, когда акт стал известен взысканию, а не дата
   регистрации самой меры (которая может быть раньше акта на дни).

5. **Валидация суммы присуждённого.** Есть ли верхний потолок (например, не выше
   «востребовано» по этой цели, `claimOf`/`scopeOf`)? Предложение: без потолка —
   суд юридически волен присудить иначе, чем просили; поле просто число ≥ 0,
   пусто = не присуждено по этой строке (не то же самое, что 0 — пусто не
   создаёт `awards`-запись вовсе, ноль создаёт запись с суммой 0).

6. **Аудит правки.** `saveAnnotation` уже требует «Причина правки» при
   перезаписи уже заполненного поля (:8040 район). Присуждено просто входит в
   ту же проверку — правка `awards` задним числом ТРЕБУЕТ причину, как и правка
   `outcome`. Это факт из уже прочитанного кода, не решение — фиксирую здесь,
   чтобы «Реализация» не гадала заново.

## Answer

Все шесть пунктов решены (`/grilling`, по одному, все рекомендации приняты без
правок):

1. **Представитель не в целях меры → слой не рождается.** Вариант (а). Никакого
   второго, локального-в-мере правила представителя не заводим — только глобальный
   `rep[r.credit]` из `tileMoney`. Гэп (иск только к поручителю/созаёмщику без
   представителя в целях) остаётся известным ограничением destination, не решается
   фолбэком.
2. **«Поглощает слой меры №X» — источник.** `<select>` из живых (не сторно) мер
   ЭТОГО дела, что уже несут `m.awards` по тому же кредиту, кроме самой текущей
   меры. Подпись опции — `${m.kind} №${m.num} от ${m.date}`.
3. **Поле «отношение к прежнему слою» — условно видимое.** Показывается ТОЛЬКО
   когда для кредита уже есть более ранняя живая мера с `awards` — тогда выбор
   `новый слой` / `поглощает слой меры №X`. Иначе поле не рисуется вовсе, жёстко
   `новый слой`.
4. **«Последняя по дате» в `layerOf`.** Дата исхода (момент `saveAnnotation`
   пишет `outcome`+`awards`), не дата регистрации меры.
   **Правка при реализации:** в коде уже есть прецедент «последняя» —
   `liveMilestones` (:1658-1664) — и он меряет по-другому: дата СОБЫТИЯ
   (`m.dates.event || m.dates.registered`) с явным обоснованием в комментарии
   («акт, поступивший с задержкой, не должен обгонять более раннюю по факту
   веху»). Это тот же сценарий, что и слой (мировое, поступившее с задержкой в
   систему, не должно перекрыть более раннее по факту решение суда) — не
   предпочтение, а обнаруженный при кодировании факт о существующем правиле.
   `layerOf` меряет ровно тем же способом, что `liveMilestones`, а не датой
   пометки — правка задним числом этого ответа, не второй вопрос к пользователю.
5. **Валидация суммы.** Без потолка (суд не связан суммой иска). Число ≥0. Пустое
   поле ≠ ноль: пусто → запись в `m.awards` для этой цели не создаётся; 0 →
   создаётся, с суммой 0 (акт был, присудил ноль).
6. **Аудит правки — факт, не решение.** `saveAnnotation` уже требует «Причина
   правки» при перезаписи заполненного поля (:8040 район). Правка `m.awards`
   задним числом попадает под ту же проверку, без отдельного кода — фиксирую,
   чтобы «Реализация» не изобретала параллельный механизм.
