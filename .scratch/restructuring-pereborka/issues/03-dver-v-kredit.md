## Question

Как одностраничное демо показывает «дверь в кредит» и движок на кредитной стороне. Сегодня
`amortize` (:458) живёт прямо в макете и зовётся из `calcRestructure`, а применение ДС
размазано: `regDS` (:1326) регистрирует реквизиты, `applyEntryOps` (:1339) правит суммы — то
самое «шесть дверей», которое РС-10 запрещает.

Пройти по одному:

1. **Форма двери.** РС-10: `restructureApplied(ds)` — кредит сам, атомарно и в своём порядке
   создаёт производный транш → выполняет перенос → кладёт версию графика → пишет записи
   условий → закрывает опустошённый транш → поднимает счётчик. «Полуприменённый ДС —
   состояние без выхода». Как атомарность показывается в демо, где нет транзакции: одна
   функция с проверкой предусловий до первой записи, или журнал-откат?
2. **Валидация на приёме (ИР-2, §6.6).** Кредит принимает **строки** графика и валидирует:
   Σ основного долга по строкам = сумме переноса, даты возрастают, последняя не выходит за
   конец срока. Что происходит при провале — тост, или ДС не регистрируется вовсе? И где
   проходит граница: заявка отдаёт строки, кредит их проверяет — в демо обе стороны в одном
   файле, значит проверка должна быть видимой, а не молчаливой.
3. **Черновик против графика.** «Заявка зовёт движок для черновика; черновик есть предмет
   согласования, а не источник графика». Как отличаются на экране черновик и вступивший
   график, и что происходит с черновиком после вступления ДС.
4. **Деньги при вступлении (РС-20).** Адресный резерв, стоявший на строках, ушедших в
   перенос, становится безадресным авансом **с уведомлением куратора** («тихое перецепление
   запрещено», `ADR-0074` §3); аванс закрытого переносом транша переезжает на кредит; план
   кредита реструктуризацией **не двигается** (`ADR-0042`). Что из этих трёх показывает демо
   реструктуризации, а что — заглушка-зеркало к платежам.
5. **Компенсирующий ДС.** «Отмена применённого ДС — компенсирующий ДС с обратным переносом и
   своей датой, а не откат». Заводится ли он в демо, или обозначается вехой в журнале.
6. **Счётчик реструктуризаций.** РС-6: считает **допсоглашения**, а не траншы (одна заявка по
   двум кредитам даёт два ДС). Где живёт счётчик и как показывается, что лимита повторов нет
   (вопрос 7 письма — порог и эскалация не отвечены).

## Answer

Решено 06.08.2026. Принцип трёх решений: **дверь одна и показывает свой домен целиком; чужой
домен (Платежи) она не достраивает — берёт зеркалом или обозначает вехой в журнале.**

### Факты, найденные чтением (разведка субагентом)

- `restructureApplied` в `restructuring.html` **не существует** (0 совпадений). Регистрация ДС
  размазана минимум по трём точкам: `regDS` (:1326–1338, пишет `app.ds`/`app.outcome`/
  `app.version.state`, зовёт `applyEntryOps`, **и сама** инкрементирует `c.restructCount+=1`
  на объекте кредита в обход какой-либо двери), `applyEntryOps` (:1339–1354, пишет журнальные
  записи `app.ops` и **напрямую** мутирует `cr.odDays=0`). Понятия «транш» в файле нет вовсе.
- ADR-0096 (`docs/adr/0096-odna-dver-v-kredit-dvizhok-amortizacii-u-kredita.md`) фиксирует
  порядок шести шагов как **некоммутативный и известный владельцу данных, а не вызывающему**
  (:16–18), и что «валидация строк — единственное место, где кредит вправе отказать» (:55–56).
- `credit.html` уже держит ровно нужный паттерн для мутирующих операций (:4279–4287): `gate()`
  → если заблокирован, `{ok:false, reasons}` и модель не тронута → если ok, применяет →
  append-only запись в `credit.audit`. В `restructuring.html` тот же приём уже живёт в
  сохраняемых стадийных гейтах `packetGate`/`conclGate`/`dsGate` (:631–634) — сосед внутри
  одного файла, не только через границу модулей.
- Прямого прецедента «кредит принимает чужие строки графика и валидирует» в `credit.html` нет —
  там `generateSchedule` строит график сам из своих параметров, а не принимает готовые строки.
  Этот кусок — новый, но форма (`gate` → `reasons`) переносится с соседних гейтов один в один.
- РС-20 (`ASUBK-restrukturizatsiya-logika.md` :277–283) — три механики: резерв → безадресный
  аванс с уведомлением куратора (`ADR-0074` §3), аванс закрытого транша → на кредит, план
  кредита реструктуризацией **не двигается** (`ADR-0042`). В `payments.html` первая механика
  есть **только текстом** в баннере (:1379–1382), без формы/кнопки; уведомления куратора как
  паттерна там нет вовсе (0 совпадений на «уведомлен»). Карта `Out of scope` явно выводит девять
  правок у соседей, включая Платежи, за пределы этой волны.
- Компенсирующий ДС описан дважды (§7 спеки :274–275, ADR-0096 :53–54) как «обратный перенос,
  своя дата, не откат» — но кода/кнопки под это нет нигде; демо-набор тикета
  [Реализация ядра](06-realizaciya-yadra.md) сценария отмены не заводит.
- Счётчик `restructCount` уже живёт на кредите (:396–420) и уже инкрементируется один раз на
  каждый кредит охвата заявки (:1333, `forEach(app.creditIds)`) — семантика «считает ДС, не
  транши» уже верна, просто вызов сейчас не внутри двери.

### 1. Форма двери — валидация до первой записи, gate-паттерн соседа

```js
const CreditSide = {
  draftSchedule(tranche, ds) { ... },         // чистый предпросмотр, решён тикетом 01

  restructureApplied(ds) {
    const reasons = validateDS(ds);            // ИР-2 и прочие предпосылки — ДО первой записи
    if (reasons.length) return { ok:false, reasons };   // ничего не тронуто, ДС не регистрируется

    const tranche = spawnTranche(ds);           // 1. производный транш
    transfer(tranche, ds);                      // 2. перенос
    tranche.schedule.push(newVersion(ds));       // 3. версия графика
    writeTermsEntries(ds);                       // 4. записи условий
    closeIfEmptied(ds.sourceTranche);            // 5. закрытие опустошённого транша
    ds.credit.restructCount += 1;                // 6. счётчик (было :1333, переезжает сюда)

    ds.credit.audit.push({ type:'ДС применён', ds: ds.no, ... });  // одна запись, не шесть
    return { ok:true };
  }
};
```

`validateDS` — ИР-2 буквально: `Σ principal(rows) === ds.transferSum`, даты строго возрастают,
последняя ≤ конца срока, плюс предусловия из существующих гейтов (пакет, заключение, Минфин).
Отказ называет нарушенное условие текстом — тем же списком-баннером, что уже держат
`packetGate`/`conclGate`/`dsGate`, а не отдельным тостом: это тот же класс события (гейт
заблокировал стадию), а не новый.

### 2. Черновик vs график — определено границей тикета 01, экран решает 05

Ничего нового не решаем: `draftSchedule` (чистый, для предпросмотра) и `restructureApplied`
(единственный пишущий) — это ровно два входа `CreditSide`, зафиксированные [Моделью демо](
01-model-demo.md). Черновик живёт на `app.version.plan` до вступления и не трогается дверью;
после вступления дверь кладёт **новую** версию графика на транш — черновик остаётся историческим
объектом заявки, не переписывается. Как это различается на экране (подпись/пилюля черновик vs
действующий) — открытый вопрос формы тикета [Вкладка расчёта](05-vkladka-rascheta.md), не этого.

### 3. Деньги при вступлении — план по-настоящему, резерв/аванс зеркалом

```js
// на кредите — реально, дверь его не трогает (ADR-0042)
credit.plan;   // restructureApplied не пишет сюда ни строки — план неизменен шагом двери

// к Платежам — зеркало-веха в журнале, не структура и не механика
ds.credit.audit.push({
  type: 'Резерв → аванс (зеркало)',
  detail: 'Адресный резерв на перенесённых строках становится безадресным авансом, куратор '
        + 'уведомлён — механика модуля Платежи (ADR-0074 §3), здесь не реализована',
  mirror: true,
});
```

План — целиком в домене кредита (ADR-0042), показываем реально: поле буквально не меняется
шагом двери, это и есть демонстрация «не двигается». Резерв→аванс и аванс→кредит — домен
Платежей, вне скопа карты (`Out of scope`); показываем той же формой зеркала, что и остальные
восемь швов к соседям (`showMirror` :1378), а не отдельной инфраструктурой ради одного места.

### 4. Компенсирующий ДС — веха в журнале, без рабочей кнопки

```js
app.ops.push({
  type: 'Отмена ДС (веха)',
  detail: 'Компенсирующий ДС — обратный перенос, своя дата (не реализовано в демо)',
});
```

Одна текстовая запись — той же формы, что уже есть у «Прощение санкций… компенсирующей
записью» (:1344). Минимальный демо-набор [Реализации ядра](06-realizaciya-yadra.md) сценария
отмены не требует; полноценный второй вызов `restructureApplied` дублировал бы уже показанный
механизм двери, не добавляя нового знания, а демо-набор пришлось бы расширять только ради него.

### 5. Счётчик реструктуризаций — уже верно устроен, переезжает внутрь двери

Ничего не меняется по смыслу: `restructCount` остаётся на кредите, инкремент — один раз на
каждый кредит охвата ДС (текущая семантика `:1333` уже совпадает с «считает допсоглашения, не
траншы»). Единственная правка — сам инкремент переезжает с `regDS` внутрь `restructureApplied`
шагом 6, чтобы не быть седьмой дверью.

### Что это меняет в других тикетах

- **05** получает точную границу: черновик и действующий график — разные объекты
  (`app.version.plan` vs `tranche.schedule`), различие на экране — её решение, не готовое.
- **06** получает готовый костяк реализации: `CreditSide.restructureApplied` с шестью шагами,
  `validateDS` с ИР-2, зеркало-веха для резерва/аванса, веха для отмены ДС.
- **08**: ИР-2 проверяется вызовом двери с заведомо неверными строками (`{ok:false, reasons}`
  без мутации), а не разбором кода; «план не двигается» проверяется сравнением `credit.plan`
  до/после ДС.
