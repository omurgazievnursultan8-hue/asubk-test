## Question

Назвать модель демо-данных, на которой держатся ИР-3, ИР-5 и РС-5. Сегодня макет держит
`state.credits` — плоский объект с `terms` и `snapshot` (`seedCredits` :394), траншей нет
вовсе, долг — четыре числа среза (`principal`, `overduePrincipal`, `accruedInterest`,
`penalty`, читаются в `calcRestructure` :524). Новая модель требует иного.

Пройти по одному:

1. **Транш как единица.** РС-2: охват заявки — траншы, не кредиты; `addCredit` (:1275) и
   `pScope` (:941) сегодня цепляют кредит целиком. Какой формы транш в демо, и как
   выражается `остаток = освоено − погашено − перенесено + принято` (ИР-3) — хранимым
   остатком с проверкой или выводимой величиной поверх датированных операций?
2. **Датированные операции.** РС-5 требует пяти вещей, из которых первая — «перенос есть
   датированная операция с основанием, а не правка суммы», четвёртая — «опустошённый транш
   закрывается переносом, не погашением» (ИР-5). Один общий журнал операций на транш
   (`{date, kind, amount, basis}`) или отдельные массивы по видам?
3. **Семь статей долга.** РС-13: расходы взыскания · сборы · накопленные проценты ·
   накопленная пеня · пеня · проценты · основной долг; срочность сжимается до двух значений
   (`просроченное → текущее`). Как это лежит в демо: статья × срочность матрицей, или список
   позиций с двумя реквизитами? Образец существующей пятистатейной формы — `payments.html`.
4. **Версия графика с периодом действия.** РС-5 п.3: «версия графика несёт период действия, а
   не только факт замены» — перестроение не затирает прежнее. Где живут версии и как по дате
   выбирается действовавшая.
5. **Граница «сторона кредита / сторона заявки» внутри одного файла.** Спека §1 разводит
   владение жёстко: записи условий, версии графика, траншы, перенос, счётчик — у кредита;
   расчёт, срез, черновой график, дифф — у заявки. В одностраничном демо это одна граница в
   коде. Где именно её провести, чтобы тикет 03 (дверь `restructureApplied`) имел на что
   опереться.
6. **Ключ субъекта вместо ИНН.** РС-2: якорь — ключ субъекта (`ADR-0019`), не строка ИНН
   (`baseApp` :668 принимает `inn`; `naFillCredits` :1468 ищет по ИНН). Что в демо служит
   ключом и как показывается смена ИНН при реорганизации.

Перед грилингом — инвентаризация фактов чтением: как `credit.html` уже моделирует транши
(280 вхождений) и как `payments.html` держит пять статей и три уровня срочности. Это факты,
не решения — смотреть, не спрашивать.

## Answer

Решено 06.08.2026. Сквозной принцип шести ответов один: **числа не хранятся там, где их можно
вывести, а форма берётся у соседа, если у него она уже есть.**

### Факты, найденные чтением (не решения)

- `credit.html` `mkTranche` (:1897) — `{id, no, subject{inn,name}, amount, plannedDate,
  conditionRecords[], disbursements[], schedules[], closed}`. **Поля `ledger` нет (ADR-0010)**:
  детальный расчёт строится при отображении из графика, условий на дату и зеркала платежей.
- `conditionsAt(t, date)` (:1699) — свёртка записей с `effectiveFrom ≤ date`. Готовая форма
  «величина на дату», её и повторяем.
- `schedules[]` (:2203) — `{ver, active, generatedFrom, generatedAt, rows[]}`: версия есть,
  **периода действия нет**. Ровно дыра РС-5 п.3.
- `fees[]` на кредите (:1939) — `{kind, date, amount, basis}`, реестр начислений, не производная.
- `closed` (:1903) — soft-close `{date, reason, by}`, Г-17.
- `payments.html`: статья лежит **строкой** (шесть подписей, из них две склейки —
  «Проценты и пеня», «Основной долг (присуждённый)»); срочность в данных уже **два** значения:
  `urg:'over'` 27 раз, `urg:'cur'` 5. Третьего уровня нет нигде — сжатие РС-13 данные уже пережили.
- `subject.html`: ключ — **плоская строка**; `keyKind` (:644) различает `ИНН` (14 цифр) и
  `ГР-NNN` (группа); псевдоним — `aliasOf` + `resolveKey` (:634) + `keysOf` (:640). Взыскание
  уже хранит `debtorKey`, не ИНН.

### 1. Остаток транша — выводимая величина, хранимого поля нет

`balanceAt(t, d) = Σ disburse − Σ repay − Σ transfer_out + Σ transfer_in` по операциям с
`date ≤ d`. **ИР-3 становится определением, а не проверкой** — нарушить нечем. Приём взят у
соседа (ADR-0010, «поля `ledger` нет») и у §6.5 спеки («долг на прошедшую дату — выводимая
величина»). Отвергнуто: хранимый остаток со сверкой (два источника правды об одном числе, и
РС-5 «перенос есть датированная операция, а не правка суммы» соблюдался бы только на словах);
кэш снимков рядом с формулой (снимки — про долг, тикет 02, а не про остаток транша).

### 2. Один журнал `ops`, чужие записи помечены, закрытие выводится

```js
tranche.ops = [
  {date, kind:'disburse',     amount, mirror:true,  owner:'Кредит',  basis:{doc}},
  {date, kind:'repay',        amount, mirror:true,  owner:'Платежи', basis:{alloc}},
  {date, kind:'transfer_out', amount, mirror:false, owner:'Кредит',  basis:{ds, to}},
  {date, kind:'transfer_in',  amount, mirror:false, owner:'Кредит',  basis:{ds, from}}
]
tranche.closed = {date, by:'ДС-1007', reason:'перенос'}   // reason ВЫВЕДЕН, не введён
```

`closed` остаётся полем (soft-close соседа, шов сходится), но `reason` не вводится — выводится
из того, какая операция обнулила остаток. **ИР-5 читается сравнением двух соседних строк одного
списка**: обнулил `transfer_out` → «перенос»; обнулил `repay` → полное погашение, другой случай,
и разница видна. Отвергнуто: три массива по видам (`balanceAt` складывает три формы, а ИР-5
требует слить их во временную ленту, чтобы вообще задать вопрос); закрытие пятым видом операции
(расходится с Г-17 соседа, шов пришлось бы объяснять в §12).

### 3. Долг — позиции с реквизитами; седьмая статья выводится

```js
const ARTICLES = [                       // порядок = очередь погашения (РС-13)
  {k:'collectionCost', n:'Расходы взыскания'}, {k:'fees', n:'Сборы'},
  {k:'accInterest', n:'Накопленные проценты', accrued:true},
  {k:'accPenalty',  n:'Накопленная пеня',     accrued:true},
  {k:'penalty', n:'Пеня'}, {k:'interest', n:'Проценты'},
  {k:'principal', n:'Основной долг', derived:true}
];
const URG = [{k:'over', n:'просроченное'}, {k:'cur', n:'текущее'}];
tranche.debt = [{article, urgency, amount, since, disputed?, periods?, basis}];  // ШЕСТЬ статей
principalAt(t, d) = { over: Σ principal строк графика с date < d, не покрытых repay,
                      cur:  balanceAt(t, d) − over }                            // СЕДЬМАЯ
```

Шесть статей **сеются данными** — движок начислений осознанная не-цель демо; основной долг
**не сеется никогда**, иначе решение 1 ломается вторым источником того же числа ровно там, где
смоук обязан показать ИР-3. Позиция, а не ячейка матрицы, потому что ячейка держит только число,
а нужны ещё `since` (с какой даты просрочено — пене и срокам взыскания), `disputed` (ИР-6:
спорная пеня в базу не входит **никогда**) и `periods` (выбранные периоды накопленного, РС-12).
Форма строки совпадает с разнесением в `payments.html` — шов сходится.

### 4. Версия графика — одна дата `validFrom`, конец выводится

```js
tranche.schedules = [{ver, validFrom, by:{kind, ref}, rows:[...]}];   // прежние НЕ затираются
scheduleAt(t, d) = последняя с validFrom ≤ d;   validTo(v) = следующая.validFrom − 1 день
```

Флаг `active` уходит совсем. Тот же приём, что `conditionsAt` соседа. «Долг на 15.06.2026» после
двух реструктуризаций берёт версию, действовавшую тогда, — это прямо сценарий §14. Отвергнуто:
хранить обе границы (дверь `restructureApplied` делала бы две записи вместо одной, и
«полуприменённый ДС» РС-10 получал бы лишний способ случиться); `active` + `replacedBy` (это и
есть «факт замены», который РС-5 называет недостаточным).

### 5. Граница владения — два неймспейса, у кредита ровно два входа

```js
const CreditSide = {           // ВЛАДЕЕТ tranche.{ops, schedules, conditionRecords, closed},
  balanceAt, scheduleAt, conditionsAt, principalAt,   //          credit.restructCount
  amortize,                    // приватный движок — уезжает сюда, РС-9
  draftSchedule(t, params, from),   // ЧИСТЫЙ: черновик, ничего не пишет
  restructureApplied(ds)            // ЕДИНСТВЕННАЯ пишущая дверь, РС-10
};
const AppSide = { /* ВЛАДЕЕТ app.{cutoff, base, dispositions, draftRows, diff, gates} */ };
```

Граница проверяема грепом: `tranche.ops.push` обязан встречаться только внутри
`restructureApplied`. Отвергнуто: секции-комментарии (нынешний `applyEntryOps` :1339 — «шесть
дверей» РС-10 — появился именно так); рантайм-сторож с заморозкой (демо начало бы учить
разработчика решению, которого в проде не будет, — там граница сетевая).

### 6. Якорь — плоская строка-ключ, псевдонимы разрешаются, реорганизация ≠ слияние

`app.anchorKey` — `'02508199700123'` (ИНН, частный вид) либо `'ГР-004'` (группа, второй вид);
`tranche.subjectKey` — при групповом кредите транш несёт **члена группы**, а не заёмщика
договора. Охват ищется по `keysOf(anchorKey)`, а не сравнением строк, — кредит на слитом ключе
из охвата не выпадает. Зеркало субъектов read-only:

```js
MIRROR.subjects = [
  {key:'…123', name:'ОсОО «Ак-Жол Агро»',        aliasOf:null},
  {key:'…999', name:'ОсОО «Ак-Жол» (дубль)',     aliasOf:'…123'},              // СЛИЯНИЕ
  {key:'…777', name:'ОсОО «Ак-Жол Агро Плюс»',   aliasOf:null,
   successorOf:'…123', since:'12.03.2026'}                                     // РЕОРГАНИЗАЦИЯ
];
```

Реорганизация псевдонимом **не является** (ADR-0019, «Следствия»: два живых лица со связью
правопреемства); в шапке заявки — строка «правопреемник …123 с 12.03.2026», оба ключа живы.

### Что это меняет в других тикетах

- **04, вопрос 3** закрыт наполовину: первоначальную ставку транша демо берёт из
  `tranche.originalRate` — реквизит, а не вывод из записей условий (записи можно перебить, а пол
  ставки РС-19 обязан считаться от исходной).
- **02** получает новый обязательный вопрос: **сцепка `repay` со строками графика.** `principalAt`
  требует знать, какие строки погашение покрыло; сегодня `repay` — просто сумма. Дописан в тело 02.
- **06** сверх снесённого получает новое: `MIRROR.subjects` с `resolveKey`/`keysOf` — такого
  зеркала в макете нет вовсе.
