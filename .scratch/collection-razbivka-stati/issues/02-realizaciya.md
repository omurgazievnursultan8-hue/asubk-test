## Answer

Внесено в `mockups/collection/collection.html`, по всем пяти пунктам тикета «Точки
интеграции» (01).

**Новые сателлиты** (после `claimSum`, рядом с проекцией §9): `CLAIM_KEYS`
(`principal|interest|overdueInterest|penalty|costs`), `CLAIM_LABELS` —
собственный набор МП5-18, не переименование `LEDGER_BUCKETS`. `claimsSnapshot(r,
scopeVolume, asOf)` — снимок пяти статей чистой алгеброй из уже посчитанного
`debtOf()` (не повторяет охват/дата-гейт второй раз): `overdueInterest =
min(interest.overdue, interest.claimable)`, `interest = interest.claimable −
overdueInterest`, `costs = d.claim − principal − penalty − interest.claimable`
(сворачивает `fees` + `costItems` в одну строку). `claimsEntryTotal(entry)` —
сумма непустых статей (пусто ≠ ноль).

**Требуемое** — `mClaimsWrap` в `openMeasureModal`, `renderMClaims(kind, r)`
(вызывается из `syncMeasureWarnings`, как `renderMScope`/`renderMBasedOn`):
таблица «цель × 5 статей» по кандидатам (r + `solidaryWith`), дефолт —
`claimsSnapshot` под охватом ПО УМОЛЧАНИЮ вида (`SCOPE_KIND_DEFAULT[kind]`,
факт вопроса 1 — форма всё равно не даёт целям разного охвата). `saveMeasure()`
читает `mClaim_<reqId>_<key>`, клэмпит `Math.min(Math.max(0,raw), cap)` против
`claimsSnapshot(x, живой mScopeVolume, дата события)` — потолок форсируется на
сохранении, не полагается на дисциплину ввода. `m.claims[reqId]` пишется на
каждую цель; `m.sum` — производная (дедуп по кредиту, тот же приём, что старый
`claimTotal`), проверено побитово: дефолтная регистрация даёт ТОЧНО то же число,
что старая формула `fmtKGS(claimTotal(targets))`.

**Присуждённое** — секция «Присуждено» в `openAnnotationModal` растёт с одного
`aAward_<reqId>` до пяти `aAward_<reqId>_<key>`. `saveAnnotation` — по строке
на статью: пустая статья наследует прежнее значение (или остаётся не
присуждённой), тронутая — перезаписывается; цель целиком пропускается, если НИ
ОДНА статья не тронута (сохраняет старый смысл «пусто ≠ ноль», растянутый на 5
строк). Сторно — по-прежнему по цели целиком (`m.stornoTargets`), построчного
не заводили (по вопросу 1 destination). `layerOf()` — `award.sum` заменено на
`claimsEntryTotal(award)` (сумма только присуждённых строк).

**Сверка «требовали → присудили»** — `claimChainsFor(r)` (новая, рядом с
`panelReq`): корень цепочки — живая мера с `m.claims[r.id]`, чей `basedOn` не
ссылается на другую claims-меру; обход потомков по `m.basedOn` (BFS), последний
по дате события `AWARD_KINDS`-акт с `m.awards[r.id]` — та же пара, что и
`layerOf`. Ветвящаяся цепочка (несколько исков на цель) — своя пара на каждый
живой корень (вопрос 3). `claimsReconcileHtml(r)` — отдельная таблица (НЕ
переиспользует `debtTableHtml`, вопрос 4), вставлена в `panelReq()` («Обзор»)
рядом с «Сумма требования»: по строке на статью — требовали / присудили /
расхождение, пустая ячейка «Присудили» — не присуждалась.

Проверено throwaway jsdom-смоуком (`_smoke-razbivka.mjs`, 20 проверок, удалён
после прогона): дефолтная регистрация без правок даёт то же `m.sum`, что старая
формула · накрутка сверх снимка клэмпится, обнуление проходит · пустая статья в
присуждённом не пишется, частичная правка одной статьи не стирает соседние ·
`layerOf().sum` считает только заполненные строки · `claimChainsFor` находит и
верно спаривает корень с решением по `basedOn` · `panelReq()` рендерит блок
сверки с заголовком МП5-18 без исключений. Отдельно — полный обход всех 100
живых требований затравки через `panelReq()`/`panelDebt()`/`panelMery()`:
0 исключений, 0 console/pageerror (старые SEED-меры без `m.claims` корректно
выпадают из сверки — не крашат, не участвуют, как и требовалось: «SEED
разбивки не заводится» вне карты).

Полный прогон `collection-check.mjs`/`collection-data-audit.mjs`/
`collection-seed-coverage.mjs` не запускался (резерв на конец пятой волны).

Destination карты достигнут: требуемое и присуждённое по пяти статьям заведены
на обеих сторонах формы регистрации меры, построчная сверка отображается в
«Обзоре» реестра требований. Карта закрыта.
