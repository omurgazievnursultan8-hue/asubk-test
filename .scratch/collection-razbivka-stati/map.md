# Карта: разбивка требуемого по статьям (наряд п.3, МП5-18)

## Destination

Пять статей (основная сумма · проценты · просроченные проценты · пеня · расходы,
§4 `ADR-0021`/`ADR-0046`) заведены в `mockups/collection/collection.html` на
**обеих** сторонах формы регистрации меры:

- **Требуемое** — `openMeasureModal`, по строке на цель (§4: «в разрезе цели, по
  строке на каждое затронутое требование»), 5 полей с дефолтом = снимок
  `debtOf(target, target-охват, дата документа)` (маппинг: «проценты» /
  «просроченные проценты» = расщепление `interest`/`interest.overdue`; «Сборы»
  (`fees`) вливается в «Расходы» — спека называет ровно 5 строк). Куратор только
  уменьшает/обнуляет — потолок = снимок, накрутить сверх нельзя (в отличие от
  присуждённого: наша заявка ограничена фактическим долгом, чужое решение суда —
  нет). Замораживается при сохранении (И-1), правится только сторно **по цели
  целиком** (не по статье — как сегодня `m.stornoTargets`). Хранится
  `m.claims[reqId] = {principal, interest, overdueInterest, penalty, costs}`.
  `m.sum` (плоская строка) остаётся производной суммой пяти строк, задедупленной
  по кредиту тем же `claimTotal`-приёмом — backward-compat для существующих
  читателей (список, плитки, TSV, «Акт сверки» gap).
- **Присуждённое** — `openAnnotationModal`, секция «Присуждено» (заведена прошлой
  картой «ключ слоя») получает те же 5 полей вместо одного `aAward_<reqId>`,
  пусто ≠ ноль **по строке** (суд мог присудить основную сумму, не присудить
  пеню). Без потолка. `relation` (новый слой / поглощает) — один на цель, не на
  статью (МП-8 про слой целиком). `m.awards[reqId] = {principal, interest,
  overdueInterest, penalty, costs, relation, by, at, reason?}`. `layerOf().sum` —
  сумма непустых строк, бейдж «Слой» в `panelDebt` визуально не меняется.
- **Построчная сверка** «требовали → присудили» (§4, часть самого МП5-18) — новый
  разворот «Обзор» в реестре требований, рядом с «Сумма требования».

Явно ВНЕ этой карты:
- Последствия МП-9 из §8.5 (роль статьи в очереди / норме распределения выручки,
  МП5-8 — три шага, три владельца) — отдельная будущая карта денежных агрегатов.
  Прошлая карта «ключ слоя» уже называла эту границу.

## Decisions so far

- [Точки интеграции (01)](issues/01-tochki-integracii.md) — охват на цели в форме
  сегодня один на меру, не по цели (факт, не меняем) · id-схема
  `mClaim_<reqId>_<key>`/`aAward_<reqId>_<key>` · сверка «требовали → присудили»
  по паре корень-цепочки (claims) / последняя-AWARD_KINDS-мера цепочки (awards),
  ветвление — отдельная строка на живой корень · сверка — отдельная таблица под
  `debtTableHtml`, не смешение с живым долгом · `m.sum` — производная сумма пяти
  `m.claims`, пересчитывается в `saveMeasure()`.
- [Реализация (02)](issues/02-realizaciya.md) — `CLAIM_KEYS`/`CLAIM_LABELS` +
  `claimsSnapshot`/`claimsEntryTotal` (алгебра из `debtOf`, не вторая свёртка) ·
  требуемое — `mClaimsWrap`/`renderMClaims` в `openMeasureModal`, клэмп в
  `saveMeasure()`, `m.claims[reqId]`, `m.sum` — производная (побитово совпадает
  со старой формулой на дефолтах) · присуждённое — `aAward_<reqId>_<key>` × 5 в
  `openAnnotationModal`/`saveAnnotation`, построчное «пусто ≠ ноль», сторно
  по-прежнему по цели целиком · `layerOf()` — `claimsEntryTotal(award)` вместо
  плоского `sum` · `claimChainsFor`/`claimsReconcileHtml` — новый блок в
  `panelReq()` («Обзор»), пара корень/последний-акт по цепочке `basedOn`.
  Проверено throwaway jsdom-смоуком (20 проверок) + полным обходом всех 100
  требований затравки (0 крашей, старые SEED-меры без `m.claims` из сверки
  корректно выпадают). **Destination карты достигнут — карта закрыта.**
