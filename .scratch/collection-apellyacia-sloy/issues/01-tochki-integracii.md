## Question

Пройти по одному вопросы, что destination (карта МП-2) оставил открытыми. Решались без
интерактивного `/grilling` (нет доступного второго голоса в этой сессии) — предложение и
обоснование фиксируются по тому же образцу, что и грилинг-тикеты прежних карт.

1. **Как правка присуждённого попадает в модель, не заводя апелляцию в `AWARD_KINDS`.**
   `AWARD_KINDS` (`:1642`) даёт трём типам отношения (`new`/`absorbs`/`adds`) и делает акт
   **источником** слоя (`layerOf` вернул бы `act: сама апелляция`) — ровно то, что design-doc
   отверг доводом №1 (ИЛ выдаётся по акту первой инстанции, апелляции в его `basisKinds` нет).
   Предложение: НЕ добавлять апелляцию в `AWARD_KINDS`. Завести четвёртый тип отношения
   `{type:'corrects', of:measureNum}` рядом с `new`/`absorbs`/`adds` — семантика «замена
   построчно», как `adds` (сложение), но без сложения. `layerOf` включает акт с этим типом
   отношения в свёртку ОТДЕЛЬНЫМ условием (не через `AWARD_KINDS.has`), а при выигрыше
   разрешает `act` не на саму апелляцию, а на `relation.of` — тот же базовый акт, что несёт
   исходное присуждение.

2. **Форма «Присуждено» — когда показывать для апелляции.** У `AWARD_KINDS`-видов секция
   показывается по виду, не по исходу (`:9076`, `AWARD_KINDS.has(m.kind)`), — исход
   `в иске отказано` тоже технически даёт доступ к полям, дисциплина на операторе. Апелляция
   не укладывается буквально: только исход `изменено` должен позволять правку, `оставлено в
   силе`/`отменено…` — нет (для `отменено` смерть слоя объявляется исходом, не суммой; для
   `оставлено в силе` слой не двигается вовсе). Предложение: секция видна ВСЕГДА для вида
   «Постановление апелляционной инстанции» (тот же приём, что остальные AWARD-виды — не
   гейтить по исходу в форме), но **relation-меню предлагает только `corrects`** — заполнение
   полей без установленного `corrects`-отношения не даёт `layerOf` ничего (нет валидного акта
   для правки), а `saveAnnotation` для этого вида требует relation обязательным (см. вопрос 3)
   — дисциплина по-прежнему на операторе, но неверный ввод не может создать новый слой (только
   не создать эффекта вовсе).

3. **`new` недоступен апелляции.** Апелляция никогда не заводит новый слой (design-doc, довод
   отвергнутого варианта). Предложение: `relField` для апелляции строит меню ТОЛЬКО из
   `corrects:NNN` по живым `AWARD_KINDS`-актам той же цели (тот же список кандидатов, что уже
   строит `priorActs`, `:9083`, — переиспользуется без изменений); опции `new`/`absorbs`/`adds`
   не рендерятся. Если кандидатов нет (базовое решение ещё не присудило по этой цели) — поле
   показывает предупреждающую пометку вместо формы сумм, `saveAnnotation` для этого вида
   игнорирует ввод без relation (тело будет пустым — `touched` не взводится).

4. **Смерть слоя от `отменено`.** `isAppealReversal` (`:1811`) уже опознаёт оба исхода
   `отменено`. Предложение: тот же приём, что «Определение об отмене судебного приказа»
   (`AWARD_DEATH_KINDS`, по `m.targets`, не `m.awards`) — `layerOf`/`claimChainsFor` включают
   апелляцию в свёртку по условию `isAppealReversal(m) && m.targets.includes(rep.id)`; при
   выигрыше — `null` (слой мёртв), без отдельного множества (`isAppealReversal` уже есть,
   заводить `AWARD_DEATH_KINDS`-дубликат незачем).

5. **`effectiveAward` — branch `corrects`.** Сегодня функция знает только `adds` (сложение
   построчно с актом-основанием). Предложение: добавить `else if(relation.type==='corrects')`
   — построчная ЗАМЕНА (тронутая статья апелляции побеждает, нетронутая наследует статью
   базового акта) — тот же цикл по `CLAIM_KEYS`, что и `adds`, другая арифметика на строку.
   «Пусто ≠ ноль» сохраняется на обоих уровнях (по строке апелляции И по строке базового акта).

6. **`layerOf` — режим начисления «по дате первого решения» (design-doc, дословно).** Слой уже
   хранит `act` (после правки вопроса 1 — базовый акт, не апелляция) — дата начисления читается
   ИЗ `act.dates`, что уже так во всех потребителях `layerOf().act` (нет отдельного поля «дата
   начисления» — она и есть дата акта). Правка вопроса 1 закрывает и этот пункт побочно:
   отдельного кода не требуется, только не сломать переносом `act` на апелляцию.

7. **Отображение — `layerTitle` (`:7562`).** Сегодня показывает `act.kind №… от …` + пометку
   `absorbs`/`adds`. С правкой вопроса 1 `act` — базовое решение, пометка `corrects` там не
   появится (у базового акта отношения `corrects` нет — оно у апелляции). Предложение: добавить
   в возврат `layerOf` поле `correctedBy` (сама мера-апелляция, когда выигрывающий акт —
   `corrects`), `layerTitle` добавляет хвост «· изменено определением апелляции №Z от W» —
   тот же паттерн, что уже есть для `absorbs`/`adds`, третья ветка тернарника.

8. **`claimChainsFor` (§4, `:7606`) — синхронизация со сверкой «требовали → присудили».**
   Сегодня фильтр `AWARD_KINDS.has(ch.kind) && ch.awards[r.id]` (`:7618`) не видит ни апелляцию,
   ни (уже существующий пробел, НЕ этой карты) отмену приказа. Предложение: добавить условие
   апелляции параллельно `layerOf` (вопрос 1+4) — `ch.kind===APPEAL_REVERSAL_KIND &&
   ch.outcome==='изменено' && ch.awards[r.id]` (правка) ИЛИ `isAppealReversal(ch) &&
   (ch.targets||[]).includes(r.id)` (смерть, `award=null` для этой цепочки). Пробел с отменой
   приказа в этой функции — НЕ трогать (вне карты МП-2, отдельная будущая находка, фиксируется
   в 02 как found-at-coding, не чинится).

9. **`ADR-0036` — третий случай правки пометки.** Design-doc уже называет его: «законный новый
   факт, у которого след ведёт на меру-основание, а не на человека». Предложение: правка
   присуждённого апелляцией НЕ трогает тело/пометки базового акта вовсе (нет `reason`, нет
   `wasSet`-предупреждения на базовом акте) — след живёт целиком на самой апелляции (её
   собственные `m.awards[reqId].by/at`). `ADR-0036` дописывается явным третьим случаем в
   таблице «послесобытийные пометки», отличным от «исправление ошибки» (тот остаётся про
   правку ОДНОЙ И ТОЙ ЖЕ меры человеком).

## Answer

Девять пунктов решены, без расхождений с предложениями:

1. **Четвёртый тип отношения `corrects:NNN`**, апелляция не входит в `AWARD_KINDS`. `layerOf`
   при выигрыше `corrects`-акта разрешает `act` на `relation.of`.
2. **Форма видна всегда** (гейт по виду «Постановление апелляционной инстанции»), дисциплина
   через закрытое relation-меню (вопрос 3), не через сокрытие формы по исходу.
3. **`new` не рендерится апелляции** — только `corrects:NNN` по кандидатам `priorActs`; нет
   кандидатов — предупреждение вместо формы.
4. **Смерть слоя** — `isAppealReversal` в той же свёртке, что `AWARD_DEATH_KINDS`, по
   `m.targets`; выигрыш → `null`.
5. **`effectiveAward` branch `corrects`** — построчная замена, «пусто ≠ ноль» на обоих уровнях.
6. **Дата начисления** — читается из `act` (после правки 1 — уже базовый акт), отдельного поля
   не требуется.
7. **`layerTitle`** — новое поле `correctedBy` в `layerOf`, третья ветка тернарника в заголовке.
8. **`claimChainsFor`** — параллельное условие апелляции; пробел с отменой приказа в этой
   функции НЕ чинится (вне карты, фиксируется как находка).
9. **`ADR-0036`** — третий случай пометки: след апелляции живёт на самой апелляции, тело
   базового акта не трогается.

Риск отдельно зафиксирован (`map.md` Notes): решения приняты без второго голоса — если модуль
уйдёт на дальнейший грилинг с ГФХ/архитектором, этот тикет — первый кандидат на повторную
сверку, а не готовый неприкасаемый результат.

Фронт тикета исчерпан — «Реализация» (02) разблокирована, кодит по девяти пунктам буквально.
