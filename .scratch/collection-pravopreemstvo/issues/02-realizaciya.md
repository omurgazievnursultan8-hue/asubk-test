## Answer

Реализовано по плану, без отклонений и без найденных регрессией дефектов.

**Поля требования.** `mkReq` несёт `continuesReq: null, liabilityLimit: null` по умолчанию.
`mkReqBranch(pred, obligorId, liabilityLimit)` строит требование-ветвь: наследует
`credit`/`_credit`/`subdivision`/`basis`/`contractRef` предшественника (та же претензия
продолжается, не открывается новая), `costs`/`states`/`handovers` — с нуля, `continuesReq`
на предшественника, свой `liabilityLimit`.

**Свёртка фазы.** `phaseOf`/`phaseSource` — при отсутствии своей меры-вехи и наличии
`continuesReq` рекурсивно свёртывают фазу/источник предшественника, до первой собственной
меры. Треки (`sudTrackOf`/`ispTrackOf`) не тронуты — уже читают только свои меры.

**Терминал условно.** `measureSetsTerminal` — спецкейс: «Определение о замене стороны
правопреемником» ставит терминал «Правопреемство», только если `m.successorCount > 1`.
N=1 требование не закрывает вовсе — линия продолжается тем же требованием.

**Follow-up модалка.** `saveAnnotation` детектирует первое выставление исхода «заменена» на
этом виде меры (`opensPravopreemstvo`) и вместо toast открывает `openPravopreemstvoModal(mi)`
(приём `recalcOnIzveschenie`). `renderPravRows()` — 1 либо N×2 полей (ФИО/наименование [+
предел ответственности при N>1]). `applyPravopreemstvo(mi)`: N=1 — заводит/находит лицо,
мутирует `r.obligor` на месте, лог в историю; N>1 — `m.successorCount=n`, n новых лиц,
n `mkReqBranch`, лог в историю, `curReq` переключается на первую ветвь (предшественник
закрывается терминалом автоматически, по обновлённому `measureSetsTerminal`).

**Свёртка дела и показ.** `successorNamesOf(p)` — по заёмщик-требованиям дела: обязанное
лицо ≠ `p.borrowerId` (N=1) либо несёт `continuesReq` (N>1-ветвь) → имя в список. Чип
«Правопреемник» на карточке дела (`panelDeal`, рядом с «Заёмщик»), показывается только
когда список непуст. Карточка требования (`panelReq`) — `ro('Продолжает требование', …)` +
`ro('Предел ответственности', …)`, только когда `r.continuesReq` задан.

**Поиск.** Код не тронут: `passFilters` уже матчит `personOf(r).name` — подтверждено
смоуком, что после мутации 583→«Кен-Тор» требование находится поиском по новому имени.

**Затравка.** Два новых минимальных K0-дела (583 «А», 584 «Б» со своим отдельным делом,
`ADR-0052` §1's главный иллюстративный сценарий) + точечный пост-`normalize()`-патч:
заёмщик-требование 583 мутировано на `PERSONS[584.borrowerId]`, симулируя уже свершившееся
N=1-правопреемство без прогона через UI (тот же приём минимальности, что K0-ОСНОВАНИЕ в
наряде п.6а). Оба дела остаются открытыми одновременно у «Кен-Тор».

**Смоук (throwaway, `.mjs`, удалён после прогона)** — 23 проверки, все зелёные (после
исправления бага теста, не приложения — см. «Ошибки и фиксы»): затравка строится
(96 дел) · 583/584 существуют и оба открыты · 583 мутирован на 584.borrowerId, `personOf`
и `successorNamesOf` это отражают, `p.borrower` дела 583 не меняется · `passFilters`
находит 583 по имени «Кен-Тор» · синтетический N=1 не закрывает требование и мутирует
`obligor` · синтетический N=3 закрывает предшественника терминалом «Правопреемство»,
создаёт ровно 3 `continuesReq`-ветви с разными `liabilityLimit`, наследующие
`basis`/`contractRef`, с `phaseOf`, совпадающим с предшественником, и переключает `curReq`
на первую ветвь · `panelDeal`/`panelReq` рендерятся без исключений на выборке · 0 ошибок
страницы. Полный `collection-check.mjs`/`collection-data-audit.mjs`/
`collection-seed-coverage.mjs` — в резерве на конец волны (наряд §30), не гонялся здесь.
