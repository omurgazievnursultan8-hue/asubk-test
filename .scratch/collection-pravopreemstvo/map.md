# Карта: правопреемство (наряд п.6б, МП5-6, МП5-15)

Вторая из пары карт наряда п.6 (`ASUBK-vzyskanie-logika.md` §30 :2243-2244). Первая —
[6а — основание требования](../collection-osnovanie-trebovaniya/map.md), независима по
обходу (словарь+переименование поля против разветвления+модалки), делит только слово
«правопреемство» в домене.

## Destination

**МП5-6 (`ADR-0052` §1, уточняет `ADR-0024`).** Дело якорится **линией заёмщика на дату
открытия** и правопреемством не мигрирует, не сливается, не расщепляется — инвариант «одно
открытое дело на линию» (не на лицо). Новая просрочка по перешедшему кредиту рождает
требование **в том деле, где кредит уже ведётся**; заголовок дела показывает исходного
заёмщика плюс чип «правопреемник — Б»; поиск/фильтры находят дело по обоим лицам.

**МП5-15 (`ADR-0052` §2).** Один правопреемник → линия требования получает новый отрезок,
ничего в модели не меняется (`ADR-0024` работает как написан). **Несколько** →
требование **разветвляется** на N требований: своя линия · свой предел ответственности ·
свой трек · связь «продолжает требование X» у каждой ветви; предшественник закрывается
терминалом «Правопреемство». Слой не разветвляется (один на кредит, `ADR-0049`, уже сделано
наряд п.2) — ветви делят слой, предел у каждой свой.

## Notes — реальный обход

- К5 «Правопреемство» контур уже целиком заведён: «Заявление об установлении
  правопреемника» (наш документ, `collection.html` :1519-1524) → либо «Решение суда
  (отсутствие правопреемника)» (внешний акт, закрывает отрицательно, :1525-1527), либо
  «Определение о замене стороны правопреемником» (внешний акт, :1536-1538).
- **Положительная ветвь УЖЕ вооружена терминалом.** `outcomes:[{value:'заменена',
  setsTerminal:'Правопреемство'}]` (:1537) — `measureSetsTerminal` (:1718-1722) уже читает
  эту пару, `TERMINAL_RANK['Правопреемство']=7` (:1184), `PERSON_STATE_CLOSE` уже
  размораживает лицо на этом виде (:2390). Комментарий на месте (:1528-1535) прямо называет,
  что заведено МИНИМАЛЬНО — «без реквизита „число преемников" и без разветвления требования
  (**наряд п.6, отдельная будущая карта**)» — однопреемниковый путь (линия продолжается,
  ничего не рвётся) уже полностью рабочий сегодня; эта карта достраивает РОВНО то, что
  комментарий явно отложил.
- **Линия (`ADR-0024`) как структура данных в коде не существует.** `r.obligor` — статичный
  id лица (`personOf = r => PERSONS[r.obligor]`, :5974), не датированный отрезок. Меры
  адресуются требованию (`measuresOf: m.targets.includes(r.id)`, :1695), НЕ лицу — подмена
  `r.obligor` на месте не переписывает адресата уже зарегистрированных мер. Пометки вручения
  (`m.sent`/`m.served`, :8418+) хранят дату/канал/документ, ФИО получателя не хранят и не
  рендерят нигде — опасение `ADR-0024` («вручали А, стало отображаться как вручали Б») в
  данных этого макета физически не воспроизводится. Вывод: одиночная замена безопасно
  реализуется мутацией `r.obligor` на месте, без generic-структуры «датированная линия» —
  обход подтверждает это эмпирически, не только по спеке.
- Разветвление (N>1) — генерический паттерн уже есть в файле: `recalcOnIzveschenie`
  (:8341-8364) — «после сохранения конкретного вида меры — отдельный follow-up шаг со своей
  модалкой», не зашитый в общий `saveMeasure`. Тот же приём годится для «Определение о
  замене стороны правопреемником» при реквизите «число преемников» > 1.
- «Предел ответственности» на ветви (`ADR-0052` п.2) — НЕ то же самое, что `scope`
  (`SCOPE_VOLUMES = ['просроченная сумма','полный остаток']`, :1807): потолок, специфичный
  самому правопреемству (наследственная масса / разделительный баланс), в модели такого
  поля нет вовсе — новый реквизит, не переиспользование.
- Поиск дела (`passFilters`, :6089-6092) матчит `p.borrower`/`p.inn`/`personOf(r).name`/
  `r._credit.num`/`procNo(p.id)` — исходного заёмщика по имени/ИНН; «правопреемник» как
  отдельная строка дела сегодня нигде не хранится и в поиск не участвует.
- Сценарий «кредит переходит другому юрлицу, у которого уже своё дело» (МП5-6, «дело не
  мигрирует») — отдельный, более редкий кейс от «наследники физлица разветвляют требование»
  (МП5-15) — общее у них только «линия», не сам сценарий; затравке нужен один пример на
  каждый, не один на двоих.
- Домен: `collection.html` — К5 контур целиком (:1519-1538), `personStateOf`/
  `PERSON_STATE_OPEN`/`PERSON_STATE_CLOSE` (:2383-2403), `phaseOf`/`liveMilestones`/
  `measuresOf` (:1695-1766), `passFilters` (:6060-6112), `recalcOnIzveschenie` (прецедент
  follow-up, :8341-8364). Спека: `ASUBK-vzyskanie-logika.md` §2.1-§2.3, §9 (МП5-6/15 строки
  :2170, :2179); `ADR-0052`, `ADR-0024`, `ADR-0053`.
- Основание требования у новых ветвей (`r.basis`) — читает словарь [карты 6а](../collection-osnovanie-trebovaniya/map.md); ветвь наследует основание предшественника или ставит своё — вопрос этой карты (см. ниже), но сам словарь заводится ТАМ.

## Decisions so far

- [Точки интеграции (01)](issues/01-tochki-integracii.md) — все пять решены.
  (1) число преемников — follow-up модалка после сохранения меры (приём
  `recalcOnIzveschenie`), хранится реквизитом меры в разрезе цели. (2) ветвь: `continuesReq` +
  `liabilityLimit` (свободный текст) + фаза-свёртка по предшественнику до первой своей меры;
  трек — только свой, не наследуется. (3) N=1 — мутация `r.obligor` на месте, без generic
  «датированной линии». (4) сценарий «юрлицо с уже открытым делом» — да, минимальный кейс в
  затравке. (5) чип «правопреемник — Б» — в периметре; поиск по «Б» уже работает бесплатно
  через `personOf(r).name` в `passFilters`, новый код не нужен.

- **Полная общая структура «датированная линия»** (`ADR-0024`, generic reusable сегменты) —
  если обход подтверждает, что сегодняшний рендер не наблюдает разницы между мутацией на
  месте и настоящим отрезком, генерическая структура не строится «на будущее» без
  называемого второго потребителя (тот же принцип, что уже применялся в наряде п.5б-ii к
  `CONTOURS`).
