# Карта: второй счётчик (наряд п.7в, МП5-11)

Третья и последняя карта наряда п.7 (после [7а — возврат ИЛ](../collection-vozvrat-il/map.md)
и [7б — давность](../collection-davnost/map.md), обе закрыты). Самая крупная по blast radius
из трёх — единственная, требующая настоящего синтетического графика взносов (новые кейсы),
не только чтения уже существующих полей.

## Destination

**`ADR-0051` §3 (МП5-11, два счётчика).** Один кредит рождает несколько судебных решений —
после решения по просроченной части график продолжает идти, новые взносы не платятся, и
сигнала об этом нет: счётчик дней просрочки давно горит красным и потому ничего не сообщает.

Решено — счётчиков два: (1) дней просрочки — как сейчас, от самого раннего неоплаченного
взноса; (2) дней **непредъявленной** просрочки — от самого раннего неоплаченного взноса,
**не покрытого** ни живым слоем, ни живым обращением в суд. Покрытие — по дате отсечения
ДОКУМЕНТА (решение/иск покрывают взносы со сроком платежа ДО своей даты), не по сумме
(частичное удовлетворение даёт меньшую сумму по тому же периоду — сравнение сумм неотличимо
от непредъявленного взноса). Вычитаются и живые слои, и живые обращения (иск подан, решения
ещё нет — просрочка уже предъявлена). Мёртвый слой (решение отменено, `ADR-0049` п.3)
покрытия не даёт — период возвращается в непредъявленные.

Видимость с 6-го дня — колонка реестра и чип на требовании. Обязательство рождается с
настраиваемого порога — умолчание 3 просроченных взноса либо 90 дней, что раньше (порог —
правило §14.4, не константа). Развилка при исполнении не одна (новый иск на новую просрочку
/ иск на весь остаток, поглощает прежний слой, `ADR-0046` п.2) — система её не выбирает.
Отвергнуто: автооткрытие нового требования на новую просрочку.

## Notes — реальный обход

- **Фундаментальное ограничение, уже подтверждённое дважды (карты 7а/7б).** Модуль кредита
  сегодня отдаёт ТОЛЬКО агрегат (`overdueDays`, счётчик) — ни одной даты отдельного взноса
  нигде нет. Даже свежий код давности (`davnostBaseOf`, наряд п.7б) читает тот же агрегат.
  Второй счётчик — единственный из трёх МП наряда п.7, которому агрегата принципиально
  недостаточно: нужно ЗНАТЬ несколько разных дат взносов, чтобы отличить «эти три покрыты
  иском, а эти два — нет» от «все пять непредъявлены». Card 7а's map (п.3, при заведении)
  уже это предвидела: «7в... нужен настоящий синтетический график из нескольких дат
  взноса (новые кейсы)».
- **Прецедент синтетического графика — только один, и он для другого.** `msSeedSchedule`
  (:4691-4700) строит равнопринципальные строки `{pay, principal}` с шагом в месяцах —
  но только для графика МИРОВОГО СОГЛАШЕНИЯ (settlement), не для графика самого кредита.
  Больше НИГДЕ в файле синтетического списка дат взносов нет — это единственный структурный
  ориентир, а не готовый переиспользуемый механизм (другая сущность, другие поля).
- **«Слой» (`layerOf`, :1799-1820) — точечная дата, не период.** Свёртка по `AWARD_KINDS`
  (Решение суда / Судебный приказ / Мировое соглашение) на кредит, тем же last-live-wins
  приёмом, что `phaseSetter`/`pauseOpenerOf`/только что заведённый `davnostBaseOf`. Отдаёт
  `{sum, relation, act, rep}` — `act.dates.event` ОДНА дата события, суммa есть, а поля
  «покрывает взносы до X» нет вовсе. `isLiveFor` (сторно-фильтр) уже даёт «мёртвый слой» —
  дополнительного признака заводить не нужно, мёртвая мера просто не попадёт в фолд.
- **Ни один вид меры не несёт периода/даты отсечения — только сумму.** `m.awards[reqId]` —
  пять денежных полей (`CLAIM_KEYS`) + `relation/by/at`, без периода. Простейшее прочтение
  ADR («покрытие считается по дате отсечения ДОКУМЕНТА») — переиспользовать уже существующую
  `m.dates.event` САМОГО документа как дату отсечения, не заводить новое поле.
- **Множественность живых покрывающих документов.** ADR сам говорит «один кредит рождает
  НЕСКОЛЬКО судебных решений» — то есть живых покрывающих документов на кредите может быть
  больше одного одновременно (иск без решения + более раннее решение по другому периоду).
  Файл нигде не считает объединение интервалов — везде один and тот же приём «последний
  побеждает» (`phaseSetter`/`pauseOpenerOf`/`layerOf`/`davnostBaseOf`). Взять MAX(дата
  отсечения) среди всех живых покрывающих документов требования — та же свёртка, тот же
  идиом файла, но это упрощение (не честный union периодов) — решать явно, не молча.
- **Порог обязательства — новый паттерн, готового не нашлось.** `PRECONDITIONS[kind].
  minLevel` (:2368+) — RULES-редактируемый, но `<select>` по дискретной лестнице уровней
  эскалации, не число дней/взносов. `catByDays`/`catOfCredit` (:1224-1261) — числовой порог
  дней С готовым чипом-паттерном («Норма/Средний/Высокий»), но захардкожен, НЕ
  RULES-редактируем. Ни один существующий кусок не даёт ОБА свойства разом (число + живое
  чтение из RULES/#settings) — придётся завести новую комбинацию, не переиспользовать
  готовое один в один.
- **Видимость «с 6-го дня»** — отдельного «покажи колонку начиная с N-го дня» гейта в файле
  нет; дело физически не существует раньше 6-го дня просрочки (Р-4) — вероятно, отдельный
  гейт не нужен вовсе (сам факт существования дела уже гарантирует ≥6 дней). Проверить на
  реализации, не предполагать заранее.
- **Домен:** `collection.html` — `layerOf`/`AWARD_KINDS`/`isLiveFor` (:1609, :1799-1820,
  :1711), `msSeedSchedule` (:4691-4700, ближайший прецедент синтетического графика),
  `overdueOf`/`overdueDays`/`buildCredit` (:2715-2716, :3260-3264), `catByDays`/`catOfCredit`
  (:1224-1261, чип-прецедент), `RULES`/`PRECONDITIONS.minLevel`/`renderSettingsPreconditions`
  (:2368+, :10236-10277, RULES-редактируемый прецедент), `ESCALATION_LEVEL` (:2315-2326).
  Спека: `ASUBK-vzyskanie-logika.md` §10 (МП5-11); `ADR-0051` §3, ссылается на
  `ADR-0046`, `ADR-0049`; `mockups/payments/ASUBK-platezhi-logika.md` §6 (несколько исков
  на один кредит — источник концепции, другой модуль, не потребитель этой карты).

## Decisions so far

[Точки интеграции (01)](issues/01-tochki-integracii.md) — закрыт, все шесть вопросов
решены рекомендованным вариантом. (1) минимальный список непогашенных взносов
`{due, amount}`, без истории оплат. (2) opt-in-only — новое поле графика только у новых
кейсов этой карты, счётчик 2 «не выведен» у остальных 94+. (3) дата отсечения = `m.dates.
event` покрывающего документа, нового поля на мере нет. (4) MAX(дата отсечения) среди
живых покрывающих документов на требовании — не union периодов. (5) порог обязательства —
новая RULES-редактируемая пара чисел (взносы/дни, 3/90 умолчание), чип-паттерн
(`catByDays`-style), не запись в `DEADLINE_TEMPLATES`. (6) видимость «с 6-го дня» —
отдельного гейта не заводим, покрывается фактом существования дела.

## Out of scope

- Настоящий график взносов ДОГОВОРА (дата выдачи, аннуитет/дифференцированный, реальный
  расчёт) — вне периметра всех трёх карт п.7 (решено ещё в карте 7а). Эта карта заводит
  МИНИМАЛЬНЫЙ синтетический список дат непогашенных взносов, не полную амортизацию.
  Ретрофит существующих 94+ кейсов новым полем графика — не входит (та же дисциплина
  opt-in-only, что `origin` в 7а и `debt.payments` изначально).
- Настоящий union периодов покрытия по нескольким живым документам сразу — упрощается до
  MAX(дата отсечения) (см. Notes), если карта не решит иначе.
- Слияние/поглощение слоя (`ADR-0046` п.2, «иск на весь остаток поглощает прежний») —
  `relation` уже размечается как факт/лейбл (наряд предыдущей волны), но вычислительно не
  сливает суммы; эта карта не добавляет вычислительное слияние — только чтение дат отсечения
  живых документов для второго счётчика, не пересчёт суммы слоя.
- **Полный прогон трёх проверок** (`collection-check.mjs`/`collection-data-audit.mjs`/
  `collection-seed-coverage.mjs`) — последний пункт наряда §30 целиком, после этой карты
  (последней в наряде п.7).
