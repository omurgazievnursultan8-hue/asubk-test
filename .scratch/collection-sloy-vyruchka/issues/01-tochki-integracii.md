## Question

Пройти по одному вопросы, что destination (карта МП5-8+МП5-10) оставил открытыми
(`/grilling`, рекомендация на каждый, ответ фиксируется здесь же):

1. **Где живёт факт реализации.** `p.realization`/`c.realStage` (:6172/:7501/:5991+)
   — модель v2, факт на ПРОЦЕССЕ. Предмет залога может обеспечивать несколько
   кредитов (§13) — факт на процессе не различает их. Предложение: перенести на
   ПРЕДМЕТ (`c.realization`), не на процесс.

2. **Очерёдность залогодержателей для делёжа между кредитами (ADR-0008).** Новую
   структуру ранга заводить, или переиспользовать существующее? В `zalog.html`
   (P13) ранг уже смоделирован (КП-9, сортировка по дате регистрации договора) —
   `collection.html` его не зеркалит. Варианты: (а) новое структурное поле ранга
   на кредите/зеркале; (б) вычислять из даты регистрации кредита (уже есть в
   `credit.num` как текст) без нового поля.

3. **Дата регистрации кредита — откуда брать.** `credit.num` (103 экз., без
   исключений) — паттерн `"Дог. №N от DD.MM.YYYY"`. Предложение: регексом из
   строки, не заводить отдельное структурное поле ради одного потребителя.

4. **Какая цифра долга кредита для делёжа (п. 49).** Варианты — `debtOf`
   разных охватов, либо завязка на слой. Предложение: `claimOf(rep,'полный
   остаток')`/`debtOf(...).totalLeft` — тот же rep-паттерн, что `layerOf`/
   `claimTotal`, без завязки на слой (свободный остаток и так авто-производный).

5. **`credit:null` (предмет обеспечивает ВСЁ дело) — как разворачивать в делёж
   между кредитами.** Предложение: раскрывать в полный список кредитов дела, тем
   же приёмом, что уже неявно делает `collsOf`.

6. **Доля кредита — публикуемая величина (ADR-0054, «своя дата и документ-
   основание», НЕ пересчитываемая, в отличие почти всего остального в коде,
   ADR-0001).** Варианты: (а) новый вид меры в журнале; (б) структурное поле на
   предмете, рядом с фактом шага 1. В коде нет ни одного вида меры под
   «распределение выручки» (`grep "распределени"` — только описательные
   комментарии и тост). Предложение: (б) — дешевле, не плодит вид меры ради
   денежной публикации без процессуального исхода/гейта/срока.

7. **Смерть слоя от отмены приказа (`layerOf`, ADR-0049 §3).** «Определение об
   отмене судебного приказа» (:1503) не несёт `m.awards` (`outcomes:[{value:
   'отменено'}]`), но `m.targets` есть у ЛЮБОЙ меры (:1737, universal).
   Предложение: включить акт отмены в ТОТ ЖЕ свёрточный `acts`-список `layerOf`
   (:1843-1846), что и `AWARD_KINDS`, тем же last-wins по дате, но вместо суммы —
   исход «слой мёртв»: если побеждает акт отмены — `layerOf` вернёт `null`.
   Условие входа — `isLiveFor(m,rep.id) && m.targets.includes(rep.id)` (не
   `m.awards`).

8. **Рост слоя от «Дополнительное решение суда» (ADR-0049 §3).** Секция
   «Присуждено» в форме показывается только для `AWARD_KINDS.has(m.kind)`
   (:8923) — у «Дополнительное решение суда» другое имя вида, форма присуждения
   для него сегодня не появляется. Предложение: (1) добавить его в `AWARD_KINDS`
   — форма присуждения и свёртка (уже расширенная п.7) подхватят сами; (2) третий
   тип отношения `{type:'adds', of:measureNum}` рядом с `new`/`absorbs`
   (:8932-8935) — `layerOf`, когда побеждающий акт `adds`, суммирует его награду
   с наградой акта-основания (`relation.of`, один уровень поиска по номеру меры,
   без рекурсии/цепочек).

9. **Какие расходы вычитает п. 49 первыми (шаг 2).** ADR-0054 прямым текстом
   (стр. 29-30): «Расходы, которые п. 49 ставит первыми, — наша пятая статья
   (§8.2), и владеет ею тоже взыскание.» — значит это существующий `r.costs[]`
   (COST_KINDS, :8211-8246), а НЕ «расходы реализации (оценка, торги,
   публикация)» из шага 1 P13 (те чисто зеркало/информационные, в делёж не идут).
   Предложение: `c.realization` (шаг1, зеркало) несёт `{proceeds, costs (P13,
   инфо), date}` отдельным полем от делёжа; делёж (шаг2) использует `r.costs[]`
   по кредиту (уже включён в `debtOf(...).claim/totalLeft`, см. правку п.14 ниже
   — двойного поля не заводим).

10. **Сборка алгоритма шага 2 — синтез п.2/4/5/9.** Очередь по приоритету
    (ADR-0008), по каждому кредиту очереди — забрать из остатка пота
    `need = claimOf(rep(кредит),'полный остаток')` (расходы уже внутри, см.
    правку п.14), пока пот не кончится; после очереди — остаток → залогодателю.
    Псевдокод:
    ```
    let pot = c.realization.proceeds;
    const perCredit = [];
    for (const credit of creditorsByPriority) {           // ADR-0008 приоритет
      const need = claimOf(rep(credit), 'полный остаток'); // расходы уже внутри (п.14)
      const take = Math.min(pot, need);
      perCredit.push({ credit, amount: take });
      pot -= take;
      if (pot <= 0) break;
    }
    const giveBack = pot;                                   // остаток → залогодателю
    ```

11. **UI — где кнопка «распределить», где виден результат.** `markRealized(ci)`
    (:8200) сегодня — конец модалки, пишет `proceeds`, закрывает. Тайл «Слой» в
    `panelDebt` (:6733, соседняя карта) — прецедент показа денежного факта рядом
    с суммой требования. Предложение: не отдельная кнопка/модалка — тот же шаг
    `markRealized`; после ввода `proceeds` модалка не закрывается, показывает
    предпросчитанный делёж (алгоритм п.10) построчно по кредиту + возврат
    залогодателю, поле «Документ-основание» (текст), допускает ручную правку
    цифр перед публикацией (реальный документ может разойтись с формулой);
    кнопка «Опубликовать» пишет `c.realization.distribution` как есть (не
    пересчитывается впредь). Отображение — строка «Доля в реализации: X (акт от
    Y)» в `panelDebt` рядом со «Слой»; таблица делёжа в `panelZalog` под
    реализованным предметом.

12. **После публикации — `debtOf` уменьшается сразу, или ждём как обычный
    платёж?** ADR-0054 прямо: «Взыскание по ней ничего не начисляет и ничего не
    гасит» (стр.51) — гашение ведут платежи (шаг3). Предложение: нет, `debtOf`
    публикацией не трогается — доля видна только тайлом (п.11), долг на экране
    отстаёт до момента, пока платежи (другой модуль) не проведут её как обычное
    поступление — тот же паттерн, что уже принят для зеркала обеспечения
    (`c.snapshotAt`).

13. **Согласованность суммы последнего акта — `layerOf` vs `claimChainsFor`.**
    `claimChainsFor` (:7531, §4/МП5-18, наряд п.3, уже закрыт) тоже фильтрует
    `AWARD_KINDS.has(ch.kind)` на последний акт цепочки и берёт его сумму КАК
    ЕСТЬ, без сложения — с добавлением «Дополнительное решение суда» в
    `AWARD_KINDS` (п.8) это расходится с новой аддитивной семантикой слоя.
    Предложение: вынести общий хелпер (сумма акта с учётом `relation.type===
    'adds'`, один уровень поиска по `of`), использовать в обоих местах —
    `layerOf` и `claimChainsFor`. Остальную логику §4/наряд п.3 не трогать.

14. **Правка арифметики п.10 (найдена при повторной проверке `debtOf`).**
    `debtOf(r,'полный остаток').claim` уже включает `r.costs[]`
    (`costsClaimable`, :2691) — «пятая статья» уже внутри. Псевдокод п.10 в
    первой версии считал расходы дважды (`costsOf(credit) + debtOf(...)`).
    Исправлено на `need = claimOf(rep(credit),'полный остаток')` без отдельного
    слагаемого расходов — представитель несёт свои расходы сам, тем же
    приёмом, что `claimTotal` уже берёт ровно одну строку на кредит.

15. **«Возврат залогодателю» — адресат.** В коде нет структурного поля
    «залогодатель»/pledgor — предмет несёт только `credit`(-ы), не личность
    заложившего. Предложение: сумма `giveBack` — из алгоритма (автоматом),
    адресат — свободный текст в той же форме публикации (рядом с «Документ-
    основание», п.11); структурную личность не заводим (не заводить до второго
    потребителя, P13 её тоже не несёт).

Факт без вопроса: «Определение о повороте исполнения» (:1503, `outcomes:null`)
кода сверх словарной записи не требует — та же форма, что уже рабочее
«Определение суда (прочее)», наряд п.1 закрыл. Подтверждает гипотезу destination,
отдельного решения не было.

## Answer

Все пятнадцать пунктов решены (`/grilling`, по одному, все рекомендации приняты
без правок, кроме арифметической самокоррекции п.14):

1. **Факт реализации → предмет.** `p.realization` → `c.realization` (шаг1,
   зеркало P13: `{proceeds, costs, date}`).
2. **Очерёдность делёжа между кредитами.** Вариант (б) — без нового поля ранга.
3. **Дата регистрации кредита.** Регекс из `credit.num`, отдельного поля нет.
4. **Долг кредита для делёжа.** `claimOf(rep(credit),'полный остаток')`, без
   завязки на слой.
5. **`credit:null` → раскрыть в полный список кредитов дела.**
6. **Доля кредита — публикация.** Структурное поле на предмете (вариант б), не
   новый вид меры.
7. **Смерть слоя (отмена приказа).** В свёртку `layerOf` тем же last-wins по
   дате; побеждающий акт отмены → `layerOf` возвращает `null`. Условие —
   `m.targets`, не `m.awards`.
8. **Рост слоя (доп. решение).** «Дополнительное решение суда» → `AWARD_KINDS`;
   третий тип отношения `{type:'adds', of:measureNum}`, сумма — своя + сумма
   акта-основания, один уровень.
9. **Расходы шага 2.** Существующий `r.costs[]` (наша пятая статья), НЕ
   информационные «расходы реализации» шага 1 P13.
10. **Алгоритм шага 2.** Очередь по приоритету (п.2/3), на каждом шаге
    забрать `need = claimOf(rep,'полный остаток')` из пота, остаток —
    залогодателю. (См. правку п.14 — расходы не дублируются.)
11. **UI.** Расширение модалки `markRealized` — предпросчитанный делёж +
    документ-основание, ручная правка перед публикацией; отображение — тайл в
    `panelDebt`, таблица в `panelZalog`.
12. **`debtOf` публикацией не трогается** — лаг до проведения платежами, тот же
    паттерн, что зеркало обеспечения.
13. **`layerOf`/`claimChainsFor` — общий хелпер** суммы акта с учётом `adds`.
14. **Арифметика п.10 исправлена** — `claimOf` уже несёт расходы, второе
    слагаемое убрано.
15. **Адресат возврата — свободный текст**, структурную личность залогодателя не
    заводим.

Факт без решения: «Определение о повороте исполнения» — кода сверх словарной
записи не требуется (наряд п.1 уже закрыл).

Фронт тикета исчерпан — «Реализация» (02) разблокирована, кодит по пятнадцати
пунктам буквально.
