# Единица работы взыскания — требование, а не дело заёмщика

**Статус:** принято · 2026-07-26 · модуль «Взыскание задолженности»

Модуль взыскания сначала был спроектирован вокруг **процесса** — одного дела на заёмщика
с одной фазой, одним охватом и вложенным списком кредитов. Модель не выдержала обычного
сценария: у заёмщика два договора, по одному подан иск, по другому только первичная
претензия. Одна фаза на дело это не выражает.

Решено: рабочая единица — **требование** = процесс × кредит × обязанное лицо. Процесс
остаётся папкой дела (кураторство, организационная процедура, вопросы на коллегиальные
органы, история), но фаза, охват, ведущее подразделение, сроки и терминальный исход
живут на требовании.

## Считаные альтернативы

**Процесс = заёмщик × охват.** Отвергнут: при ускорении долга (п. 20.4) охват меняется,
и кредит пришлось бы мигрировать между процессами.

**Процесс = кредит.** Отвергнут: один иск на трёх договорах превратился бы в три
процесса, судебная работа задваивается.

**Отдельный процесс на поручителя** (у него свой ИНН). Отвергнут: один и тот же долг
попал бы в два процесса, и любой агрегат по списку — сумма требований, плитки,
отчётность — задваивался бы. Вместо этого обязанное лицо стало третьей координатой
требования; сумма считается один раз по кредиту.

## Последствия

- Одна мера-веха может быть вехой сразу для нескольких требований (иск ко всем
  ответчикам, п. 32) — связь мера↔требование многие-ко-многим.
- Гейт последовательности вех считается на требовании, не на процессе.
- Главный список стал списком требований: иначе покредитные колонки (фаза, охват,
  категория, дни просрочки) пришлось бы сворачивать в worst-of, а именно на этом уже
  возникли дефекты Д-1/Д-2.
- Гейт `crossingOnCourt` («два иска по одному кредиту») переосмыслен: теперь это
  проверка внутри дела, а не между делами.
- Legacy это уже так и работал: главный рабочий список там был по фазам
  (`/collectionPhaseViews`), а не по должникам.
