# Реструктуризация делит транш, а перенос — датированная операция

**Статус:** принято · 2026-08-05 · модуль «Реструктуризация» · частный случай
[ADR-0001](./0001-proizvodnye-ne-hranyatsya.md) · соседствует с
[ADR-0060](./0060-transh-schet-oblast-ochered.md) · дополняет `CONTEXT.md` («Транш»,
«Освоение») и спеку `mockups/loan-credit/ASUBK-kredit-logika.md`

Старая система вела реструктуризацию **субкредитами**: часть договора, которая не меняется,
вносилась первым субкредитом, новый график — вторым, а кредит показывал сумму
(`requirements/legacy/02-loans.md:91`). В новой системе отдельного субкредита нет — `SubLoan`
это и есть транш (`requirements/tz/06-transhi-osvoenie.md:33`). Остаётся вопрос, который
надо решить прямо: где живёт часть долга, ушедшая на новые условия, если другая часть
осталась на прежних.

## 1. Транш рождается двумя способами

Освоением — либо **разделением по допсоглашению**. Производный транш несёт перенесённую
базу, дату начала, равную дате вступления ДС, свой график и свои записи условий; исходный
транш продолжает жить по старым условиям с остатком, уменьшенным на перенесённое.

Причина в том, где живут условия: комплект условий и график принадлежат траншу, а не
кредиту (`CONTEXT.md`). Один транш не может нести два комплекта условий, действующих
одновременно, — записи условий датированы, и «с 01.09 ставка 4%» относится ко всему траншу
целиком.

## 2. Перенос — операция, а не правка суммы

```
остаток тела транша = освоено − погашено − перенесено + принято
```

Перенос датирован, имеет основание (ДС) и две стороны (из транша → в транш). Правка суммы
транша на месте запрещена: она сдвинула бы каждый расчёт, сделанный до реструктуризации, и
лишила бы систему возможности показать долг на дату, предшествующую ДС, — а показывать его
она обязана, и после нескольких реструктуризаций тоже.

«Принято» — вторая половина той же операции и нужна не только при делении: капитализация
растит тело транша, не будучи освоением.

## 3. Опустошённый транш закрывается переносом, а не погашением

Если ДС забрал весь остаток, исходный транш заканчивается с нулём — но денег не приходило.
Оформить это погашением значит соврать денежными показателями ровно так же, как оформление
списания платежом ([ADR-0076](./0076-spisanie-umenshaet-nachislennoe.md)): в отчёт «собрано
за месяц» попадёт сумма, которой не было.

## 4. Делим только при расхождении условий

Если весь остаток идёт на новые условия, деления нет: пишутся записи условий и новая версия
графика на существующем транше. Производный транш появляется тогда и только тогда, когда
после ДС по кредиту одновременно действуют два разных комплекта условий.

## Отвергнуто

- **Кредит-обёртка над субкредитами** (форма старой системы) — договор из допсоглашения не
  рождается: у кредита есть свой номер, своя дата и стороны, а ДС меняет уже существующий
  договор. Обёртка потребовала бы придумывать реквизиты договора, которого не заключали.
- **Правка суммы и графика транша на месте** — см. §2: убивает расчёт на прошлую дату,
  который и есть главное требование к модели.
- **Новый кредит на реструктурированную часть** — пришлось бы переносить обеспечение,
  требования и историю; норма же считает реструктуризацию изменением условий, а не выдачей.
- **Отдельный транш под капитализированные суммы** — своих условий у них нет, а состав базы
  виден разбивкой.

## Последствия

- Инвариант И-3 модуля кредита («Σ освоений транша ≤ суммы транша»,
  `ASUBK-kredit-logika.md:343`) к производному траншу неприменим: освоений у него нет.
  Переформулируется: сумма производного транша равна сумме переноса.
- Отчёты об освоении производный транш выдачей не считают — иначе объём выдачи вырастет на
  величину реструктуризаций.
- [ADR-0060](./0060-transh-schet-oblast-ochered.md) уже разносит платёж по всем траншам
  кредита по дате наступления — отдельной двери для деления не нужно.
- Счётчик реструктуризаций кредита считает **допсоглашения**, а не траншы: один ДС,
  поделивший три транша, — одна реструктуризация.
