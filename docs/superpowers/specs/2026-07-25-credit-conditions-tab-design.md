# Вкладка «Условия» карточки кредита — версионность условий

Дата: 2026-07-25
Файл-цель: `mockups/loan-credit/credit.html`, функция `tabUsloviya`
Канон: `/home/azamat/Downloads/prompt-kredit-mockup.md` (решения Р-1…Р-20, гейты Г-1…Г-17)

## 1. Задача

Условия кредита не статичны:

- приходят из **заявки** при создании кредита;
- меняются **доп. соглашением**;
- меняются **решением суда** и **постановлением правительства** — без согласия сторон;
- условий много, **у каждого своя дата вступления в силу**;
- по каждому **траншу** условия могут различаться.

Текущая вкладка этого не показывает. Дыры:

1. Дат вступления в силу нет — у ДС только дата подписания (`c.agreements[].date`).
   Ответить «какие условия действовали на 01.05.2026» нельзя.
2. Суд и ПП не являются источниками изменения условий: `source` — свободная строка
   (в демо `'реструктуризация'`), судебные решения лежат зеркалом `mirror.court`
   во вкладке «Проблемные», ПП — только в блоке «Происхождение» (Р-18).
3. Транш не версионируется: «дифф траншей» — плоский снимок «база → транш» на сейчас.
4. Условия из заявки не оформлены как первичная версия — базовый комплект просто
   лежит полями `c.baseConditions` без провенанса.

## 2. Принятые решения

| № | Решение |
|---|---|
| Д-1 | Переделывается вкладка **кредита** (`loan-credit/credit.html`). Вкладка «Условия кредита» заявки (`loan-application.html`, 3-слойный дифф программа→заёмщик→комиссия) не трогается. |
| Д-2 | Версионируется **каждое условие отдельно** (запись на параметр со своей датой вступления), а не комплект-changeset. В UI основной вид истории — всё равно «документ → что изменил» (группировка записей по документу) + срез на дату. |
| Д-3 | Записи живут **только на транше**. `baseConditions` кредита = шаблон наследования при создании транша, на действующие условия не влияет. Тот же приём, что Р-13 для срока. Правила «уровень бьёт дату» нет — ось одна. |
| Д-4 | Решение суда и ПП — **не заводятся в кредите**, запись условия ссылается на существующий документ (`basis.ref`). Паттерн Р-7/Р-16 («из кредита не заводятся»). ДС кредит по-прежнему владеет. |
| Д-5 | Ретроспективное изменение **не пересчитывается автоматически**: плашка «требуется перегенерация графика» + переход в «Расчёты». Движка сторнирования в макете нет и не появляется. |
| Д-6 | Раскладка: «действует сейчас» первым экраном, история ниже, срез на дату — контролом. Сводная матрица параметр × дата — свёрнутым блоком (объясняет модель дев-команде). |
| Д-7 | При выборе «по кредиту» карточки показывают **агрегат с маркером расхождения** по траншам (Р-13-подобно), а не шаблон. |

Новое решение канона: **Р-21 — условия суть записи на параметр, лежащие на транше
(`param · value · effectiveFrom · basis`); действующий комплект и любой исторический
срез — производные (Р-11), не хранятся.**

## 3. Модель данных

### 3.1 Новая сущность

Записи хранятся **на транше** (`t.conditionRecords`), не на кредите. Причина:
при Д-3 `scope` всегда равен `tranche.id` — поле избыточно; плюс `buildSchedule(tranche,
fromDate)` не получает ссылку на кредит (тот же случай, из-за которого `accrualHold`
зеркалится на каждый транш), а условия ему нужны. Кредит-уровневые виды (журнал,
агрегат, ретро-флаги) собираются через `c.tranches.flatMap(t => t.conditionRecords)`.

```js
t.conditionRecords = [{
  id:'CR-1',
  param:'rate',                    // ключ из PARAMS
  value:7,
  effectiveFrom:'01.05.2026',      // дата вступления в силу — НЕ дата документа
  basis:{ kind:'court',            // 'application' | 'agreement' | 'court' | 'govAct'
          ref:'COURT-2026-118',
          label:'Решение АС г. Бишкек № АД-118 от 20.04.2026',
          date:'20.04.2026' },
  note:'Пеня списана судом с начала года',
  createdAt:'12.07.2026',
  createdBy:'Кредитный специалист'
}]
```

Формат дат — `DD.MM.YYYY`, как во всём макете (`TODAY = '23.07.2026'`).

### 3.2 Реестр параметров

`PARAMS` — справочник условий-параметров (label, тип, единица, форматтер):

`rate · reserveRate · penaltyMain · penaltyInt · term · payDay · lastPaymentAnchor ·
freq · payMonths · method · graceMain · graceInterest · graceIntDistFrom ·
graceIntDistTo · graceAccrual · dayMethod`

`queue` в реестр **не входит** — параметр расчётного движка, живёт в «Расчётах»
(шаг 14), судом и ПП не меняется. `penaltyMaxPct` не входит — поле мёртвое (cap
в расчёте пени не применяется, шаг 4).

> **Поправка 11.08.2026.** Исходная редакция этого абзаца называла десять параметров и
> выносила `dayMethod` в расчётный движок вместе с `queue`. Поставленный код держит
> шестнадцать, включая `dayMethod` (`credit.html:1744–1767`), и прав он: база дней —
> контрактный термин, он записан в договоре и влияет на начисление, а очередь погашения
> действительно движковая. Реестр приведён к коду; `dayMethod` отнесён к зоне «вне п. 89» и
> меняется прямым ДС вида «прочее изменение условий»
> ([ADR-0111](../../adr/0111-vid-ds-razvodit-marshruty-izmeneniya-usloviy.md)). Туда же
> добавляются `earlyRepayMoratorium` и `earlyRepayFee` — условия транша по
> [ADR-0074](../../adr/0074-dosrochka-grafik-po-zayavleniyu.md), в реестре пока
> отсутствующие.

### 3.3 Изменения существующей модели

| Было | Стало |
|---|---|
| `c.baseConditions` — «условия кредита» | шаблон наследования: копируется в записи при создании транша; в UI — свёрнутый блок «Шаблон наследования» |
| `t.conditions` — хранимый объект | **удаляется**; производное `conditionsAt(t, date)`. Переводятся 5 мест чтения: `credit.html:1525, 1747, 1796, 2820, 3292` |
| `c.agreements[].before/after` | **удаляются**; ДС становится одним из `basis`, «что изменил» — производное (группировка записей по `basis.ref`) |
| `c.agreements[]` как носитель истории | остаётся реестром документов-ДС (номер, дата, скан); истина по значениям — `conditionRecords` |
| условия из заявки — просто поля | первичные записи: `basis.kind='application'`, `ref` = № протокола комиссии, `effectiveFrom` = дата регистрации кредита |
| `mirror.court`, `c.origin` (ПП) | не меняются, служат источником `basis.ref` для пикера |

### 3.4 Производные (Р-11, рантайм)

- `conditionsAt(tranche, date)` → комплект: по каждому параметру последняя запись
  `t.conditionRecords` с `effectiveFrom <= date`; при равных `effectiveFrom` —
  позже созданная (`createdAt`, затем `id`).
- `creditConditionsAt(credit, date)` → агрегат по активным траншам:
  `{value}` если все согласны, иначе `{divergent:true, values:[{trancheNo, value}]}` (Д-7).
- `retroFlags(credit)` → записи с `effectiveFrom < createdAt`; питает красную плашку (Д-5).
- `basisGroups(credit)` → журнал: записи, сгруппированные по `basis.ref`,
  сортировка по `effectiveFrom` desc.
- `divergenceRows(credit, date)` → строки таблицы расхождений: параметр × транш,
  только параметры с различающимися значениями.

## 4. Действия и гейты

Действие «Оформить доп. соглашение» заменяется на **«Изменить условия»** —
конструктор записи или пачки записей за один документ.

Форма:

1. **Основание** — тип, дальше ветвится:
   - ДС: № + дата + скан вводятся здесь (кредит владеет документом);
   - суд: пикер «Привязать решение» из `mirror.court`, ввода реквизитов нет (Д-4);
   - ПП: пикер из `c.origin` / модуля решений, только выбор.
2. **Дата вступления в силу** — одна на пачку по умолчанию, переопределяется
   у отдельного параметра (это и есть Д-2).
3. **Транши** — чекбоксы, по умолчанию все активные. N траншей × M параметров =
   N×M записей за одно действие.
4. **Параметры** — чекбокс + новое значение, рядом действующее («было → станет»)
   до сохранения.

### Гейты

| гейт | правило |
|---|---|
| **Г-9** (правится) | Прямая правка шаблона — только ЖЦ «Проект». После регистрации — только запись с основанием. Формулировка «только доп. соглашением» **исправляется** на «только зарегистрированным основанием (ДС · суд · ПП)» — прежняя противоречит Д-4. |
| **Г-10** (расширяется) | Реквизиты обязательны по типу: ДС — номер + дата; суд/ПП — непустой `basis.ref` на существующий документ. |
| **Г-18** (новый) | `effectiveFrom` не раньше даты регистрации кредита. |
| **Г-19** (новый) | `effectiveFrom < TODAY` (ретроспектива) допустима только для `kind ∈ {court, govAct}`; для ДС — запрет (сделка сторон задним числом не подписывается). |
| **Г-20** (новый) | Ретроспективная запись требует непустой `note`. |
| **Г-21** (новый) | Записи не удаляются. Отмена = новая запись с прежним значением и своим основанием (как Р-20, без физического delete). |

Роли не меняются: ключи `addAgreement` / `editConditions` в `ROLE_ACTS` остаются,
`Наблюдатель` — read-only.

Аудит: каждая запись → `pushAudit(credit, 'conditionRecord', null, record)`.

## 6. Демо-данные

- Все 59 кредитов: `baseConditions` → первичные записи `basis.kind='application'`,
  `effectiveFrom` = `c.date` (дата договора), записи по каждому активному траншу.
- `K-4`: существующий `ДС-РС-1004` (`rate 9→7`, `term 36→48`) → 2 записи
  (2 параметра × 1 транш `K-4-T1`), `effectiveFrom='01.05.2026'`, `kind='agreement'`.
- `K-3` (есть `mirror.court`): ретро-запись `penaltyMain → 0`, `effectiveFrom`
  в прошлом, `kind='court'`, `ref` на существующее решение — единственный кредит,
  демонстрирующий красную плашку Д-5 и гейты Г-19/Г-20.
- `K-2`: `reserveRate` меняется, `kind='govAct'`, `ref` на ПП из `c.origin` (Р-18).
- Расхождение по траншам — на двухтраншевом кредите: `K-1` (`K-1-T1`/`K-1-T2`)
  либо ближайший `K-C*` со `tr2:true` (сценарий «Кемин-Агро»). Запись `method`
  только на транш №2 отдельным ДС → демонстрирует `⚠ расх.` и таблицу расхождений.
  Предпочтителен `K-C*`: `K-1…K-6b` под смоуком, лишних правок на них лучше не делать.
- Остальные `K-C*` не трогаются: только первичный комплект.

## 7. Проверка

`node scripts/inspect/credit-check.mjs` — существующие 32 проверки должны остаться
зелёными (переезд `t.conditions` → `conditionsAt` не должен менять цифры графика
и агрегата срока). Добавляются:

1. `conditionsAt(t, TODAY)` для каждого транша каждого кредита = прежний
   `t.conditions` на сид-данных (регрессия переезда).
2. `conditionsAt(t, дата до первой записи)` → пусто, без ошибки.
3. `termAgg` считается из `conditionsAt`, значение не изменилось.
4. Г-18: запись с `effectiveFrom` раньше даты договора отбивается.
5. Г-19: ретро-ДС отбивается, ретро-суд проходит.
6. Г-20: ретро-запись без `note` отбивается.
7. `creditConditionsAt` даёт `divergent:true` ровно на кредите с расхождением.
8. `retroFlags` непусто ровно на `K-3`.

## 8. Не делается

- Автоматический пересчёт графика и леджера при ретро-изменении (Д-5).
  Сторно-строк в леджере нет.
- Матрица очередей погашения при судебном решении — остаётся открытым вопросом
  канона №4 (плита-предупреждение, без реализации).
- Вкладка «Условия кредита» заявки не меняется (Д-1).
- `queue` не переводится в записи — остаётся полем в «Расчётах». (`dayMethod` из этой
  строки убран поправкой 11.08.2026 — см. §3.2: он в реестре и в коде.)
- Перевод долга Р-14 не переводится в `conditionRecords`: он меняет субъекта,
  а не параметр условия.

## 9. Открытые вопросы

1. **Приоритет источников.** Если ПП и ДС задают разные значения одного параметра
   с одной датой вступления — по спеке побеждает позже созданная запись.
   Юридически, вероятно, ПП/суд должны бить ДС независимо от порядка ввода.
   Макет: побеждает позже созданная, помечено как допущение.
2. **Условие на новый транш, созданный после ретро-изменения.** Наследует шаблон
   или действующий комплект соседних траншей? Макет: шаблон.
3. **Скан основания для суда/ПП** — файл живёт в модуле-владельце документа;
   нужна ли копия в «Досье» кредита. Макет: только ссылка.
