# Реструктуризация: суммы получают адрес — расчёт живёт на транше

Дата: 11.08.2026 · Мокап: `mockups/restructuring/restructuring.html` · Спека модуля:
`mockups/restructuring/ASUBK-restrukturizatsiya-logika.md` · Область правки: финансовое
ядро заявки (охват, база, распоряжения, версия условий, ДС) и вкладка «Расчёт». Виды,
маршрут стадий, заключения, пакет документов, взыскание и залог — не трогаем.

## Задача

Спека уже обещает многокредитную заявку: охват называет **траншы**, заявка вправе
охватывать траншы нескольких кредитов одного субъекта, и «одна заявка по двум кредитам
даёт **два допсоглашения**» (РС-2, `ASUBK-restrukturizatsiya-logika.md:66–76`). Макет
охват держит: `app.creditIds[]` заполняется, кредит добавляется вручную
(`addCredit`), гейт покрытия и гейт согласий уже ходят по всем кредитам охвата
(`coverGateApp`, `consentGate` — `rows = creditIds.map(...)`), признак «повторная»
считается по каждому кредиту.

**Финансовое ядро при этом однокредитное и одинтраншевое:**

| Что | Сегодня | Следствие при 2+ кредитах |
|---|---|---|
| транш под расчёт | `app.calcTranche` — **один** | второй кредит в расчёт не входит вовсе |
| база | `app.base` — плоский список | ключ строки — пара `(статья, срочность)`, адреса нет |
| распоряжения | `app.dispositions` | `dispositionFor(d, article, urgency)` — тот же ключ |
| параметры условий | `app.version` — один | срок и ставка одни на все кредиты охвата |
| допсоглашение | `app.ds` — одно | два ДС спеки негде хранить |
| шесть мест рендера | `creditIds[0]` | `restructuring.html:1284, 1571, 2455, 2510, 2640, 2809` |

Отсюда исходный вопрос: **при двух и более кредитах по какому кредиту какая сумма —
неразличимо.** Не потому что механизм сломан, а потому что оси нет: сумма не имеет
адреса.

Норма давит в ту же сторону и по параметрам, а не только по суммам: пол ставки считается
от первоначальной ставки **кредита** (п. 34 и п. 92, РС-35), предел длины графика — от
остатка задолженности **по кредиту** (п. 90, РС-37). Один `app.version` на заявку эти два
гейта делает непроверяемыми, как только кредитов больше одного.

## Решение

### 1. Единица расчёта — транш; заявка держит их список

```
app = {
  id, subjectKey, inn, borrower,
  kindIds[],           // виды — на заявке, объединение разрешённого (§3)
  scope: [trancheId],  // охват — траншы (РС-2)
  cutoffDate,          // дата среза — одна на заявку
  calcs: [Calc],       // ровно один расчёт на транш охвата (ИР-16)
  acts[]               // журнал актов; стадия — свёртка, поля stage нет (РС-23)
}

Calc = {
  trancheId, creditId,
  base:         [{article, urgency, amount, since, included, blockedBy}],
  dispositions: [{article, urgency, kind, amount, periods}],
  version,                            // срок · ставка · льготные · метод
  cutoffSum, factSum,                 // срез и факт на дату вступления (РС-8)
  dsRef | excluded:{reason, date, by} // одно из двух, третьего нет (§4)
}

ds = { no, date, creditId, appId, calcIds[], kmAct:{no, date}, params }
```

**Ключ строки базы и распоряжения — тройка `(транш, статья, срочность)`.** Внутри расчёта
пара `(статья, срочность)` остаётся парой: `dispositionFor(dispositions, article, urgency)`
сигнатуру не меняет — меняется владелец списка, им становится `calc`, а не `app`. Тройкой
ключ работает на границе расчёта: в итогах заявки, в сторожах, в сверке базы с ДС.

Почему транш, а не кредит: условия и график принадлежат траншу, а не кредиту (`CONTEXT.md`,
`ASUBK-kredit-logika.md`), перенос — датированная операция **из транша в транш**
(`ADR-0092`, ИР-3), а инвариант ИР-2 «Σ статейных колонок графика = сумме переноса» меряется
на графике, то есть тоже на транше. Ключ по кредиту оставил бы кредит с двумя траншами в
той же неразличимости, из которой мы выходим, и потребовал бы выдумать правило разнесения
переноса по траншам — правило, которого норма не содержит.

**`creditIds` перестаёт быть полем** и выводится: `uniq(scope → транш → кредит)`. Это и
убирает шесть `creditIds[0]`: там, где рендер брал первый кредит, он теперь идёт циклом по
`app.calcs` либо по выведенным кредитам.

### 2. Что на каком уровне считается

| Величина | Уровень | Основание |
|---|---|---|
| база · распоряжения · параметры условий · график | **расчёт** (транш) | §1 |
| дата среза · виды · пакет документов · заключения · стадия · регламентные сроки | **заявка** | обращение одно, решение КМ одно (п. 82) |
| сумма среза · факт на дату вступления | расчёт; по заявке — Σ | РС-8 |
| порог существенности, **ступень 1** (виза куратора) | расчёт | §5 |
| порог существенности, **ступень 2** (возврат на комитет) | заявка, Σ расчётов | §5 |
| гейт согласий (ИР-8) · гейт покрытия (РС-18, РС-29) | кредит | уже так сегодня |
| пол ставки (п. 34, п. 92) · длина графика (п. 90) | кредит, над своими расчётами | РС-35, РС-37 |
| признак «повторная» ≥ 3 | кредит | уже так сегодня (РС-32) |
| ИР-1 «транш не в двух активных заявках» | транш | ключ переезжает с `creditIds` на `scope` |

### 3. Виды — на заявке, объединение одно

`kindIds` остаётся полем заявки; `allowedDispositions(app)` — объединение разрешённого,
одно на все расчёты. Акт Кабинета Министров один на обращение и называет формы обращения
целиком; второй набор видов на расчёте дал бы поле, которое нечем подпереть в акте.

Цена решения названа прямо: на транше видны пункты, разрешённые ради другого транша. Она
приемлема, потому что **фактически применённый набор форм выводится из распоряжений**, а не
из ещё одного поля, — в письмо и проект решения уходит разбивка «кредит → формы», собранная
из того, что куратор реально распорядился.

### 4. Регистрация ДС — по очереди; закрытие требует ответа по каждому расчёту

Одно ДС на кредит; ДС несёт записи условий по траншам своего охвата и ссылается на расчёты
(`calcIds`). Регистрируется **своими гейтами и своей датой вступления**: согласия (ИР-8),
покрытие либо снятие (РС-18, РС-29), регуляторные пределы (РС-19, РС-35), реквизиты
постановления КМ (ИР-12).

Переход **`оформление → закрыта`** требует, чтобы каждый расчёт заявки был либо
зарегистрирован (`dsRef ≠ null`), либо **явно снят** (`excluded` с основанием, датой и
автором). Молчания как варианта нет — тот же приём, что у гейта согласий ИР-8: «либо
согласие, либо явная отметка о прекращении».

Почему не транзакцией на все ДС разом: застрявшее согласие поручителя по кредиту 2 держало
бы готовую и одобренную сделку по кредиту 1, а сроки идут по обоим. Почему не закрытие по
первому ДС: незарегистрированное ДС по второму кредиту выпало бы из работы, оставшись
обязательством, за которым никто не следит.

### 5. Порог существенности — ступень 1 по расчёту, ступень 2 по заявке

Ступень 1 (≥ 10 % либо ≥ 500 000 сомов → виза куратора с письменным обоснованием) считается
**от базы среза расчёта**: она блокирует регистрацию конкретного ДС, значит и меряться
обязана тем, что в это ДС уходит. Считать её от суммы по заявке значит дать крупному кредиту
охвата глушить расхождение по мелкому — виза не возникнет там, где возникла бы при отдельной
заявке.

Ступень 2 (≥ 25 % либо ≥ 5 000 000 сомов → возврат на комитет, регистрация заблокирована)
считается **от Σ базы среза всех расчётов**: она откатывает заявку целиком, а комитет
высказывался по обращению, а не по кредиту. Блокировка при срабатывании ступени 2 — на все
расчёты заявки, а не только на превысивший.

Формулировка РС-26 «расхождение считается по базе целиком, не по статьям» сохраняется по
смыслу: разбивка по статьям по-прежнему не участвует ни в одной ступени. Уточняется, что
«целиком» значит по расчёту для ступени 1 и по заявке для ступени 2.

### 6. Инварианты

**ИР-16 (новый).** У каждого транша охвата ровно один расчёт, и у каждого расчёта — транш
из охвата. Иначе появляется сумма без адреса либо адрес без суммы.

Переформулируются по расчёту, а не по заявке:

- **ИР-2** (Σ всех статейных колонок графика = сумме переноса) — график свой у каждого
  производного транша;
- **ИР-15** (интервал сроков распоряжения лежит внутри длины графика) — длина графика своя
  у каждого расчёта, и РС-40 «интервал молча не подрезается» работает в границах расчёта.

Без изменений: ИР-1 (ключуется траншем и раньше), ИР-3, ИР-4, ИР-5, ИР-6, ИР-7, ИР-8,
ИР-9, ИР-10, ИР-11, ИР-12, ИР-13, ИР-14.

### 7. Экран

Вкладка «Расчёт» получает два яруса.

**Шапка-итог по заявке** — Σ базы · Σ переноса · расхождение ступени 2 с её порогом.
Единственное место, где суммы складываются через кредиты, и оно подписано как итог, а не
как база.

**Секции подряд, по одной на транш.** Заголовок секции:
`ТР-2 · КД-62021 · база 118 000 · ДС-62021/1` либо `… · не оформлено`. Внутри — нынешняя
таблица статей и двери распоряжений **без правок разметки**: они и так работают на паре
`(статья, срочность)`, которая внутри расчёта остаётся парой.

**При одном транше секция-заголовок не рисуется** — экран остаётся сегодняшним. Регрессии
для однокредитной заявки (а это все демо-заявки, кроме RS-1020) нет.

`pickTrancheBlock` уходит: транш под расчёт больше не выбирается отдельным шагом — расчёт
заводится добавлением транша в охват. Кнопка «Выбрать транш-источник» становится «Добавить
транш в охват», кандидаты берутся тем же `trancheCandidates` (открытый транш с остатком),
из списка вычитаются уже вошедшие в охват.

### 8. Правка макета

- `app.calcTranche` → `app.calcs[]`; `app.base` / `app.dispositions` / `app.version` /
  `app.ds` переезжают внутрь `Calc`.
- `defaultBase(app, date)` → `defaultBase(calc, date)`; `ensureBaseDispositions(app)` →
  `ensureBaseDispositions(calc)`; `toggleBaseRow` / `setDisposition` / `setDispAmount` /
  `setDispPeriods` получают `calcId` первым аргументом вместо чтения `app.base`.
- `dispositionFor` — без изменений.
- Шесть `creditIds[0]` (`1284, 1571, 2455, 2510, 2640, 2809`) → цикл по `app.calcs`;
  `app.creditIds` заменяется выводимым геттером над `scope`.
- `setCalcTranche` → `addTrancheToScope` (заводит `Calc` и черновик `version` от условий
  кредита этого транша); `removeTrancheFromScope` сносит расчёт вместе с траншем.
  `addCredit(appId)` (охват по кредиту) уходит следом: охват называет траншы, и кредит в
  нём появляется вместе со своим траншем, а не отдельным действием.
- `recalcPlan(appId)` → `recalcPlan(appId, calcId)`; кнопка живёт в секции.
- Гейт `оформление → закрыта` дополняется проверкой §4; заводится действие «снять расчёт с
  оформления» с обязательным основанием.

### 9. Демо и сторожа

- **RS-1020** (`CR-62021`, `CR-62017`, стадия «проектКМ») — единственная многокредитная
  заявка сида и сегодня расчёта не имеет вовсе. Получает два расчёта с **разными** базами:
  различие сумм должно быть видно глазом, а не выводиться из кода.
- Новый сценарий смоука: у заявки с двумя траншами разных кредитов суммы секций различны,
  Σ шапки равна их сумме, ступень 2 меряется от Σ, ступень 1 — от секции.
- Новый сценарий смоука: гейт `оформление → закрыта` не пропускает заявку, у которой один
  расчёт зарегистрирован, а второй ни зарегистрирован, ни снят.
- Существующие сторожа однокредитных заявок обязаны пройти без правок — это и есть
  проверка того, что §7 не тронул экран при одном транше.

## Что не делаем

- **Не заводим виды на расчёте** — §3.
- **Не трогаем канон долга.** Пять статей охвата (`ADR-0110`), семь статей канона
  (`ADR-0093`) — расхождение остаётся ровно там, где было.
- **Не меняем маршрут стадий** (`ADR-0107`): девять стадий, сроки на заявке, решение КМ
  одно на обращение.
- **Не вводим правило разнесения переноса по траншам** — его не нужно: перенос адресован
  траншу с самого начала.
- **Не переписываем взыскание и залог**: гейты покрытия и согласий уже per-credit и
  остаются как есть.
