# Единый переключатель области карточки кредита (КВ-17)

Дата: 04.08.2026 · Мокап: `mockups/loan-credit/credit.html` · Область правки:
состояние карточки (`detailTrancheNo` / `condScope` / `calcConsolidated`), `headerHtml()`,
пять вкладок (Условия · Транши · График · Прогноз · Расчёты), три модалки
(освоение, график, платёж). Модель кредита, `derive()`, реестр — не трогаем.

## Задача

Область просмотра (кредит целиком или отдельный транш) сейчас набрана **тремя
пересекающимися контролами и тремя переменными**:

| контрол | переменная | значения | вкладки |
|---|---|---|---|
| select «по кредиту (агрегат) / Транш №N» | `condScope` | `'credit'` \| N | Условия (скрыт при 1 транше) |
| select «Транш №N» | `detailTrancheNo` | только N | График, Прогноз, Расчёты |
| клик по строке таблицы | `detailTrancheNo` | N | Транши |
| чекбокс «консолидировано по кредиту» | `calcConsolidated` | bool | Расчёты (только детальный расчёт) |

Три дефекта:

1. **«Расчёты» несут два контрола вместо одного.** Селект транша плюс чекбокс
   «консолидировано» вместе дают ровно семантику `condScope` (`'credit'` \| N),
   только разнесённую по двум элементам управления, стоящим в одной панели рядом.
2. **Область объявлена дважды разными словами.** «по кредиту (агрегат)» на «Условиях»
   и «консолидировано по кредиту» на «Расчётах» — одно и то же понятие под двумя
   именами, в двух разных типах контрола (select и чекбокс).
3. **Область — свойство карточки, а не вкладки.** Тот же класс, что КР-29 (дата среза
   жила на вкладке «Условия» и остальным не управляла); он был закрыт КВ-10 переносом
   `cardAsOf` в шапку. Область — второй параметр того же среза и осталась не перенесённой.

## Решение

### 1. Одна переменная

```js
let cardScope = 'credit';   // 'credit' | номер транша — область просмотра карточки
```

Удаляются `detailTrancheNo`, `condScope`, `calcConsolidated`. Все места чтения
переводятся на `cardScope` через один хелпер:

```js
/* Транш, к которому относится вкладка. При области «по кредиту» — null (агрегат/сводка).
   Кредит с одним траншем: 'credit' и «Транш №1» неразличимы → всегда отдаём транш. */
function scopeTranche(c){
  if (c.tranches.length === 1) return c.tranches[0];
  return cardScope === 'credit' ? null : (c.tranches.find(t => t.no === cardScope) || null);
}
```

`cardScope = 'credit'` встаёт в блок сброса при открытии карточки — туда же, где уже
стоят `cardAsOf = TODAY` и `condScope = 'credit'` (`openDetail`, ~строка 5185).

**Модалки свои селекты транша сохраняют.** В `addDisbursement`, `buildSchedule`,
`addPayment` транш — параметр действия, а не область просмотра; выбор там адресный и
от области не зависит. Предвыбор берут из `scopeTranche(c)` (при `null` — первый
активный транш), по подтверждении ставят `cardScope = <номер транша>` — ровно то, что
эти модалки уже делают через `detailTrancheNo`.

### 2. Контрол в шапке

Встаёт в `phead-acts` **перед** `asOfBox`: область читается раньше даты — «что смотрим»,
затем «на когда».

```
Область [По кредиту ▾]   По состоянию на [04.08.2026]  [⟲ сегодня]  [Печать ▾]
```

- Значения: `По кредиту` · `Транш №1` … `Транш №N`.
- **Кредит с одним траншем** → контрол не рендерится вовсе: выбирать нечего, а
  «По кредиту» и «Транш №1» дали бы два имени одному и тому же. Идиома уже
  применена на «Условиях» (`c.tranches.length > 1`).
- **Инертные вкладки** — Договор, Платежи, План, Обеспечение, Проблемные, Досье —
  область не читают. На них контрол рендерится `disabled` с
  `title="Вкладка «<имя>» — всегда по кредиту целиком"`. Не прячем: шапка не должна
  дёргаться при переходе между вкладками, а выбранное значение остаётся на виду.
- **Плитки шапки за областью не следуют** — все девять строятся из `derive(c, cardAsOf)`
  и считаются по кредиту целиком; долг, категория риска и обеспеченность на транш не
  считаются вовсе. Чтобы контрол рядом с ними не читался как обещание, при
  `cardScope !== 'credit'` под рядом плиток выводится строка-подпись:
  `Плитки — по кредиту целиком; область «Транш №N» действует на вкладки ниже.`
  Плашку `info-plate` (как у `cardAsOf !== TODAY`) не берём: смена даты — событие
  редкое, выбор транша — рутина, и плашка на каждый клик стала бы шумом.

### 3. Что означает «По кредиту» на каждой вкладке

Правило одно, и оно уже написано в макете: `calcConsolidated` на «Расчётах» сливает
строки всех траншей в одну таблицу и добавляет колонку «Транш». Эта идиома
распространяется на «График» и «Прогноз».

| вкладка | область «По кредиту» | область «Транш №N» |
|---|---|---|
| **Условия** | агрегат `creditConditionsAt(c, cardAsOf)` + блок «Расхождения по траншам» | комплект `conditionsAt(t, cardAsOf)`, блок расхождений скрыт |
| **Транши** | ни одна строка таблицы не подсвечена | строка транша подсвечена |
| **График** | плитки — Σ по траншам; таблицы версий и позиций остаются двумя, но каждая слита по траншам: +колонка «Транш», сортировка по дате | как сейчас |
| **Прогноз** | плитки — Σ по траншам; таблица позиций слита, +колонка «Транш», сортировка по дате | как сейчас |
| **Расчёты** | нынешнее `calcConsolidated === true` | нынешнее `calcConsolidated === false` |

Поведение вкладок «Условия», «Транши» и «Расчёты» в области «По кредиту» уже
реализовано — меняется только источник признака (`cardScope` вместо `condScope` /
`calcConsolidated`).

Две оговорки для «Графика» и «Прогноза»:

- **Плитка платежа** (`st.payLabel` / `st.payValue` из `trancheScheduleTotals`) выводится
  из метода погашения условий транша. Если методы траншей на дату среза разошлись —
  значение `—`, подпись `несколько методов погашения`. Складывать медианы разных
  методов нельзя: это уже ловилось и было причиной, по которой `trancheScheduleTotals`
  сделали однотраншевым.
- **Кнопка «Сформировать график»** при области «По кредиту» —
  `disabledBtn('Сформировать график', 'График принадлежит траншу — выберите транш в шапке')`.
  Действие адресное (Р-1), агрегата у него нет.

## Отклонено

**Стопка отдельных секций по траншу** вместо слитой таблицы на «Графике»/«Прогнозе».
«Расчёты» уже задали идиому слияния с колонкой «Транш»; две разные трактовки
«По кредиту» в соседних вкладках хуже одной. Плюс стопка растёт линейно по числу
траншей и ломает сортировку по дате — а именно она отвечает на вопрос «что платим
следующим», ради которого агрегат и нужен.

**Переключатель без варианта «По кредиту»** (только транши). Это самый малый диф, но
слияние получилось бы неполным: агрегат условий и консолидированный расчёт пришлось
бы оставить отдельными контролами внутри вкладок — то есть три контрола стали бы
двумя вместо одного.

**Плитки шапки, следующие за областью.** Обещание было бы честным, но это другая
задача: долг, категория риска и обеспеченность на транш не считаются, их
пришлось бы либо проектировать заново, либо показывать прочерками. Граница проведена
так: шапка — всегда кредит целиком, область управляет телом вкладки.

## Проверка

Демо-данные уже содержат нужные случаи: `K-C*` — двухтраншевые кредиты, среди них
есть расхождение по методу погашения (транш №2, ДС-1007), и есть валютные
`K-B2/K-B4/K-B6` с траншем и освоением. Ручной сценарий:

1. Двухтраншевый `K-C*`: переключить область на «Транш №2», обойти все 11 вкладок —
   Условия/Транши/График/Прогноз/Расчёты показывают транш №2, остальные шесть
   гасят контрол с подсказкой, выбранное значение из селекта не пропадает.
2. Он же, область «По кредиту»: «График» и «Прогноз» показывают слитую таблицу с
   колонкой «Транш»; кнопка «Сформировать график» неактивна с подсказкой; плитка
   платежа при расхождении методов даёт `—` и подпись «несколько методов погашения».
3. Однотраншевый кредит (любой `K-B*`, `K-1`…): контрола в шапке нет; «График»,
   «Прогноз», «Расчёты» показывают транш №1; «Условия» — его комплект без блока
   расхождений.
4. Модалка освоения на двухтраншевом при области «Транш №2»: селект транша в
   модалке предвыбран на №2; выбрать в модалке №1 и подтвердить → область в шапке
   стала «Транш №1».
5. Смена области не сбрасывает `cardAsOf`, смена даты не сбрасывает `cardScope`;
   выход в реестр и повторный вход — область снова «По кредиту».
