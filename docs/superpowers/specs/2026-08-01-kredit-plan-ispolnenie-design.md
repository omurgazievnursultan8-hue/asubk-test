# План · Прогноз · Исполнение плана в макете кредита — дизайн

**Дата:** 2026-08-01 · **Макет:** `mockups/loan-credit/credit.html`
**Основание:** [ADR-0042](../../adr/0042-plan-kredita-vvodimaya-velichina-snimok-prognoza.md),
глоссарий [CONTEXT.md](../../../CONTEXT.md) (термины «Прогноз», «План», «Исполнение плана»)
**Спека логики:** [ASUBK-kredit-logika.md](../../../mockups/loan-credit/ASUBK-kredit-logika.md)

## Задача

CONTEXT.md и ADR-0042 приняты 31.07.2026 и ввели три термина, которых в макете нет
вовсе: **прогноз**, **план**, **исполнение плана**. Макет остался жить по прежней
модели, где будущее кредита описывает только график погашения.

Внедрить все три. Ключевое требование ADR-0042: **план — вводимая величина, а не
производная**, и это явное исключение из ADR-0001, которое обязано быть видимым.

## Что уже есть в макете (точки крепления)

| Что | Где |
|---|---|
| График погашения транша, версии, позиции | `trancheScheduleRows(t)`, `buildSchedule(t, from)`, вкладка «Расчёты» |
| Детальный расчёт (начислено/погашено по позициям) | `buildLedger(c, asOf)` → `d.ledger.index`, ключ `ledgerKey(trancheNo, no)` |
| Засчитывается ли платёж | `paymentCounts(p)` — читает две оси (Р-27) |
| Разнесение платежа по статьям | `p.layers`, `paymentAllocated(p)`; дата поступления — `p.date` |
| Дата среза карточки | `cardAsOf`, единая на карточку (Р-24) |
| Вкладки карточки | `DTABS` (8 шт.), диспетчер в `renderDetailTab` |
| Гейты и кнопки под ними | `actBtn(c, action, ctx, label, onclick, cls)`, `modalGuard(action)` |
| Плитки шапки | `.phead-dims` |
| Смоук | 79 проверок, `node scripts/inspect/credit-check.mjs` |

## Решения (приняты владельцем 2026-08-01)

1. **Размещение.** Прогноз → вкладка «Расчёты» (он пересчитывает график, живёт в разрезе
   транша). План и исполнение → **новая 9-я вкладка «План и исполнение»** (месяц × кредит
   целиком — другая гранулярность, на транш-вкладке ей тесно).
2. **Глубина прогноза.** Полная перестройка от фактического остатка ОД, а не позиционная
   дельта: иначе досрочное погашение не уменьшает будущие суммы и прогноз вырождается в
   третий способ спросить то же, что график.
3. **Заведение плана.** Пачкой за период, каждая строка предзаполнена прогнозом месяца.
4. **Витрина.** Плитка «Исполнение плана» в шапке карточки. Колонка и фильтр в реестре
   кредитов — **не делаем** (потребовала бы сидировать план на все 59 демо-кредитов).
5. **След правки.** Вариант **А**: `history` на строке плана + дубль-запись в общий
   `c.audit`.

---

## 1. Модель

Хранимое поле **одно** — план. Прогноз и исполнение выводятся в рантайме (Р-11, ADR-0001).

```js
c.plan = [{
  month:'2026-08',            // YYYY-MM; сумма — в валюте кредита
  amount:120000,              // вводимая величина; null = план снят
  setBy:'Иванов А.', setAt:'20.07.2026',
  seededFrom:118450,          // прогноз на МОМЕНТ заведения — снимок, не связь
  history:[{ at:'14.08.2026', by:'Иванов А.', prev:100000, note:'уточнено после ДС-2' }]
}]
```

**`seededFrom` держится отдельно от `amount`.** Иначе не видно, правили строку от
предзаполнения или приняли прогноз как есть, — а ADR-0042 именно про то, что план
отвязывается от прогноза в момент сохранения.

**Снятие плана — не удаление** (И-14). Снятие ставит `amount:null` и кладёт прежнее
значение в `history`; строка остаётся видимой с пометкой «снят», месяц выпадает из
расчёта исполнения.

**Отвергнуто:**
- след правки только в общем `c.audit` — «кто двигал план на август» ищется грепом по
  журналу досье;
- версионирование записями `param·value·effectiveFrom·basis`, как условия (Р-21) — у
  плана нет зарегистрированного основания, его двигает человек, а не документ.

## 2. Прогноз — производная транша

```
trancheForecastRows(t, ledgerIndex, asOf) -> [{ no, date, scheduled, forecast, delta }]
```

Даты позиций **не меняются** — меняются только суммы:

| Позиция | Прогноз |
|---|---|
| дата ≤ даты среза | непокрытый остаток позиции (просроченный хвост) из `ledgerIndex` |
| весь непокрытый хвост прошлого | сваливается в ближайшую будущую позицию |
| будущие | `buildSchedule`-логика от **фактического остатка ОД на дату среза** и оставшегося числа платежей, ставка — `conditionsAt(t, asOf)` |

Агрегат для предзаполнения плана:

```
forecastByMonth(c, ledgerIndex, asOf) -> Map<'YYYY-MM', сумма прогноза по ВСЕМ траншам>
```

**UI.** Блок «Прогноз (транш №N)» сразу после «График — позиции» во вкладке «Расчёты»:
`№ · Дата · По графику · Прогноз · Δ · Статус`. `section-note` говорит прямо: прогноз —
предположение о том, как график сложится фактически; контракт он не подменяет и в
исполнение плана не входит.

**Д-9 (новое демо-ограничение).** Прогноз — детерминированное упрощение, ровно как и
график: аннуитет не пересобирается по банковским правилам, производственный календарь не
применяется (тот же открытый вопрос №5).

## 3. Исполнение плана — производная

**Факт месяца** = Σ `paymentAllocated(p)` по платежам, у которых `paymentCounts(p) === true`
и дата фактического поступления `p.date` попала в месяц.

Все четыре статьи кредита входят. Расходы по обращению взыскания не входят и **не могут
войти по построению**: они приходят отдельным зеркалом `mirror.collectionCosts`, а не
платежами. Оговаривается комментарием у функции — правило принадлежит CONTEXT.md, а не
случайной форме данных.

**Исполнение** = факт / план за тот же месяц.

**Месяц без плана выпадает целиком** — из своей строки, из суммы квартала и из суммы года
(CONTEXT.md). Факт такого месяца показывается серым, справочно: он существует, но
сравнивать его не с чем.

```
planExecOf(c, asOf) -> {
  rows:[{ month, forecast, plan, fact, pct, edits, dropped }],
  quarters:[{ q, plan, fact, pct }],
  year:{ plan, fact, pct, monthsWithPlan, monthsTotal },
  current:{ month, plan, fact, pct } | null      // месяц даты среза — для плитки шапки
}
```

## 4. UI

### 4.1. Новая вкладка «План и исполнение»

В `DTABS` вставляется **после «Платежи»** — исполнение сверяется именно с ними.

1. **Плитки:** `План за год · Факт за год · Исполнение, % · Месяцев с планом` (N из 12).
2. **Тулбар:** селектор года + `actBtn(c,'setPlan',…,'Поставить план')`.
3. **Таблица месяцев:** `Месяц · Прогноз · План · Факт · Исполнение % · Правки`.
   Исполнение — пилюля-светофор. Строка без плана: «—» в плане и в проценте, приписка
   «в расчёт не входит». Строка со снятым планом — та же приписка плюс пометка «снят».
4. **Итоги** по кварталам и за год — строками; считаются только по месяцам с планом.
5. **Раскрытие строки** → журнал правок: кто · когда · было → стало · примечание. Там же
   `seededFrom` подписью «предзаполнено прогнозом: …».

### 4.2. Модалка «Поставить план»

`с месяца — по месяц` → таблица строк на период. Каждая строка предзаполнена
`forecastByMonth` того месяца, галка «ставить» на каждой, сумма правится. Месяцы, где план
уже стоит, приходят со своим `amount` и помечаются «будет правка» (с показом прежнего
значения) — чтобы правка задним числом не выглядела заведением с нуля.

### 4.3. Плитка шапки

«Исполнение плана»: процент за месяц даты среза, основание — `факт X / план Y · год Z %`.
Плана на месяц нет → «план на месяц не поставлен». **Не ноль**: ноль означал бы «ничего не
собрали», а не «цели не ставили».

## 5. Гейты и инварианты

- **Г-30 `setPlan`** — ЖЦ не «Проект» и не «Закрыт»; сумма > 0 либо явное снятие; месяц не
  раньше месяца договора. Отказ называет **сработавшую причину**, а не имя гейта (§10.1
  спеки логики).
- **И-18** — план не входит ни в один гейт, ни в одну производную долга, ни в категорию
  риска, ни в подгруппу заёмщика. Он показатель для отображения. Причина: цель, которую
  сам себе поставил куратор, не может ужесточать регуляторную оценку кредита.
- **Р-29** — формулировка ADR-0042 в шапку `credit.html`: план — вводимая величина, снимок
  прогноза при заведении; прогноз и исполнение — производные; три сущности друг на друга
  не ссылаются.

## 6. Проверка

Смоук 79 → ~88. Новый блок «План и исполнение»:

1. `derive` на кредите с планом и без плана даёт побитово равные `debtBalance`,
   `riskCategory`, `coverage`, `overdueDays` — И-18.
2. Месяц без плана не входит ни в квартальную, ни в годовую сумму.
3. Правка кладёт прежнее значение в `history`; `seededFrom` при правке не двигается.
4. **Ключевая проверка ADR-0042:** сохранённый план не меняется после изменения прогноза —
   вносим платёж, прогноз на месяц едет, план стоит на прежнем значении.
5. Прогноз ≠ график на кредите с досрочным погашением.
6. Σ прогноза по будущим позициям = остаток ОД + будущие проценты.
7. Г-30 закрывает кредит в «Проекте» и в «Закрыт»; отказ называет причину.
8. Рендер вкладки на всех 59 демо-кредитах — включая кредиты без плана и без графика.

Проверка запуском: `node scripts/inspect/credit-check.mjs`.

## 7. Демо-данные

План сидируется на **K-1** (8 месяцев: один с правкой в `history`, один снятый, два месяца
периода без плана — чтобы «выпадение из расчёта» было видно на демо), плюс на **K-2** и
**K-3**, чтобы плитка шапки не была пустой при первом открытии. Фон-кредиты `K-B*` и
`K-C*`, а также смоук-кредиты `K-1…K-6b` в остальной части не трогаются.

## Границы

- Реестр кредитов не меняется: ни колонки, ни фильтра по исполнению плана.
- План живёт только на карточке кредита; сводного реестра планов по портфелю нет.
- Прогноз не влияет ни на начисление, ни на график, ни на гейты — только отображается.
- Печатных форм по плану не добавляется (печать вне объёма макета).
