## 0. Краткая суть

Семь решений, определяющих логику:

1. **Доступ никогда не задаётся прямо на пользователе.** Только через роли.
2. **Роль и scope — независимы.** Одна и та же роль у сотрудника головного офиса и у
   сотрудника филиала даёт разный доступ к записям.
3. **Один чистый вычислитель прав** — `resolvePermission(пользователь, функция, действие,
   запись?, контекст)`. Весь интерфейс гейтится только через него, второго пути нет.
4. **Четыре независимых измерения в строгом порядке:** функциональное → строчное → сетевое →
   контроль.
5. **Политика подразделения только сужает.** Запретов как отдельной сущности нет — есть
   изъятия из того, что дала роль.
6. **Замещение — не передача учётной записи, а срочное расширение прав замещающего** с семью
   проверками, из которых шесть блокирующие, а седьмая продавливаемая под запись в аудит.
7. **Журнал аудита — append-only.** Записи замораживаются при создании; интерфейса правки и
   удаления не существует ни у кого, включая администратора.

## 1. Сущности

### 1.1. Внешние (владелец — отдел кадров, модуль их читает)

| Сущность | Что несёт |
|---|---|
| **Подразделение** | дерево (родитель), код, наименование, **признак «головной офис»** |
| **Сотрудник** | ФИО, табельный номер, подразделение, должность, **кадровый статус** (Работает / В отпуске / Уволен), контакты |

**Подразделение сотрудника — источник строчной видимости.** Признак «головной офис» даёт
видимость вниз по дереву; у обычного подразделения видимость — только своё.

### 1.2. Учётная запись

Логин · **тип** (Личная / Техническая) · ссылка на сотрудника (у технической — пустая) ·
статус · признак «требует смены пароля» · дата смены пароля · счётчик неудачных попыток ·
последний вход (время и IP) · кем и когда создана.

**Пароль хранится только хэшем и не отображается никогда и никому.**

### 1.3. Роль

Код · наименование · описание · **признак globalScope** · статус (Действует / Архивная) ·
набор разрешений вида «функция → список действий».

**Архивная роль** не назначается новым учётным записям, но остаётся видимой в истории: снятие
роли не стирает прошлое.

### 1.4. Реестр функций — системный, только для чтения

Дерево функций повторяет навигацию приложения. У каждой функции объявлено:

- **какие действия к ней применимы** из пяти: `view` · `create` · `edit` · `delete` ·
  `execute`;
- **проверка принадлежности объекта**, если нужна (три вида, §3.4);
- **признак «критичная»** — попадает под сетевое ограничение.

Функции двух родов: **экранные** («Заявки», «Кредиты», «Справочники») и **операционные**
(«Заявка · Отправить в комиссию», «Кредит · Списание задолженности», «Залог · Снятие залога»,
«Комиссия · Голосовать», «Роли · Назначение роли»). У операционной применимо обычно только
`execute`.

### 1.5. Назначение роли (связь)

Учётная запись × роль, кем и когда назначена, **когда снята**. **Снятие — это дата снятия, а
строка не удаляется:** иначе нельзя ответить, какие права были у человека в марте.

### 1.6. Политика роли в подразделении

Пара «роль × подразделение» с **перечнем изъятых разрешений**. Только сужает.

Пример из прототипа: у роли «Кредитный специалист» в филиале «Юг» изъято «Заявка · Отправить
в комиссию» — отправка идёт через головной офис. Тот же специалист в филиале «Север» отправляет
сам.

### 1.7. Замещение

Замещаемый сотрудник · замещающая учётная запись · период (с / по) · **ссылка на приказ** ·
**набор ролей (подмножество ролей замещаемого)** · статус · кем создано · продавленное
предупреждение, если было.

Статусы: **Запланировано → Действует → Завершено**, плюс досрочное **прерывание**.

### 1.8. Сессия и сетевая политика

**Сессии одновременные разрешены** (один человек — несколько устройств). У сессии IP и
устройство.

**Сетевая политика** — именованный набор IP-диапазонов (CIDR) и, вспомогательно, MAC-адресов.
**Ограничение функции** — тройка «функция × действие → политика».

### 1.9. Запись журнала аудита

Время · актор (учётная запись **либо система**) · сессия · IP · действие · тип и идентификатор
объекта · **было → стало** · **«замещая кого»**.

## 2. Что модуль не заводит, а читает

| Данные | Владелец | Зачем модулю |
|---|---|---|
| Подразделения и сотрудники | отдел кадров | подразделение даёт строчную видимость; увольнение отключает запись |
| **Кураторство** (кто за какими записями закреплён) | модуль кураторства | кураторский scope |
| **Членство в комиссиях** | данные заявки, **не оргструктура** | проверка «голосовать может только член этой комиссии» |

Про кураторство прототип оговаривается прямо: он держит его отдельным реестром и **читает**;
где кураторство ведётся на самом деле — открытый вопрос модуля доступа, решённый уже в
соседнем модуле.

## 3. Ядро: единый вычислитель прав

**`resolvePermission(пользователь, функция, действие, запись?, контекст) → {разрешено,
причина, подробность}`**

Причина — одно из шести значений: `ok` · `no-role` · `denied-by-policy` · `out-of-scope` ·
`blocked-by-network` · `pending-control`.

**Порядок четырёх измерений строгий.** Он же — порядок объяснения отказа: пользователю
сообщается **первая** причина, а не список.

### 3.1. Измерение 1 — функциональное

**Эффективные роли = роли активных назначений ∪ роли активного замещения.**

Далее из полученного **вычитаются изъятия** политики роли в подразделении пользователя.

**Запретов (deny) в модели нет.** Есть только «дала роль» и «изъяла политика». Причина: два
источника — разрешающий и запрещающий — требуют правила приоритета, а правило приоритета
всегда оказывается неочевидным в тот момент, когда нужно объяснить отказ.

Результат шага: `no-role` (ни одна роль не даёт этого действия на этой функции) ·
`denied-by-policy` (дала роль, изъяла политика подразделения) · `ok`.

### 3.2. Измерение 2 — строчное (scope)

Проверяется **только при наличии записи**. Запись в scope, если верно хотя бы одно:

1. у пользователя есть роль с **globalScope** — видит все записи системы;
2. подразделение записи входит в **подразделение пользователя плюс поддерево** (поддерево
   раскрывается только у головного офиса);
3. запись **закреплена за пользователем кураторством** — своя или **замещаемого** при активном
   замещении;
4. пользователь — **владелец** записи (автор);
5. пройдена проверка принадлежности объекта (§3.4).

Отказ: `out-of-scope`.

**Пустой scope — законное состояние.** Техническая учётная запись без сотрудника и без
кураторства не видит ни одной записи, и это правильно, а не ошибка настройки.

### 3.3. Роль ≠ scope — центральный тезис

**Роль отвечает «что можно делать», scope — «по каким записям».** Они не складываются в одну
величину и настраиваются разными людьми.

Наглядно на одной роли «Кредитный специалист»:

| Пользователь | Подразделение | «Заявка · Подтвердить комплект» |
|---|---|---|
| сотрудник головного офиса | ГО | **Доступно** |
| сотрудник филиала «Север» | филиал | **Вне scope** |

Права одинаковые. Разный ответ даёт проверка принадлежности объекта, а не роль.

Второй наглядный случай — та же роль в двух филиалах:

| Пользователь | «Заявка · Отправить в комиссию» |
|---|---|
| филиал «Север» | **Доступно** |
| филиал «Юг» | **Изъято политикой** |

### 3.4. Проверка принадлежности объекта

Три вида, объявляются на функции:

| Вид | Что проверяет | Пример функции |
|---|---|---|
| **головной офис** | пользователь работает в подразделении с признаком «головной офис» | «Заявка · Подтвердить комплект (2-й уровень)» |
| **член комиссии** | пользователь входит в состав **той самой** комиссии | «Комиссия · Голосовать / подтвердить» |
| **подразделение заключения** | запись относится к подразделению-исполнителю пользователя | заключения отделов |

Проверка «головной офис» оценивается **по пользователю** и потому работает без записи;
остальные две **без записи не оцениваются** — возвращают «не определено», а не «запрещено».

Отсюда важное следствие для интерфейса: **«одна роль на все отделы».** «Свой отдел»
проверяется scope-ом, а не отдельной ролью на каждый отдел — иначе ролей столько же, сколько
отделов, и каждое изменение оргструктуры требует правки набора ролей.

### 3.5. Измерение 3 — сетевое

Если для пары «функция × действие» задано ограничение, действие возможно **только из сети,
описанной политикой**. Проверяется IP по CIDR; MAC учитывается, если политика его задаёт.

**Критичные операции прототипа:** списание задолженности по кредиту · снятие залога ·
назначение роли · создание замещения.

Отказ: `blocked-by-network` с человекочитаемой причиной («доступно только из сети
„Корпоративная сеть"; сейчас вне офиса, ip …»).

**Заблокированное сетью действие не исчезает, а гаснет с объяснением.** Пропавшая кнопка
читается как «мне это не положено», погасшая — как «не отсюда».

**Оговорка о MAC:** по HTTP он не передаётся. В прототипе это демонстрационный параметр
политики, в реальности механизм требует отдельного решения.

### 3.6. Измерение 4 — многоуровневый контроль (отложено)

Точка расширения, оставленная в ядре явной заглушкой: здесь появится ветка «действие уходит в
очередь подтверждения» с причиной `pending-control`. Сейчас условие константно истинно.

Отложено, потому что не решён вопрос **сколько уровней контроля** нужно. Оставлено именно
измерением, а не отдельным механизмом: иначе очередь подтверждения окажется пятым способом
запретить действие, не видимым из вычислителя прав.

## 4. Замещение

### 4.1. Что это

**Не передача учётной записи, а срочное расширение прав замещающего.** Замещающий входит под
своим логином, видит свои записи **плюс** записи замещаемого и действует **своими руками** —
но в аудите каждое такое действие помечено «замещая Осмонова О.».

Наследуется **кураторский scope замещаемого**: закреплённые за отсутствующим кредиты и заявки
попадают в scope замещающего на срок замещения.

**Роли замещения — подмножество ролей замещаемого.** Замещение не может дать больше, чем есть
у того, кого замещают.

### 4.2. Семь проверок

Шесть блокирующих:

| № | Проверка |
|:--:|---|
| **V1** | замещающий и замещаемый — **из одного подразделения** |
| **V2** | у замещаемого **нет замещения с пересекающимся периодом** |
| **V3** | у замещающего **нет замещения с пересекающимся периодом** |
| **V4** | роли замещения — **подмножество ролей замещаемого** |
| **V5** | учётная запись замещающего в статусе **«Активна»** |
| **V6** | замещающий **не совпадает** с замещаемым |

Плюс общие: выбран замещаемый и замещающий, указан период, «с» не позже «по», выбрана хотя бы
одна роль.

Седьмая — **предупреждение, а не запрет**:

> **V7 «четыре глаза».** Замещающий уже имеет **подтверждающую** роль, а по замещению получает
> **исполняющую** — контроль схлопывается в одни глаза.

Кнопка при срабатывании V7 меняет подпись на **«Всё равно создать (продавить V7)»** и цвет на
опасный; продавливание **пишется отдельной записью в аудит** и остаётся отметкой «V7
продавлено» на самом замещении навсегда.

Почему предупреждение, а не запрет: в отпускной период в малом отделе законных пар может не
быть вовсе, и жёсткий запрет остановил бы работу. Но продавливание обязано быть **видимым и
именным**, а не молчаливым.

**Подтверждающая** роль опознаётся по праву голосовать в комиссии; **исполняющая** — по правам
на переходы (отправить заявку в комиссию, списать задолженность, снять залог).

### 4.3. Жизненный цикл

**Запланировано** (период в будущем) → **Действует** (наступила дата «с») → **Завершено**
(прошла дата «по»). Автопереходы пишутся в аудит **актором «система»**.

Действующее или запланированное замещение можно **прервать досрочно**.

## 5. Жизненный цикл учётной записи

**Создана → Активна → Заблокирована ⇄ Активна → Отключена.**

| Переход | Как происходит |
|---|---|
| Создана | администратор заводит запись; **«требует смены пароля» = да** |
| → Заблокирована | вручную администратором **либо автоматически после 5 неудачных попыток входа** |
| Заблокирована → Активна | «Разблокировать»; **счётчик попыток сбрасывается** |
| → Отключена | вручную **либо автоматически при увольнении сотрудника** |
| **Отключена → Активна** | **невозможен.** Кнопка «Разблокировать» присутствует, но погашена с объяснением |

**Отключение необратимо.** При восстановлении сотрудника **заводится новая учётная запись с
новым логином**: иначе история действий двух разных периодов работы сливается в одну и
перестаёт быть доказательством.

**Отключение завершает все сессии** учётной записи, и число завершённых попадает в запись
аудита.

**Увольнение сотрудника отключает учётную запись автоматически.** Карточка и роли
**сохраняются для истории** — запись не удаляется никогда.

**Сброс пароля** ставит признак «требует смены при входе» и пишется в аудит; по отключённой
записи невозможен.

**Автоблокировка пишется в аудит актором «система», а не именем залогиненного
администратора.** Это был один из двух дефектов, найденных состязательной проверкой и
исправленных: иначе журнал утверждает, что администратор заблокировал человека, чего не было.

## 6. Аудит

**Append-only, физически.** Запись **замораживается в момент создания**, единственный способ
попасть в журнал — функция записи; интерфейса правки и удаления не существует ни у кого.
Экран журнала — грид только для чтения с фильтрами (время · ФИО или логин · отдел · действие)
и **ни одной кнопки правки или удаления**.

**Предзагруженная история заморожена так же, как рантайм-записи.** Это был второй найденный
дефект: заморозка распространялась только на новое, и сид-история оставалась изменяемой —
дырка ровно там, где журнал должен быть неопровержим.

**Действия администратора аудируются наравне со всеми.** Создание записи, назначение роли,
сброс пароля, продавливание V7 — всё в том же журнале, доступном аудитору.

Каждая запись несёт **«было → стало»** и, если действие совершено под замещением, **«замещая
кого»**.

| Экран | Что внутри |
|---|---|
| **Пользователи** | грид с фильтрами (подразделение · статус · роль · тип · поиск); тулбар Создать · Изменить · Заблокировать · Разблокировать · Отключить · Сбросить пароль · Завершить сессии — **видимость и погашение каждой кнопки считает вычислитель прав**. Карточка: Общая информация · Роли · Замещения · Сессии · История |
| **Роли** | грид (код · наименование · описание · globalScope · число назначений · статус). Карточка: Общая · **Матрица разрешений** (дерево функций × пять действий) · **Политики по подразделениям** (изъятия, сравнение базовых и эффективных прав) · Пользователи с ролью |
| **Замещения** | грид плюс форма создания с **живой валидацией V1–V7** |
| **Сетевые политики** | список политик (IP/CIDR, MAC) и привязки «функция × действие → политика»; **реально меняет гейтинг** |
| **Журнал аудита** | только для чтения, фильтры, без кнопок изменения |
| **Проверка прав** | «рентген» модели: эффективные роли и scope плюс дерево функций × действий с итогом вычислителя и **цветовой маркировкой причины**, плюс строчный доступ на реальных записях |

**Экран «Проверка прав» — не отладочный инструмент, а рабочий.** Вопрос «почему Асанов не
видит эту заявку» иначе решается перебором четырёх настроек в четырёх местах.

**В шапке переключается пользователь, а не роль.** Роли, scope и сетевой контекст
**вычисляются из модели**. Переключатель роли врал бы: он показывал бы права, которых у
конкретного человека нет, потому что его scope другой.

## 8. As-is: как это устроено сегодня (штатная безопасность Jmix)

Приложение не имеет собственного модуля доступа — работает штатный механизм платформы.

### 8.1. Три уровня

| Уровень | Что контролирует | На какой вопрос отвечает |
|---|---|---|
| **Ресурсные роли** | пункты меню, экраны, кнопки, CRUD сущностей, поля | что пользователь может делать |
| **Роли уровня строк** | какие **записи** видны и доступны для правки (JPQL-предикат) | какие строки видит пользователь |
| **Пользователи** | учётные записи и назначение ролей | кому какие роли |

Доступ **никогда** не задаётся прямо на пользователе — только роли, затем назначение.

### 8.2. Источник роли

**Аннотированный класс** — задана в Java-коде, в интерфейсе **только для чтения** (например
полный доступ, минимальный интерфейс, запуск отчётов). **База данных** — создаётся и правится
в интерфейсе; именно такими и управляет администратор.

### 8.3. Пять типов ресурсной политики

| Что контролировать | Тип | Ресурс | Действие |
|---|---|---|---|
| пункт бокового меню | `menu` | id меню | Доступ |
| экран (можно ли открыть) | `screen` | id экрана (список и форма — отдельно) | Доступ |
| операции с данными сущности | `entity` | имя сущности | Чтение / Создание / Изменение / Удаление |
| поле на форме или колонка | `entityAttribute` | `Сущность.поле` либо `Сущность.*` | Изменение / Чтение |
| нестандартная кнопка или доменное действие | `specific` | id специфичного права | Доступ |

**Стандартные кнопки** (Создать / Изменить / Удалить) управляются политикой `entity`
автоматически. **Нестандартные** (Одобрить, Отклонить, Назначить, экспорт) требуют политики
`specific`, и **список этих id определяет команда разработки** — администратор не может
выдать право, которого разработчик не зарегистрировал.

**Переиспользование — через дочерние роли:** узкие роли (по одной на экран) собираются в
должностную. Должностная роль может состоять **только** из дочерних, без собственных политик.

### 8.4. Подводные камни живого стенда

- **Пустая роль = нет доступа.** На стенде роли «СУГС» и «Специалист кредитного отдела» **без
  политик** — пользователь только с ними видит пустое приложение.
- **Меню без экрана и сущности:** пункт виден, страница не открывается. Набор выдаётся целиком.
- **Забытый атрибут сущности:** форма открылась, поля пустые или только для чтения.
- **Пустое выражение Where в политике уровня строк ничего не фильтрует** — ошибка роли `test`
  на стенде, то есть роль, выглядящая как ограничение, не ограничивает.
- **Роли с источником «Аннотированный класс» править нельзя** — они принадлежат коду.
- **Область действия имеет значение:** роль без отметки «UI» в веб-интерфейсе не применяется.
- **Изменения вступают в силу при следующем входе** пользователя или обновлении сессии.

Связь для строчных ограничений: пользователь → сотрудник → подразделение; она и используется в
JPQL уровня строк.

## 9. Ключевые решения и их причины

| Решение | Причина |
|---|---|
| Доступ только через роли, никогда полем на пользователе | флаг на пользователе нельзя ни повторить, ни проверить: каждая настройка становится единичным случаем |
| Роль и scope — независимые измерения | одна роль на все филиалы против роли на каждый филиал: второе умирает при первой правке оргструктуры |
| Один вычислитель прав, весь интерфейс через него | второй путь гейтинга расходится с первым, и кнопка появляется там, где действие запрещено |
| Порядок измерений строгий | пользователю сообщается первая причина отказа, а не список; иначе объяснение бесполезно |
| Запретов нет, есть изъятия | два источника (разрешающий и запрещающий) требуют правила приоритета, которое всегда неочевидно в момент отказа |
| Политика подразделения только сужает | расширяющая политика — второй способ выдать право, минуя роль |
| «Одна роль на все отделы», свой отдел — через scope | иначе ролей столько, сколько отделов |
| Проверка «член комиссии» без записи не оценивается | «не определено» и «запрещено» — разные ответы; второй врёт в проверке прав |
| Пустой scope законен | техническая запись без сотрудника не должна видеть ничего, и это не ошибка настройки |
| Критичные операции ограничены сетью | списание задолженности из дома — не то же самое, что из офиса |
| Заблокированное сетью действие гаснет, а не исчезает | пропавшая кнопка читается как «не положено», погасшая — как «не отсюда» |
| Контроль оставлен измерением, а не отдельным механизмом | иначе очередь подтверждения станет пятым способом запретить, невидимым из вычислителя |
| Замещение — расширение прав замещающего, а не передача записи | под чужим логином действия становятся анонимными |
| Роли замещения ⊆ роли замещаемого | иначе замещение — способ получить права, которых нет ни у кого |
| Кураторский scope наследуется замещающим | иначе отсутствие куратора останавливает работу по его кредитам |
| V1–V6 блокируют, V7 предупреждает | в малом отделе в отпускной период законной пары может не быть вовсе; но продавливание обязано быть именным и видимым |
| Продавливание V7 пишется в аудит и остаётся отметкой | разовое решение не должно исчезать вместе с тем, кто его принял |
| Снятие роли — дата, строка не удаляется | иначе нельзя ответить, какие права были в марте |
| Архивная роль видна в истории, но не назначается | прошлое не переписывается, будущее не плодит мёртвые роли |
| Отключение необратимо, восстановление — новая запись | иначе история двух периодов работы сливается и перестаёт быть доказательством |
| Увольнение отключает запись автоматически | ручной шаг здесь пропускается ровно тогда, когда он важнее всего |
| Автоблокировка пишется актором «система» | иначе журнал утверждает, что человека заблокировал администратор, чего не было |
| Аудит замораживается физически, включая сид-историю | журнал, который можно поправить, не доказывает ничего |
| Действия администратора аудируются наравне со всеми | администратор — самый интересный для аудита актор |
| Переключается пользователь, а не роль | переключатель роли показывал бы права, которых у человека нет, потому что его scope другой |
| Экран «Проверка прав» — рабочий, не отладочный | иначе «почему он не видит заявку» решается перебором четырёх настроек в четырёх местах |

## 10. Открытые вопросы и долги

1. **Спецификация модуля отсутствует.** Прототип объявляет её источником истины и цитирует
   параграфы; файла нет ни в одном коммите. Модель восстановима только из кода прототипа.
2. **Сколько уровней контроля нужно** — не решено; слой контроля отложен явной заглушкой в
   ядре.
3. **Реализуемость MAC** — по HTTP не передаётся; в прототипе демонстрационный параметр.
4. **Двухфакторная аутентификация** отложена, вне модели входа прототипа.
5. **Где ведётся кураторство** — прототип держит отдельный реестр и читает его; фактический
   владелец определён уже в модуле кураторства, но шов не описан.
6. **Значения политик** (длина и срок пароля, порог попыток, таймаут сессии) —
   демонстрационные; порог попыток 5 взят условно, нормативных значений нет.
7. **Разрыв as-is и to-be не сшит.** Приложение стоит на штатной безопасности платформы
   (ресурсные политики пяти типов, JPQL уровня строк), а прототип описывает собственную модель
   (реестр функций, четыре измерения, замещения, сетевые политики). Как одно переходит в
   другое — не записано: покрывается ли «функция × действие» ресурсными политиками, чем
   становятся `specific`-права, как scope ложится на JPQL.
8. **Права на боевом стенде настроены неполно:** две роли без политик, роль уровня строк с
   пустым выражением. Это состояние стенда, но оно же показывает, что модель без проверки
   заполненности разрешает «роль, которая ничего не значит».

## 11. Словарь терминов

| Термин | Значение |
|---|---|
| **Учётная запись** | логин и вход; бывает личная (привязана к сотруднику) и техническая |
| **Роль** | набор разрешений «функция → действия» |
| **globalScope** | признак роли: видит все записи системы |
| **Функция** | единица реестра функций: экран либо операция |
| **Действие** | одно из пяти: `view` · `create` · `edit` · `delete` · `execute` |
| **Разрешение** | пара «функция × действие» |
| **Scope (строчное измерение)** | множество записей, доступных пользователю |
| **Изъятие** | разрешение, вычтенное политикой роли в подразделении |
| **Проверка принадлежности объекта** | дополнительное условие функции: головной офис / член комиссии / подразделение заключения |
| **Замещение** | срочное расширение прав замещающего ролями замещаемого |
| **Продавливание V7** | сознательное создание замещения, схлопывающего «четыре глаза», с записью в аудит |
| **Сетевая политика** | именованный набор IP-диапазонов и MAC-адресов |
| **Ограничение функции** | привязка «функция × действие → сетевая политика» |
| **Append-only** | журнал, в который можно только добавлять; записи замораживаются |
| **Ресурсная роль** | штатная роль платформы: экраны, сущности, поля, кнопки |
| **Роль уровня строк** | штатная роль платформы: JPQL-фильтр видимых записей |
