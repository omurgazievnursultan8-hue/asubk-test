## 0. Краткая суть

Комиссия — **запись о коллегиальном рассмотрении одной заявки**: состав, голоса, дедлайн,
протокол и единственное итоговое решение.

Пять вещей, которые определяют логику модуля:

1. **Движок решения один и живёт здесь.** Карточка заявки итог не выносит, а **отражает**
   (read-only зеркало). Два движка с расходящимися правилами — главная опасность, которую эта
   архитектура закрывает.
2. **Одна комиссия судит кредит и залог вместе.** Отдельной залоговой комиссии нет.
3. **Кворум-гейт:** итоговое решение нельзя вынести, пока не проголосовало `⌊n/2⌋+1` членов и
   не заполнены номер протокола и дата заседания. Причина блокировки всегда называется словами,
   в порядке устранения.
4. **Решение выносит только председатель.** Голосуют члены состава, протокол ведут председатель
   и секретарь, записи создаёт и удаляет секретарь.
5. **Комиссия голосует одинаково в обоих потоках заявки, но обязана показать последствие
   одобрения до нажатия кнопки:** поток A даёт кредит, поток B — нет.

## 1. Назначение и место в конвейере

```
Заявка (статус «На рассмотрении»)
      │  отправка в комиссию
      ▼
Комиссия по заявкам:  состав → голоса → кворум → решение → протокол → скан
      │
      ├─ Одобрено          → заявка: поток A «На оформлении» (кредит создаётся)
      │                      поток B «Ожидает решения/программы» (кредита нет)
      ├─ Отклонено         → заявка «Отклонена» (терминал)
      └─ Требуется доп.    → заявка «Требуется доп. информация» (возврат специалисту)
         информация
```

Модуль не решает, готова ли заявка к рассмотрению — это гейт отправки на стороне заявки.
Модуль решает, можно ли вынести итог по уже поступившей заявке.

### 1.1. Две фазы, один движок

| Фаза | Где живёт | Что делает | Движок здесь? |
|---|---|---|---|
| **A. Предварительное изучение** | карточка заявки, вкладка «Комиссия» | список обязательных документов, «Запросить замену» (возврат документа специалисту), «Вынести на заседание комитета» | да — переход фаз и возврат документа |
| **B. Заседание комитета** | **модуль комиссии** | голосование, кворум, решение, протокол, скан | да — **единственный** |
| B (зеркало) | карточка заявки, та же вкладка | read-only: решение, голоса с комментариями, скан, прогресс; баннер направляет в модуль | **нет** |

**Инвариант:** функции вынесения решения, голосования, подписи и загрузки протокола в карточке
заявки **удалены физически**. Раньше вкладка заявки имела собственное вынесение решения **без
кворума** — то есть два движка с разными правилами. Осталась только фаза A.

**Связь записей:** макет держит заявку строкой без идентификатора; реальный модуль обязан
связывать структурные номера `З-2026-000123` ↔ `К-2026-000138`, чтобы зеркало читало итог из
записи комиссии, а не из копии.

## 2. Модель данных

### 2.1. Запись комиссии

| Поле | Описание |
|---|---|
| Номер | структурный `К-ГГГГ-NNNNNN` (единый формат с номером заявки `З-ГГГГ-NNNNNN`) |
| Заявка | рассматриваемая заявка (в проде — ссылка, не строка) |
| Заявитель | ИНН/ПИН + наименование |
| Кредитная программа | название либо признак отсутствия → **поток B** |
| Комиссия | какой именно коллегиальный орган (у программы может быть несколько) |
| Дата создания | когда заявка поступила в комиссию |
| Крайний срок | дедлайн рассмотрения |
| Статус | «На рассмотрении» · «Одобрено» · «Отклонено» · «Требуется доп. информация» |
| Номер протокола · Дата заседания | реквизиты протокола; **входят в гейт решения** |
| Причина | обоснование решения |
| Скан протокола | подписанный бумажный протокол |
| Состав | список членов (§2.2) |
| Документы | материалы к заседанию |
| История | журнал событий записи |

**Признак потока не хранится отдельным полем** — он однозначно выводится из наличия программы.
Дублировать его полем значило бы завести второй источник правды, который рано или поздно
разойдётся с программой.

### 2.2. Строка состава

| Поле | Описание |
|---|---|
| Роль | Председатель · Член комиссии (плюс секретарь как роль модуля) |
| Сотрудник | ФИО |
| Решение | Одобрил · Отклонил · Воздержался · (не голосовал) |
| Риск | оценка риска из справочника |
| Дата | когда проголосовал |
| Комментарий | отзыв члена комиссии |

Дубля колонки «Сотрудник» (логин и ФИО двумя колонками, как на живом стенде) в целевой модели
нет — одна колонка с ФИО.

## 3. Роли и права

| Роль | Права |
|---|---|
| **Председатель** | голосует как член состава; **единственный, кто выносит итоговое решение** (под гейтом); ведёт протокол |
| **Член комиссии** | голосует по нерешённой комиссии, если ещё не голосовал |
| **Секретарь** | создаёт и удаляет записи комиссии; ведёт протокол |
| **Просмотр** | только чтение |

Формально:

- **голос** — член состава, комиссия не решена, этот член ещё не голосовал;
- **решение** — роль председателя **и** статус «На рассмотрении» **и** пройденный гейт;
- **протокол** — председатель или секретарь при статусе «На рассмотрении»;
- **создание/удаление записей** — секретарь.

Повторный голос заблокирован: кнопка голосования живёт **в строке своего члена**, а не общей
кнопкой над таблицей.

## 4. Кворум и гейт итогового решения

### 4.1. Подсчёт голосов

Кворум = `⌊n/2⌋ + 1` от числа членов состава.

Подсчёт даёт четыре категории: одобрили · отклонили · воздержались · не проголосовали.
Проголосовавшими считаются первые три. **Воздержавшийся участвует в кворуме**, но не в исходе.

### 4.2. Гейт: четыре проверки в порядке устранения

1. статус ≠ «На рассмотрении» → «Решение по этой комиссии уже вынесено»;
2. кворум не набран → «Кворум не набран: проголосовало N из M, требуется K»;
3. не заполнен номер протокола;
4. не указана дата заседания.

Пустая причина = гейт пройден. Порядок проверок намеренно совпадает с порядком, в котором
пользователь их устраняет.

### 4.3. Что решение делает

| Решение | Статус записи | Последствие для заявки |
|---|---|---|
| **Одобрить** | Одобрено | поток A: формируется кредит, заявка «На оформлении»; поток B: **кредит не формируется**, заявка «Ожидает решения/программы» |
| **Отклонить** | Отклонено | заявка «Отклонена» (терминал) |
| **Запросить доп. информацию** | Требуется доп. информация | заявка возвращается специалисту, круг может повториться |

**Подтверждение называет действие, запись и последствие**, а не «Вы уверены?»: «Одобрить заявку
«Заявка - 97» по комиссии К-2026-000138? Протокол № … от … Решение необратимо.» При одобрении
в потоке B добавляется предупреждение: кредит **не** будет сформирован, заявка уйдёт в ожидание
решения и программы. Деструктивное решение — красная кнопка.

Решение пишет в историю две записи: итог с номером протокола и **системную запись о
последствии** (сформирован кредит по программе / кредит не сформирован, заявка ждёт).

### 4.4. Критический инвариант

**UI-гейт без серверной проверки кворума защитой не является.** Отдельной задачей требуется
подтвердить, что сервер валидирует кворум перед сменой типа решения.

### 4.5. Расхождение с обследованной системой

На живом стенде (19.06.2026) кворума **не было вовсе**: председатель закрывал комиссию в любой
момент, голоса носили справочный характер. Целевое ядро **вводит** порог `⌊n/2⌋+1` — это
осознанное ужесточение, которое требует согласования канонического правила с заказчиком.

## 5. Правила комиссии (закрытые решения)

| # | Правило | Состояние |
|---|---|---|
| 1 | **Финал ручной + аудит.** Решение выносится кнопкой (Одобрить / Отклонить / Запросить), автоматизации по тэлли нет. Но сохранение финала обязано писать аудит: кто, когда, решение и причина — **особенно при расхождении с подсчётом голосов** | правило принято; аудит-запись при расхождении, вероятно, на бэкенде |
| 2 | **Правило четырёх глаз — предупреждением, не запретом.** Если автор или податель заявки оказался членом или председателем комиссии по ней же — **не блокировать**, предупредить и пометить в аудите | в интерфейсе пока нет |
| 3 | **Кворум** | as-is без порога; to-be — порог `⌊n/2⌋+1` (§4.5) |
| 4 | **Одна комиссия судит кредит и залог** (реверс решения 06.07.2026) | принято, двух-комиссионная модель отменена |
| 5 | **Крайний срок члена принуждается уведомлением**, а не автоматикой: голос **не** меняется сам, авто-«воздержался» не ставится. Нужен планировщик и нотификации члену и председателю | требует таймера/планировщика |

Удаление записи: решённую комиссию удалять **нельзя** — это уничтожает аудит-след решения.
Удаление нерешённой требует подтверждения с явным «Действие необратимо».

## 6. Список комиссий как рабочая очередь

| Элемент | Поведение |
|---|---|
| Плитка и фильтр **«Ждут моего голоса»** | тот же предикат, что право голоса: член состава, комиссия не решена, ещё не голосовал. В строке — тег «ваш голос» |
| Колонка **«Крайний срок»** | чип: «Просрочен N дней» / «Сегодня» / «дата · N дн.»; показывается **только пока «На рассмотрении»** — у решённой записи дедлайн смысла не имеет |
| Колонка **«Тип решения»** | статус-чип вместо простого текста |
| Колонка **«Голоса»** | мини-полоса сегментов + «N из M» |
| Фильтр по программе | отдельное значение **«Без программы (поток B)»**: пустую строку селект не отличил бы от «любая» |
| Убрано | константная колонка «Тип документа» и всегда-пустой «Комментарий» |
| Обрезка | подсказка на обрезанных ячейках |
| Номер | структурный `К-2026-000138`, единый формат с заявкой |

**Счётные плитки:** «Всего» равно сумме статусных плиток по построению; плитки кликабельны как
фильтр (повторный клик снимает); рамка серая при нуле, статусная при значении > 0.
Фильтр — «Применить / Сбросить» плюс чипы активных условий, свёрнут по умолчанию.

## 7. Карточка комиссии

**Одна карточка read-only + зоны действий** (голос · решение · документы · протокол) — вместо
двух прежних экранов. Прогресс голосования стоит **над** блоком решения: сначала видно, набран
ли кворум, и только потом кнопки.

- **Прогресс:** стек-сегменты по четырём категориям + строка «Проголосовало N из M · кворум K
  набран/не набран». Контраст цветов — не ниже 4,5:1. На живом стенде «Отклонили» имели
  контраст ≈ 2,3:1 (провал требований доступности), а «Не проголосовали» рисовались чёрной
  плашкой.
- **Состав:** грид с решением и комментарием в той же строке; отдельной пустой секции
  «Комментарии членов» нет. Длинный комментарий обрезается с кнопкой «Показать полностью»,
  причём обрезка **измеряется по факту** (ширина содержимого против ширины ячейки), а не
  угадывается по длине строки.
- **Протокол — не тупик:** пока протокола нет, показывается пустое состояние с действиями
  «Сформировать протокол» и «Загрузить скан подписанного» под тем же гейтом прав; когда скан
  есть — баннер с реквизитами, ссылка на файл и печать.
- **Документы:** пустое состояние с кнопкой «Загрузить» (на стенде кнопки не было вовсе).
- **История:** таймлайн событий записи.
- Правки самой сущности и кнопок «OK/Отмена» в карточке нет — карточка не форма редактирования.

### 7.1. Диалоги

Escape и клик по подложке закрывают диалог (со стеком вложенности). При несохранённом вводе
(форма отзыва члена) — подтверждение потери данных. Одна пара подписей «Да/Отмена» на всё.
Текст диалога называет и действие, и запись. Диалог «Ваш отзыв» — фиксированной ширины, поле
«Решение» обязательно, «Риск» берётся из **реального справочника**, а не свободным текстом.

## 9. Ключевые решения и их причины

| Решение | Причина |
|---|---|
| Движок решения один и живёт в модуле комиссии | раньше вкладка заявки имела своё вынесение решения **без кворума** — два движка с разными правилами по одной записи |
| Карточка заявки — read-only зеркало | итог должен читаться из записи комиссии, а не существовать во второй копии |
| Признак потока выводится из программы, а не хранится полем | второе хранимое поле разошлось бы с программой |
| Комиссия показывает последствие одобрения **до** нажатия | в потоке B «одобрено» не означает «кредит выдан»; без предупреждения председатель одобряет, думая, что запускает выдачу |
| Кворум-гейт с называемой причиной | «решение недоступно» без причины заставляет искать нехватку наугад |
| Порядок проверок гейта = порядок устранения | пользователь исправляет по одной причине за раз |
| Решение выносит только председатель | коллегиальный орган имеет одного ответственного за итог |
| Кнопка голосования — в строке своего члена | общая кнопка над таблицей позволяет проголосовать «за кого-то» |
| Прогресс над блоком решения | сначала кворум, потом кнопки: обратный порядок провоцирует решение без кворума |
| Правило четырёх глаз — предупреждением, не запретом | в малых филиалах состав пересекается физически; запрет остановил бы работу, а след в аудите — нет |
| Дедлайн принуждается уведомлением, а не авто-голосом | автоматическое «воздержался» подделывает волю члена комиссии |
| Решённую комиссию нельзя удалить | удаление уничтожает аудит-след юридически значимого решения |
| Реквизиты протокола входят в гейт | решение без номера протокола и даты заседания нельзя оформить документом |
| Дедлайн-чип только у нерешённых | у решённой записи «просрочен на 40 дней» — шум |
| «Без программы (поток B)» отдельным значением фильтра | пустая строка в селекте не отличима от «любая» |
| Обрезка комментария измеряется, а не угадывается | по длине строки кнопка «показать полностью» появляется там, где текст влез |
| Пустые состояния с действием | «Протокол не сформирован» без кнопки — тупик |

## 10. Открытые вопросы и долги

1. **Кворум:** согласовать каноническое правило (as-is без порога ↔ to-be `⌊n/2⌋+1`) и
   обеспечить **серверную** валидацию перед сменой типа решения.
2. **Аудит расхождения с тэлли** (решение председателя против подсчёта голосов) — правило
   принято, реализация, вероятно, на бэкенде, не подтверждена.
3. **Предупреждение о четырёх глазах** в интерфейсе отсутствует.
4. **Дедлайн члена** требует планировщика и системы уведомлений — их нет.
5. **Связь записей по идентификатору** (`З-…` ↔ `К-…`): в макете заявка — строка без ссылки.
6. **Зеркало в карточке заявки беднее модуля:** одноцветная полоса прогресса без строки
   кворума; при реализации читать те же данные и повторять эталон прогресса.
7. **Создание записи комиссии** в макете — демо-действие; кто и когда создаёт запись (секретарь
   руками или система при отправке заявки), формально не зафиксировано.
8. **На живом стенде почти ничего из этого не сверено.**

## 11. Словарь терминов

| Термин | Значение |
|---|---|
| **Комиссия по заявкам** | коллегиальный орган и запись о рассмотрении одной заявки |
| **Кворум** | минимальное число проголосовавших для правомочности решения: `⌊n/2⌋+1` |
| **Тэлли** | подсчёт голосов по категориям (одобрили / отклонили / воздержались / не голосовали) |
| **Гейт** | проверяемое условие, блокирующее действие, с человекочитаемой причиной |
| **Поток A / поток B** | заявка по программе / индивидуальная заявка без программы |
| **Фаза A / фаза B** | предварительное изучение (в карточке заявки) / заседание комитета (в модуле) |
| **Зеркало** | read-only отображение итога комиссии в карточке заявки |
| **Протокол** | документ заседания: номер, дата, решение, подписи, скан |
| **Правило четырёх глаз** | тот, кто готовил заявку, не должен решать по ней |
