## 0. Краткая суть

Заявка — центральная сущность фазы «до кредита». Она собирает **заёмщика, условия кредита,
документы, залог и (для групповых программ) состав группы**, проводит их через проверку и
коллегиальное решение и после одобрения порождает кредит.

Шесть вещей, которые определяют логику модуля:

1. **Заявка — управляемый конечный автомат, а не редактируемая карточка.** Девять статусов,
   переходы только действиями с аудитом; редактируемость полей гейтится статусом и ролью.
2. **Два потока происхождения.** Поток A — по программе (условия наследуются конвертом
   программы, после одобрения сразу кредит). Поток B — индивидуальная заявка (программы нет,
   условия свободные; после одобрения кредита ещё нет — ждём привязки решения и программы).
   **Поток выбирается наличием программы в форме создания**, без отдельной кнопки и роли.
3. **Статус и стадия процесса ортогональны.** Статус — юридическая веха («Новый», «На
   рассмотрении», «Одобрена»). Стадия — где физически стоит комплектация (5 узлов: документы
   → подтверждение головного филиала → заключения отделов → комиссия → комитет). Стадия
   **выводится**, не хранится.
4. **Один гейт готовности на всё.** Кнопка «Отправить в комиссию», бейдж «готова» в списке и
   колонка «Стадия» считаются **одним и тем же правилом**. Разойтись им нельзя по построению.
5. **Одна комиссия судит кредит и залог вместе.** Двух-комиссионная модель отменена; залог —
   не отдельный статус, а гейт отправки (коэффициент покрытия + залоговые документы).
6. **Трёхслойная провенанс-модель условий:** программа (базовое) → заёмщик (запрошенное) →
   комиссия (одобренное). У каждого условия видна цепочка «было → стало» с тегом источника.

## 1. Назначение и границы

### 1.1. Что делает модуль

Принимает обращение заёмщика, приводит его к проверяемому комплекту, проводит через
двухуровневую проверку документов и заключения профильных отделов, отдаёт на коллегиальное
решение и после одобрения передаёт условия в кредит.

### 1.2. Что НЕ входит

- Формирование кредита и траншей, график **выданного** кредита, назначение кураторов — модуль
  «Кредит» (условия наследуются при выдаче).
- Реестр субъектов/заёмщиков, справочники залога, областей, отделов — внешние модули; в заявке
  это окна выбора и справочники-источники.
- Печатные формы и шаблоны договоров как таковые — поздняя стадия.
- Итоговое решение комиссии — модуль «Комиссия по заявкам»; в карточке заявки фаза заседания
  комитета — **read-only зеркало**.

### 1.3. Два потока происхождения заявки

| | Поток A — по программе | Поток B — индивидуальная |
|---|---|---|
| Признак | программа в форме создания **выбрана** | программа **не выбрана** |
| Условия | наследуются конвертом программы, правятся в её границах | свободные, вводятся вручную |
| После одобрения | «Сформировать кредит» → «На оформлении» | «Ожидает решения/программы»: ждёт привязки нового госрешения + программы, дальше идёт как поток A |

**Почему поток выбирается пустым полем, а не кнопкой или ролью.** Отдельная кнопка «создать
индивидуальную заявку» потребовала бы своего роль-гейта и своей формы; при этом единственное
содержательное отличие — есть ли конверт условий. Пустая программа легальна и сама означает
поток B, поэтому её пустоту не блокируют, а подписывают хинтом.

### 1.4. Чем целевая модель отличается от обследованной системы

1. **Двух-комиссионная модель отменена** (04.07–06.07.2026): одна комиссия судит кредит и залог
   — один голос, одно решение, один протокол. Убраны колонка «Статус залога», вторая кнопка
   «Отправить в залоговую комиссию» и параллельные статусы.
2. **Статус-степпер управляемый:** переходы только через действия жизненного цикла с аудитом.
3. **Добавлен воркфлоу комплектации:** документы → подтверждение головного филиала →
   заключения отделов → комиссия (предварительно) → комитет.
4. **Форма создания — один экран**, а не мастер с «Далее» на 6 шагов.
5. **Появился аудит-трейл:** на стенде История заявки, прошедшей путь «подача → одобрено»,
   была пуста.

## 2. Роли и фазы

### 2.1. Пять ролей

| Роль | Зона ответственности |
|---|---|
| **Кредитный специалист** | создаёт и правит заявку в черновике, все действия тулбара, назначает отделы на заключения |
| **Головной филиал (ГФ)** | второй уровень проверки: подтверждает укомплектованность документов |
| **Отдел (заключение)** | вносит заключение **только за свой отдел**, и только после подтверждения ГФ |
| **Комиссия** | правит операционные условия и голосует, когда заявка «На рассмотрении» |
| **Остальные** | только чтение |

### 2.2. Три фазы редактируемости (выводятся из статуса)

| Фаза | Статусы | Кто правит меняемые условия |
|---|---|---|
| **draft** | Новый · Требуется доп. информация · **Ожидает решения/программы** | кредитный специалист |
| **review** | На рассмотрении | комиссия (экран специалиста read-only) |
| **locked** | Одобрена · Отклонена · Отозвана · На оформлении · Оформлена | никто — зафиксировано |

**Почему «Ожидает решения/программы» относится к draft, а не к review.** Это состояние потока B
**после** одобрения: заявка вернулась к кредитному специалисту, который привязывает программу и
решение и подгоняет условия под конверт программы. Отнесение к review отдавало право правки
комиссии и лишало специалиста возможности сделать ровно то, зачем статус существует. Это был
реальный дефект, исправленный 12.07.2026.

### 2.3. Матрица прав: право = (роль × фаза) И включённый режим правки

| Право | Что даёт | Кому |
|---|---|---|
| правка запроса *(edit)* | заявитель, документы, члены группы, залог | специалист × draft |
| правка опер-условий *(edit)* | операционные условия + комментарий комиссии | комиссия × review |
| правка графика *(edit)* | окно правки графика погашения | специалист × draft **или** комиссия × locked |
| голос | голос члена комиссии | комиссия × review |
| подтверждение документов | подтвердить укомплектованность | ГФ × draft |
| назначение отделов | назначить состав заключений | специалист × draft |
| заключение отдела | внести/отозвать своё заключение | отдел × draft, **только свой отдел**, только после подтверждения ГФ |
| тулбар | действия жизненного цикла заявки | специалист, любая фаза |

Две тонкости реализации, важные для логики:

- **Права, помеченные *(edit)*, требуют явного включения режима «Изменить».** Потенциальное
  право роли и фактическая возможность писать — разные вещи: просмотр остаётся просмотром,
  пока пользователь не вошёл в правку.
- **Роль и отдел фиксируются снимком в момент проверки права.** Иначе замыкания «внести
  заключение своего отдела» продолжали бы действовать после смены роли.

### 2.4. Иммутабельные поля

Кредитный специалист не меняет **никогда**, даже в черновике:

- **субъект (заявитель)** — фиксируется при создании;
- **поля, изменённые комиссией** — третий слой провенанса заблокирован для специалиста.

По статусу: в {Новый, Требуется доп. информация} правится по линзе наследования конверта
программы; во всех прочих статусах — полный read-only.

## 3. Статусы, переходы, стадии

### 3.1. Девять статусов

| # | Статус | Смысл | Веха | Владелец |
|---|---|---|:--:|---|
| 1 | **Новый** | создаётся и заполняется, ещё не в комиссии | 0 | специалист |
| 2 | **На рассмотрении** | отправлена в комиссию | 1 | комиссия |
| 3 | **Требуется доп. информация** | комиссия вернула на дозаполнение (возврат, не решение) | 1 | специалист |
| 4 | **Одобрена** | решение комиссии — одобрить | 2 | — |
| 5 | **Отклонена** | решение комиссии — отклонить (терминал) | 1 | — |
| 6 | **Ожидает решения/программы** | *только поток B*: одобрено, кредита нет — ждёт привязку решения и программы | 2 | оператор |
| 7 | **На оформлении** | кредит и транши сформированы; договоры на нотариальной регистрации | 3 | оператор |
| 8 | **Оформлена** | договоры зарегистрированы — терминал (успех) | 4 | — |
| 9 | **Отозвана** | отозвана до решения (терминал) | 1 | специалист |

«Черновик» и «Новый» слиты в один статус: на стенде они различались только тем, сохранена ли
запись, и это различие уже несёт наличие записи.

**Нормализация legacy-значений.** Старые значения приводятся к каноническим при загрузке
(«Одобрено» → «Одобрена», «Отклонено» → «Отклонена»). Правило: новые синонимы добавляются в
таблицу алиасов, **не в бизнес-логику**; сравнения по статусу — только по каноническим
строкам. Инвариант касается и счётных плиток над списком: считать **после** нормализации,
иначе один статус разъедется на две плитки.

### 3.2. Граф переходов

| Из | Действие | В |
|---|---|---|
| Новый | Отправить в комиссию | На рассмотрении |
| Новый | Отозвать | Отозвана |
| На рассмотрении | Вернуть (комиссия) | Требуется доп. информация |
| На рассмотрении | Одобрить (комиссия) | Одобрена |
| На рассмотрении | Отклонить (комиссия) | Отклонена |
| На рассмотрении | Отозвать | Отозвана |
| Требуется доп. информация | Отправить в комиссию (**без лимита циклов**) | На рассмотрении |
| Требуется доп. информация | Отозвать | Отозвана |
| Одобрена (поток A) | Сформировать кредит | На оформлении |
| Одобрена (поток B) | Сформировать кредит (авто-ветвление) | Ожидает решения/программы |
| Ожидает решения/программы | Привязать решение + программу | На оформлении |
| На оформлении | Зарегистрировать договоры (нотариус) | Оформлена |
| Отклонена / Отозвана | Пересоздать (клон) | Новый (новая заявка) |
| Оформлена | — | терминал |

Правила графа:

- **Отзыв возможен только из** {На рассмотрении, Требуется доп. информация}.
- **При отзыве запись комиссии уничтожается** — круг голосования не переносится.
- {Оформлена} — тупик; из {Отклонена, Отозвана} выход только клоном в новую заявку.
- Ветвление A/B на действии «Сформировать кредит» — по признаку потока, а не по роли.

### 3.3. Пять узлов пайплайна, ортогональных статусу

Статус — юридическая веха. Пайплайн — где физически стоит комплектация.

| Узел | Подпись | Достигнут, когда |
|:--:|---|---|
| 1 | Комплектация | обязательные документы ещё собирают/проверяют |
| 2 | Подтверждение ГФ | комплект собран, ждут подтверждения головного филиала |
| 3 | Заключения отделов | ГФ подтвердил, ждут заключений отделов |
| 4 | Комиссия (предварительно) | «На рассмотрении», фаза предварительного изучения |
| 5 | Комитет · решение | фаза заседания либо решённые статусы |

Заявка со статусом «Новый» может стоять на узле 1, 2 или 3 — в зависимости от готовности
комплекта, подтверждения ГФ и заключений. Стадия **вычисляется**, не хранится.

Два флага поверх узлов: **готова к отправке** (зелёный) и **есть отрицательное заключение
отдела** (красный).

**Инвариант «готова к отправке».** Признак обязан считаться **гейтом отправки**, а не
«готовностью узла»: последний не знает про гейт группы и покрытие залогом и пометил бы
«готовой» заявку, которую кнопка отправить не даёт. Список, колонка «Стадия» и кнопка
считаются **по одному правилу**.

### 3.4. Действия жизненного цикла

Все кнопки тулбара заявки жмёт кредитный специалист; решения комиссии — во вкладке «Комиссия»,
не здесь.

| Статус | Действия |
|---|---|
| Новый | Изменить · Отправить в комиссию · Удалить |
| На рассмотрении | Отозвать |
| Требуется доп. информация | Изменить · Отправить в комиссию · Отозвать |
| Одобрена | Сформировать кредит (поток A) / авто-ветвление в ожидание (поток B) |
| Ожидает решения/программы | Привязать решение + программу |
| На оформлении | Зарегистрировать договоры |
| Отклонена / Отозвана | Пересоздать |
| Оформлена | — |

Гейты и аудит:

- **Удалить** — только в «Новый»; одобренную заявку удалить нельзя («есть связанный кредит»).
  Удаление требует подтверждения и пишет результат; проверка на клиенте **и на сервере**.
- **Отправить в комиссию** — честный гейт готовности (§6.4); не прошёл → кнопка неактивна, а в
  подсказке — человекочитаемая причина.
- **В режиме правки** тулбар заменяется на «Сохранить»/«Отмена»; сохранение гейтится
  валидацией условий и модели.
- **Каждое действие пишет запись в аудит** с ключом, связывающим реальную запись с
  синтетической вехой таймлайна (§9).
- Гард по статусу парный: действие проверяет **и роль, и статус**.

### 3.5. Структурный номер заявки

Формат: `З` + год (4 цифры) + `-` + порядковый номер (**6 цифр** с ведущими нулями).
Пример: `З-2026-000123`. Без кода программы и органа.

- **Годовой сброс:** серия начинается с `000001` с 1 января, ключ — год.
- **Присваивается при подаче**, не в черновике (у черновика временный технический id).
  Номер неизменяем и не переиспользуется.
- **Реализация:** атомарная последовательность в базе по ключу года. **Запрещены** `max(id)+1`
  и клиентский счётчик — гонка даёт дубль.

Как было: голый счётчик «Заявка - 60», который не сортируется между годами.

## 4. Форма создания

Открывается как **отдельная страница-редактор**, все поля видны сразу, три секции:
«Заявитель», «Условия кредита», «Дополнительная информация».

| Поле | Обяз. | Правило |
|---|:--:|---|
| Субъект | **Да** | выбор из реестра субъектов; метка «‹ИНН/ПИН› - ‹Наименование›», при подаче разбирается на ИНН и имя |
| Адрес | Нет | readonly, автозаполнение из субъекта |
| Номер телефона | Нет | маска `+996 XXX XXX XXX`; валиден при нуле или ровно девяти цифрах |
| Кредитная программа | **Нет** | **переключатель потока** (§1.3); предзаполняет условия и **никогда не блокирует ввод**; хинт «Не выбрана → индивидуальная заявка (поток B): условия вручную» |
| Запрашиваемые сумма и срок | **Да** | сумма > 0 и в границах конверта программы; срок > 0 и в границах конверта |
| Комментарий к заявке | Нет | свободный текст |

**Обязателен только субъект.** Он — ядро заявки (звёздочка, inline-подпись «обязательно»,
серверная валидация). Программа не обязательна: её пустота легальна и означает поток B.

Из формы вынесены прочие условия кредита (решение 05.07.2026): их несёт программа либо
вкладка «Условия кредита» карточки. В форме остаются только запрашиваемые сумма и срок.

## 5. Список заявок

### 5.1. Тулбар и гарды по статусу

Кнопки: «Создать» (всегда) · «Просмотр» (по выделению) · «Удалить» · «Отправить в комиссию».

- «Отправить» доступна при статусе ∈ {Новый, Требуется доп. информация} **и** пройденном гейте
  готовности; иначе в подсказке причина.
- «Удалить» недоступна для статуса «Одобрена» с явным текстом причины.
- Удаление — подтверждение + результат; ролевой гард — только специалист; для массового
  удаления результат по строкам. Клиент **и сервер**.

### 5.2. Фильтр: два ряда

**Ряд 1 (базовый):** номер · статус · стадия · кредитная программа · дата создания (интервал).

**Ряд 2 (территория и исполнитель):**

| Фильтр | Каскад |
|---|---|
| Область заявителя | родитель обоих каскадов |
| Район заявителя | дочерний области; без области — все 45 районов, сгруппированные по областям |
| Филиал/отдел | дочерний области, родитель специалиста |
| Кредитный специалист | дочерний подразделения |

**Два независимых среза, которые нельзя путать:** область и район — атрибут **заявителя**
(адрес субъекта); филиал и отдел — атрибут **специалиста** заявки. Заявка из Ошской области
может вестись отделом головного офиса.

Справочники: 9 областей → 45 районов; подразделения с перечнем обслуживаемых областей
(7 филиалов + 2 отдела головного офиса); специалисты по подразделениям.

Поведение каскада: дочерний селект **сохраняет значение, если оно осталось валидным**, иначе
сбрасывается. Связь «подразделение ↔ область» держит консистентность: комбинация «Ошская
область + Чуйский филиал» честно даёт пустой список, а не тихо игнорирует один из фильтров.

**Инварианты для прода:** ключ района — **id, а не имя** (имена районов между областями
повторимы, например «Ленинский»); сортировка «область/район» — по паре, а не по строке.

### 5.3. Колонка «Стадия процесса»

Бейдж «номер · короткая подпись», полная подпись в подсказке; красный при отрицательном
заключении, зелёный у готовых к отправке; сортировка по номеру узла. Фильтр стадии имеет две
группы: сама стадия (1..5) и состояние (готовы к отправке / есть отрицательное заключение);
фильтры соединяются логическим И.

**Производительность:** стадия считается один раз на отрисовку через кэш по номеру заявки —
её вычисление обходит документы, членов группы и заключения.

### 5.4. Таблица или карточки

Переключатель представления; выбор запоминается локально и восстанавливается **до первой
отрисовки**. Карточка: монограмма, ФИО, номер и дата, бейджи статуса и стадии, сумма крупно,
программа, область/район, специалист и подразделение.

**Инвариант:** фильтры, сортировка, счётчик и гейты — общие; выборка считается **один раз**, и
уже потом выбирается способ отрисовки. Второго источника данных для карточек заводить нельзя.

### 5.5. Счётные плитки над списком

Считаются из выборки; «Всего» равно сумме статусных плиток **по построению**, а не отдельным
запросом. Плитка на каждый встречающийся статус. Клик по плитке = быстрый фильтр, повторный
снимает, активная помечается. Рамка серая при нуле, статусная при значении > 0.

Как было: плитки захардкожены в разметке и разошлись с данными («Всего 22» при 31 заявке,
совпадала одна плитка из пяти, статус «Новый» не показан, плитки некликабельны).

## 6. Условия кредита в карточке

### 6.1. Модель правок

«Изменить» снимает снимок и включает режим правки; поля пишутся вживую, и правка сразу видна
во всех вкладках, в шапке и в списке. «Сохранить» валидирует, фиксирует «было → стало» и пишет
аудит. «Отмена» **и смена роли** делают откат — несохранённая правка не переживает смену роли.

### 6.2. Трёхслойный провенанс

Слои: **программа** (базовое) → **заёмщик** (запрошенное) → **комиссия** (одобренное).

- У каждого условия печатается цепочка «было → стало» со стрелкой, прежние значения
  зачёркнуты, у каждого слоя — тег источника.
- Где вариант единственный, значение не менялось или прежнего нет — **одно значение без
  стрелки**: изменение не фабрикуется.

### 6.3. Три класса редактируемости условий

**Класс 1 — readonly (единственное значение программы):** кредитная программа, валюта, тип
основной ставки, плавающая ставка, ставка за резерв, штраф за просрочку основной суммы, штраф
за просрочку процентов, максимальный размер штрафа, очередь погашения, метод погашения (но
автоматически «Индивидуальный» при графике по конкретным месяцам).

**Класс 2 — ограничено программой** (выбор из опций программы либо число в границах min–max):
назначение кредита, источник финансирования, вид кредита, кредитная линия, вид счёта погашения,
сумма, срок, годовая ставка, три льготных периода (не предусмотрено → заблокировано;
фиксированный → список; диапазон → границы), периодичность платежей.

**Класс 3 — свободно (операционные, не из программы):** способ задания графика, конкретные
месяцы платежей, метод расчёта дней, база дней, дата выдачи (только для не-групповых), день
платежа (1–31), обработка нерабочих дней, привязка последнего платежа, минимальное и
максимальное число дней от освоения до первого платежа.

### 6.4. Гейт и особые правила

- Единое право правки условий: специалист правит до отправки, комиссия — на «На рассмотрении».
  Разделения «запрос / операционные условия» нет — правит тот, чья фаза.
- **Комментарий комиссии** — только комиссия; для остальных ролей read-only.
- «По конкретным месяцам» принудительно ставит метод погашения «Индивидуальный» (readonly).
- Баннер фазы объясняет, почему поля доступны или нет.
- Валидация при сохранении: сумма и срок > 0 и в границах; льгота ≥ 0 и ≤ срока; день платежа
  1–31. Ошибка → не сохраняется, показывается проблемное поле.
- У заблокированной заявки селекты — **read-only слои с сохранёнными значениями**, а не пустые
  выпадающие списки (это был реальный дефект: одобренные условия отображались пустыми).

## 7. Условные вкладки карточки

| Вкладка | Показывается | Драйвер |
|---|---|---|
| Члены группы | признак групповой заявки | программа: «Групповой кредит» |
| Залог | признак наличия залога | программа: «Требуется залог» |
| График погашения | всегда | — |

Границы гейтов (размер группы, максимальная доля, минимальное покрытие, виды залога) должны
приходить **с программы**; в макете они демо-константы, потому что на программе этих полей
ещё нет — это зависимость от модуля программы.

### 7.1. Члены группы

Модель — **зонтичный batch: один кредит, N траншей**, члены независимы; солидарной
ответственности и лидера группы нет.

| Поле строки | Правила |
|---|---|
| Субъект (ПИН + ФИО) | только через окно выбора реестра; **дубль ПИН запрещён** |
| Сумма транша | > 0; пересчитывает сумму, доли и гейт |
| Планируемая дата освоения | календарь |
| Доля % | read-only, `сумма/Σ×100`, помечается при превышении лимита |

- **Инвариант суммы — снизу вверх:** «Сумма кредита» = Σ траншей, итог read-only.
- **Гейт группы** (единый для вкладки и для гейта отправки): размер в границах (демо 3–10
  членов) · доля каждого ≤ лимита (демо 40%) · `|Σ траншей − сумма| < 0,01`. Баннер либо
  подтверждает укомплектованность, либо перечисляет причины блокировки.
- **Удаление члена запрещено после одобрения** (транш в работе). Вместе с членом **каскадом**
  уходят его документы.
- Добавление члена недоступно при достигнутом максимуме.

### 7.2. График погашения

Десять колонок: № · дата начала · дата платежа · дней · ставка % · остаток на начало ·
проценты · погашение основного долга · платёж итого · остаток на конец. Один формат у члена
группы, у свода и у индивидуального кредита.

- **Индивидуальная заявка:** один график; обязательное поле «Дата выдачи», от неё считается
  первая дата начала.
- **Групповая заявка:** выбор «График по: ‹член · сумма› / Вся группа», по умолчанию — вся
  группа. У члена свой график от его транша и его даты освоения. «Вся группа» —
  **read-only свод**: слияние по-членных строк по датам, проценты/тело/итого — суммы по
  членам, дни и остатки — на уровне группы. Правка возможна **только на вкладке члена**.
- **Расчёт процентов.** Ставка за период `T = rate/100 × эффективная_частота/12`; аннуитет
  `PMT = P·T/(1−(1+T)^(−n))`, при нулевой ставке `P/n`; начисление
  `accrued = остаток_на_начало × rate/100 × дней/база`, база 365; дифференцированный метод —
  `P/число_строк_с_телом`. Поддержаны все три льготных периода. Дата платежа **зажимается по
  длине месяца** (31 → 28/29/30) и не «перетекает» на следующий месяц; опционально —
  перенос с нерабочих дней. На живом стенде был дефект: «Проценты» = 0 при ставке 12%.
- **Правка строк — под отдельным гейтом:** тулбар строк («Построить график», «Добавить»,
  «Изменить», «Удалить строку») виден только в режиме правки, право — специалист в черновике
  **или** комиссия при заблокированной заявке (окно правки после одобрения). Вне окна —
  read-only автоматический расчёт. Валидация строки: тело ≥ 0, дата строго позже предыдущей и
  не позже «выдача + срок»; ручные строки помечаются. **Баланс-инвариант:** остаток на конец
  должен быть нулём, иначе баннер. Правки графика пишутся в аудит.

### 7.3. Залог

| Поле предмета | Правила |
|---|---|
| Вид залога | только из справочника **программы**, не глобального; смена вида сбрасывает документы предмета |
| Оценочная стоимость | > 0 |
| Собственник (залогодатель) | тот же реестр субъектов, что заёмщик и члены группы |
| Описание | свободный текст |

- Добавление через модальное окно с валидацией «вид ∈ разрешённых программой» и
  «стоимость > 0». Удаление предмета **каскадом** снимает его залоговые документы. Итог
  «Σ оценок» — read-only.
- **Гейт покрытия:** `покрытие = Σ оценок / сумма × 100`; порог с программы (демо 120%);
  сверка по **сырому** покрытию — 119,6% не округляется до 120%. Три состояния: нет предметов
  → предупреждение; покрытие ниже порога и/или залоговые документы не собраны →
  предупреждение с перечислением; достаточно → ок.
- Залоговые **документы** живут во вкладке «Документы» и здесь не дублируются; при нескольких
  предметах они сгруппированы в под-панели по предмету.
- **Отдельной залоговой комиссии и залогового статуса нет** — залог входит в общий гейт
  отправки через покрытие и комплект залоговых документов.

## 8. Документы и заключения

### 8.1. Жизненный цикл документа: 8 хранимых статусов + 1 производный

| Статус | Когда | Кто переводит |
|---|---|---|
| **Требуется** | файла нет | — |
| **Запрошено** | запрошен из госсистемы, ждём ответа | специалист |
| **Загружен** | файл есть, заявка не в комиссии | специалист |
| *На проверке* | **производный вид**: «Загружен» у заявки, находящейся в комиссии | — (не хранится) |
| **Принят** | специалист нажал «Проверил» (1-й уровень) | специалист |
| **Подтверждён** | ГФ нажал «Подтвердить» (2-й уровень) | головной филиал |
| **Отклонён** | вернули на перезагрузку | специалист / комиссия |
| **Просрочен** | истёк срок действия документа | система |
| **Не требуется** | освобождён специалистом | специалист |

**Два уровня подтверждения** дают две галочки в строке: «✓ специалист / ○ ГФ». Документ,
подтверждённый ГФ, специалист **не трогает** — сначала ГФ снимает подтверждение.

Действия строки зависят от статуса и вида: «Загрузить» → «Проверил»/«Отклонить»;
«Перезагрузить» для отклонённых и просроченных; «Вернуть» для освобождённых; у печатных форм
— «Печать» → «Загрузить скан»; у договорных — «Сгенерировать»; у запрошенных — «Отменить
запрос»/«Ответ получен».

**Три производных предиката комплектности** (на них стоят все гейты):

- **собран** — все обязательные закрыты;
- **принят специалистом** — все обязательные приняты;
- **подтверждён ГФ** — все обязательные подтверждены → **открываются заключения отделов**.

Открытые блоки — «требуется», «отклонён», «просрочен», «запрошено»; при этом «запрошено» —
открытый блок, но **не** blocker: ожидание ответа интеграции не равно отсутствию работы.

### 8.2. Шесть секций документов

| Секция | Обязательность | Особенности |
|---|---|---|
| Идентификация заёмщика | по типу лица | физлицо: паспорт, ИНН, согласия; юрлицо: устав, выписка из реестра, решение, приказ |
| Печатные формы | обяз./опц. | бланк → печать → подпись → скан |
| Платёжеспособность | обяз./опц. | физлицо: справка о доходах; юрлицо: отчётность и декларации; кредитный отчёт — опционально |
| Целевые / проектные | все опциональные | по решению специалиста (бизнес-план, ТЭО, финмодель) |
| Залоговые | обязательны по программе | под-панели по предмету, комплект из справочника «вид залога → типовые документы»; **источников интеграции не имеют** |
| Договорные | обязательны | шаблоны с подстановкой полей, заблокированы до одобрения |

Программа **сужает** первые четыре секции до своего пакета документов; залоговые и договорные
берутся как есть.

### 8.3. Обязательные документы как гейт

Договорные и залоговые документы **исключены** из подсчёта комплектности: договорные — этап
после одобрения, залоговые — отдельный гейт по покрытию.

### 8.4. Запрос из внешних госсистем

Маппинг «документ → система»: паспорт → ГРС (Тундук); ИНН → ГНС; регистрация и выписка из
реестра → Минюст; справка о доходах → Соцфонд; налоговые → ГНС; кредитный отчёт → Кредбюро.

Поток: «Требуется» → («Запросить из X») → **«Запрошено»** («Запрошено из X · дата») →
(«Ответ получен») → «Загружен» («Получено из X · автоматически») → обычная проверка.
«Отменить запрос» возвращает в «Требуется». Гейт умеет ждать: «Ожидается ответ интеграции по
N док.».

**Инвариант:** источник определяется по **идентификатору документа**, а не по сырому ключу
строки. У составных ключей идентификаторы пересекаются: «регистрация» залогового транспортного
средства — не та «регистрация», что запрашивается в Минюсте. Разворачивать можно только ключи
члена группы; залоговые документы источника не имеют никогда.

### 8.5. Документы по членам группы

- В групповой заявке секции «Идентификация» и «Платёжеспособность» уходят **на уровень члена**
  (печатные, проектные и договорные остаются на заявке). Тип комплекта — по типу субъекта
  члена.
- Селектор «Документы по: ‹член · N/M› / Вся группа», тот же приём, что на графике; свод даёт
  сводку и замечания по членам.
- **Гейт называет членов поимённо:** «У 2 чл. (ОРОЗБЕКОВА А.М. — 0/6, БЕКТУРГАНОВ Э.Н. — 5/6)
  комплект не собран». Безличное «комплект не собран» в группе из десяти человек бесполезно.

### 8.6. Командный центр вкладки «Документы»

Три блока над аккордеонами:

1. **Сегментный прогресс** с тремя накопительными порогами: собрано → принято специалистом →
   подтверждено ГФ; крупный процент — по первой незавершённой стадии.
2. **Конвейер стадий-фильтров:** чипы по стадиям жизненного цикла со счётчиками, клик
   фильтрует (несовпавшие строки скрываются); первым идёт синтетический чип «Надо загрузить»
   (требуется + отклонён + просрочен).
3. **Очередь «Требуют вашего действия»** по роли: специалисту — загрузить/перезагрузить/
   проверить/ответ получен; ГФ — подтвердить. Клик раскрывает и подсвечивает строку.

**Инвариант:** очередь строится на праве «роль × фаза», а **не** на включённом режиме правки —
обзор работает и в просмотре. Охват доменов повторяет подсчёт комплектности (статические
документы + члены + залог по предметам), договорные исключены.

### 8.7. Утилиты пакета

«Скачать пакет» и «Опись» видны, когда есть хотя бы один файл (учитываются **все** документы,
не только обязательные). **Инвариант прода:** граница по праву на **чтение** документов, а не
по видимости кнопки — иначе кнопка становится каналом выгрузки всего дела для роли, которой
поштучное скачивание закрыто.

### 8.8. Заключения отделов

**Справочник из 7 отделов:** рисков (по умолчанию), кредитный (по умолчанию), залога
(автоматически при наличии залога), юридический, аналитики, безопасности, мониторинга.

**Назначение состава** (специалист, в черновике): рисков и кредитный — несъёмные; отдел залога
добавляется автоматически при наличии залога и несъёмен, пока залог есть; остальные — добор из
справочника. Снятие непустого заключения — через подтверждение. Роль «Отдел» правит **только
свой** блок, чужие — read-only.

**Жизненный цикл заключения:** ожидается → черновик → внесено. Действия: «Внести», «Сохранить
черновик» (вердикт снимается), «Отозвать» (возврат в черновик, содержимое цело). Возврат
комиссией переводит внесённое обратно в черновик.

**Вердикты:** положительное · с условиями · отрицательное. Условия — список (минимум один
пункт при вердикте «с условиями»), плюс вложения.

**Валидация «Внести»:** нет вердикта → «Выберите вердикт»; пустой текст → «Заполните текст»;
«с условиями» без пунктов → «Добавьте пункт»; отрицательное с текстом короче 20 символов →
«Обоснуйте отрицательное заключение».

**Гейт заключений:** состав назначен, все заключения внесены, ни одного отрицательного.
Отрицательное заключение **блокирует отправку**: узел пайплайна краснеет, причина называет
отдел поимённо («Отрицательное заключение: Отдел рисков — устраните замечания, отдел отзовёт и
внесёт новое»). **Эскалации «вопреки» нет.**

Порядок причин в баннере (он же порядок устранения): не подтверждён ГФ → отделы не назначены →
есть отрицательное → внесено N из M → все внесены.

**Одно заключение на отдел на заявку** — и при группе, и при нескольких предметах залога.

Инварианты переноса в прод: карточка заключения рисуется в двух местах (редактор своего отдела
и read-only свод у комиссии) и должна различать контекст — редактор только в своей вкладке;
форма снимается **перед** перерисовкой, иначе правки теряются; запертость вычисляется, а не
хранится полем (хранимое поле было мёртвым и всегда ложным).

## 9. Гейт отправки в комиссию и аудит

### 9.1. Единый гейт готовности

Одна кнопка «Отправить в комиссию». Порядок проверки (он же порядок устранения):

1. заявка выбрана;
2. роль — кредитный специалист;
3. статус ∈ {Новый, Требуется доп. информация};
4. **комплект обязательных документов собран**;
5. при группе — **гейт группы** пройден (размер, доли, сходимость суммы);
6. при залоге — есть предметы **и** покрытие не ниже порога;
7. **подтверждено головным филиалом**;
8. **заключения готовы и без отрицательных**.

Причина блокировки всегда человекочитаема и называет конкретную нехватку.

Число комиссий-адресатов берётся из программы: одна → отправка сразу; две и более →
обязательный выбор из этих комиссий. Отправка переводит статус в «На рассмотрении», пишет
адресата, **сбрасывает голоса на новый круг** и пишет аудит.

### 9.2. История и аудит

На живом стенде История заявки, прошедшей «подача → одобрено», была **пуста**. Целевой аудит
юридически значим.

Механизм: реальные действия пишутся в журнал с ключом события; таймлайн собирается как
**синтетические вехи, выведенные из текущей модели, плюс реальные записи**, причём
синтетическая веха печатается только если реальной записи с этим ключом нет (защита от
задвоения). Формат: дата-время · пользователь · событие · было → стало.

Что логируется:

- **Статусные вехи:** заявка создана · отправлена в комиссию · возврат из комиссии · решение
  одобрить/отклонить · ожидание решения/программы (поток B) · сформирован кредит · договоры
  зарегистрированы · заявка отозвана.
- **Уровень поля («было → стало», юридически значимо):** сумма, срок, годовая ставка,
  назначение, источник финансирования, вид кредита, кредитная линия, вид счёта погашения, три
  льготных периода. Автор помечается как специалист (в черновике) или комиссия (на
  рассмотрении); «было» пишется один раз — первое зафиксированное значение. Плюс правки
  комиссии, добавление члена группы, укомплектование обязательного комплекта (N из M), правка
  графика после одобрения.
- **Без диффа** (только факт правки): телефон и прочие не-денежные поля.

| Сосед | Что берём | Что отдаём |
|---|---|---|

| **Субъект / заёмщик** | заявителя, членов группы, залогодателей — все из одного реестра, одним окном выбора; адрес и телефон подтягиваются | сквозную навигацию «заявка → карточка субъекта» по ИНН |
| **Комиссия по заявкам** | итоговое решение, голоса, протокол, скан — **только на чтение** | заявку в работу комиссии; связь по структурным номерам `З-…` ↔ `К-…` |
| **Кредит** | — | условия одобренной заявки при выдаче; групповая заявка даёт один кредит и N траншей |

читало итог из записи комиссии.

## 11. Ключевые решения и их причины

| Решение | Причина |
|---|---|
| Заявка — конечный автомат, а не свободная карточка | статус определяет права и юридические последствия; свободная правка статуса делает аудит бессмысленным |
| Поток выбирается пустой программой | единственное отличие потоков — наличие конверта условий; отдельная кнопка потребовала бы своего роль-гейта |
| «Ожидает решения/программы» — фаза черновика | иначе специалист лишён права сделать то, ради чего статус существует |
| Одна комиссия на кредит и залог | два статуса и два голосования по одной заявке давали противоречивые исходы и двойной протокол |
| Статус и стадия ортогональны | статус — юридическая веха, стадия — физическое место комплектации; их склейка порождала бы 15+ статусов |
| Стадия выводится, а не хранится | хранимая стадия расходится с документами при первой же правке |
| Один гейт готовности на кнопку, бейдж и колонку | три независимых правила разошлись бы: «готова» в списке при неактивной кнопке |
| Гейт называет причину, а не просто блокирует | без причины оператор перебирает вкладки наугад |
| Два уровня подтверждения документов | проверка специалиста — операционная, подтверждение ГФ — контрольная; одна галочка стирает разницу |
| Подтверждённый ГФ документ заперт для специалиста | иначе второй уровень обходится подменой файла |
| Заключения открываются только после подтверждения ГФ | отделы не должны заключать по неподтверждённому комплекту |
| Отрицательное заключение без эскалации | коллегиальное решение «вопреки» отделу превращает заключение в формальность |
| Одно заключение на отдел на заявку | иначе при группе из 10 членов отдел рисков пишет 10 заключений |
| Трёхслойный провенанс условий | нужно видеть, что запросил заёмщик и что одобрила комиссия, а не только итог |
| Изменение не фабрикуется, где его не было | стрелка «было → стало» с одинаковыми значениями обесценивает диф |
| Правка графика после одобрения — отдельное окно права | график выданного кредита меняется, но не всеми и не всегда |
| Дата платежа зажимается по длине месяца | 31-е число в феврале «перетекало» на март и сдвигало весь график |
| Сверка покрытия по сырому значению | округление 119,6% до 120% пропускает необеспеченный кредит |
| Виды залога — из справочника программы | глобальный справочник разрешил бы вид, не предусмотренный продуктом |
| Структурный номер с годовым сбросом через последовательность БД | голый счётчик не сортируется между годами; `max(id)+1` даёт дубли при гонке |
| Legacy-статусы приводятся алиасом на загрузке | иначе сравнения по статусу расползаются по всей бизнес-логике |
| Плитки считаются из выборки, «Всего» = сумма плиток | захардкоженные плитки разошлись с данными |
| Каскадные фильтры сохраняют валидное значение дочернего | сброс при каждом изменении родителя стирает работу оператора |
| Территория заявителя и подразделение специалиста — разные срезы | заявка из одной области может вестись отделом головного офиса |
| Форма создания — один экран | мастер на 6 шагов заставлял проходить все шаги ради двух полей |
| Обязателен только субъект | остальное либо приходит из программы, либо уточняется до отправки |
| Снимок роли при проверке права | иначе право «своего отдела» переживает смену роли |
| Несохранённая правка откатывается при смене роли | иначе правка специалиста «уезжает» в сессию комиссии |

## 12. Открытые вопросы и долги

1. **Роли ГФ и «Отдел» и узлы «Подтверждение ГФ» / «Заключения отделов»** есть в макете, но не
   в закрытом графе статусов. Решить: это под-состояния статуса «Новый» или отдельные шаги.
2. **Кворум комиссии:** обследованная система — без порога (председатель закрывает в любой
   момент, голоса справочно); целевое ядро вводит кворум `⌊n/2⌋+1`. Осознанное ужесточение,
   требует согласования и **серверной** валидации.
3. **Счётные плитки:** считать по текущей выборке (сводка) или по всему реестру (портфель)?
   В модуле комиссий выбрана выборка.
4. **Терминальная «Отклонена»** формально стоит на ранней вехе, а на полном таймлайне
   отматывается на веху решения — проверить, что бейдж и степпер не показывают её как ранний
   шаг.
5. **Число вкладок** карточки превысило гайдлайн «максимум 7» после добавления «Условий
   кредита» и «Заключений».
6. **Все UI-гейты требуют серверных двойников:** обязательность полей, кворум, «нет
   отрицательных заключений», «комплект подтверждён ГФ», покрытие залогом. UI-гейт без
   серверной проверки защитой не является.
7. **Границы гейтов на программе.** Размер группы, максимальная доля, минимальное покрытие,
   справочник видов залога должны приходить с программы; в макете это демо-константы, потому
   что соответствующих полей на программе ещё нет.
8. **Связь с модулем комиссии по идентификатору**, а не по строке названия.
9. **Зеркало фазы заседания** в карточке беднее модуля комиссии (одноцветная полоса без
   строки кворума) — при реализации читать те же данные из записи комиссии.
10. **Вложения в макете фиктивны**; интеграции с госсистемами смоделированы, реальных
    контрактов обмена нет.
11. **Совпадение ролей** «Ответственный за проверку документов» из программы и ролей ГФ/отдела
    не проверено.

## 13. Словарь терминов

| Термин | Значение |
|---|---|
| **Заявка** | обращение за кредитом с комплектом документов и условиями, проходящее коллегиальное решение |
| **Поток A / поток B** | заявка по программе / индивидуальная заявка без программы |
| **Конверт программы** | границы, в которых условия заявки могут отличаться от условий программы |
| **Провенанс условия** | цепочка «программа → заёмщик → комиссия», показывающая происхождение значения |
| **Стадия процесса** | вычисляемый узел пайплайна комплектации (1..5), ортогональный статусу |
| **Гейт** | проверяемое условие, блокирующее действие, с человекочитаемой причиной |
| **ГФ (головной филиал)** | второй уровень проверки документов |
| **Заключение отдела** | письменный вердикт профильного отдела: положительное / с условиями / отрицательное |
| **Зонтичный batch** | групповой кредит: один договор, N траншей по членам, без солидарной ответственности |
| **Транш** | часть кредита с собственными условиями и расчётом |
| **Коэффициент покрытия** | Σ оценок предметов залога / сумма кредита × 100% |
| **Тундук** | государственная система межведомственного электронного взаимодействия КР |
| **ГРС / ГНС / Соцфонд / Кредбюро** | Государственная регистрационная служба, Государственная налоговая служба, Социальный фонд, кредитное бюро |
| **Аннуитет / дифференцированный** | методы погашения: равные платежи / равные доли основного долга |
