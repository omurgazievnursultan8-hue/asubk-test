# АСУБК — логика модуля «Госрешение» (решение правительства)

> **Что это за файл.** Самодостаточное описание текущей логики модуля. Рассчитан на чтение
> без доступа к репозиторию проекта: термины расшифрованы, правила приведены целиком,
> ссылки на внутренние документы даны только как указание на первоисточник.
>
> **Контекст системы.** АСУБК — автоматизированная система управления бюджетным
> кредитованием Государственного финансового холдинга (ФКФ, Кыргызская Республика).
> Подсистема «Система кредитования» ведёт полный жизненный цикл государственного
> кредита: нормативное основание → кредитная программа → заявка и комиссия → заёмщик →
> кредит → транши и освоение → платежи → реструктуризация → взыскание.
> Новая система реализуется на платформе **Jmix поверх Vaadin** (Java SPA,
> русскоязычный бэк-офис), заменяет legacy-систему ФКФ.
>
> **Статус модуля:** целевая модель (to-be) согласована заказчиком 22.06.2026
> (доработки R1–R7). Макета-прототипа с живой логикой у модуля нет — есть спецификация
> воркфлоу и образец вёрстки страницы деталей. Состояние описания — на 23.09.2026.
>
> Первоисточники в проекте: `requirements/tz/01-gosreshenie.md` (раздел ТЗ),
> `mockups/decision/decision-workflow.html` (статусы, переходы, роли, матрица прав,
> версия 0.2 от 22.06.2026), `mockups/decision/decisions.html` (вёрстка страницы деталей),
> `requirements/features/01-government-decision.md` (обследование живого стенда 17.06.2026),
> `requirements/concepts/government-decision.md` (зачем сущность нужна).

## 0. Краткая суть

Госрешение — **запись о нормативном акте, который разрешает государственное кредитование**.
Это корневая сущность всей кредитной подсистемы: кредитная программа ссылается ровно на
одно госрешение, кредит — на программу, поэтому любой выданный кредит «разматывается»
обратно до конкретного государственного акта и приложенного PDF-первоисточника.

Сам акт система **не создаёт** — он приходит извне (Кабинет Министров, ведомство), а
сотрудник Холдинга его **регистрирует**. Поэтому модуль — это не «согласование решения
правительства», а **внутреннее согласование факта регистрации**: проверка, что заведённая
карточка соответствует бумажному акту, и допуск её к использованию.

Три вещи, которые определяют всю логику модуля:

1. **Шесть статусов, две роли, одиннадцать переходов.** Жизненный цикл — единственный
   способ сменить статус; руками статус не правится.
2. **«Отклонён» и «Закрыт» — разные исходы** и не смешиваются: отказ в согласовании
   регистрации vs. отмена действовавшего решения. Оба **не терминальны** — админ
   возвращает запись на рассмотрение.
3. **Статус «Действует» и флаг карточки «Действующее решение (Да/Нет)» — разные вещи.**
   Флаг хранится отдельно и из статуса не выводится (открытый вопрос §9).

## 1. Назначение и место в конвейере

### 1.1. Зачем сущность существует

- **Правовое основание.** Холдинг — государственная организация и не может выдавать
  средства без законного основания. Запись о решении и есть это основание, зафиксированное
  в системе.
- **Точка происхождения средств и условий.** Решение задаёт рамку: какое направление
  кредитуется, в рамках какого государственного акта. Из решения «вырастают» программы,
  из программ — кредиты.
- **Прослеживаемость.** На вопрос «на каком основании выданы эти средства» система
  отвечает ссылкой на конкретный акт и приложенный документ.
- **Жёсткая зависимость:** без записи о решении кредитную программу создать нельзя —
  программе не на что сослаться, цепочка происхождения средств рвётся.

### 1.2. Положение в цепочке

```
Госрешение  (нормативный акт — разрешает направление кредитования)
     │ 1:N
     ▼
Кредитная программа  (условия: ставки, сроки, лимиты; ссылается на решение)
     │
     ▼
Заявка  →  Рассмотрение комиссией
     │
     ▼
Заёмщик  →  Кредит (выдача)  →  Транши / освоение  →  Платежи
```

Маршрут модуля в приложении: `/gov-decisions`.

### 1.3. Откуда берутся записи

Решение принимает государственный орган — сотрудник Холдинга **регистрирует** его:
заводит карточку и прикладывает PDF акта. Виды актов (справочник «Вид решения»):

| Вид | Что это |
|---|---|
| Постановление | Постановление (как правило — Кабинета Министров) |
| Распоряжение | Распоряжение |
| Основное | Базовое/основное решение |
| РКМКР · РПКР · ПКМКР | Ведомственные типы актов |

Перечень собран с живого стенда, а не из нормативной базы — официальные расшифровки
ведомственных типов подлежат уточнению у домен-эксперта.

## 2. Модель данных

### 2.1. Сущность «Госрешение»

| Поле | Тип | Обяз. | Кто заполняет | Описание |
|---|---|---|---|---|
| Наименование | текст | да | пользователь | Полное официальное наименование акта |
| Краткое наименование | текст | да | пользователь | Короткое название; выводится в списке и в связанных программах |
| Код | текст, только чтение | авто | система | Системный код записи, генерируется при создании (§2.2) |
| Номер решения | текст | да | пользователь | Официальный номер акта («80-р», «№554») |
| Вид решения | ссылка на справочник | да | пользователь | Тип акта (§1.3) |
| Дата решения | дата | да | пользователь | Дата принятия акта; по умолчанию — текущая; будущие даты запрещены |
| Статус | перечисление, только чтение | авто | жизненный цикл | Один из шести статусов (§3); при создании — «Черновик» |
| Действующее решение | флаг Да/Нет | — | пользователь | **Отдельное хранимое поле**, из статуса не выводится |
| Причина отклонения | текст | условно | согласующий | Обязательна при действии «Отклонить»; видна в просмотре и в списке |
| Примечание | многострочный текст | нет | пользователь | Произвольный комментарий (отдельная вкладка) |

### 2.2. Код решения — правило генерации

- Код **генерируется системой** при создании; поле только для чтения, ручного ввода нет.
- Формат: `{ТИП}-{ГГГГ}-{NNNN}`
  - `ТИП` — короткий код вида решения: `ПОСТ` / `РАСП` / `ОСН` / `РКМКР` / `РПКР` / `ПКМКР`;
  - `ГГГГ` — год из поля «Дата решения»;
  - `NNNN` — сквозной порядковый номер **внутри пары «тип + год»**, с ведущими нулями.
- Пример: `ПОСТ-2026-0007`.
- Уникальность обеспечивается счётчиком на стороне сервера, а не проверкой формы.
- Старые пустые legacy-коды миграции не требуют: предстоит полное обнуление данных.

**Почему код не вводится руками.** На живой системе код был ручным и обязательным при
создании — и при этом часть записей была с пустым кодом. На код опираются downstream-сущности
(программа ссылается на решение), поэтому дубли и расхождения в ручном коде — риск целостности.

### 2.3. Документы решения (вложения)

Отдельный блок загрузки файлов, **независимый от «Примечания»**:

- формат — **только PDF**; лимит размера ≈ 10–20 МБ; валидация при загрузке;
- можно прикрепить **несколько** файлов (основное решение + приложения/изменения),
  ровно один помечается как **основной**;
- на статусах «Черновик» и «На рассмотрении» файл **необязателен**; для перехода
  в «Действует» **наличие основного документа обязательно**;
- замена файла — загрузкой **новой версии** с сохранением истории, без перезаписи;
- у действующего решения удаление файла **запрещено**;
- кто и когда загрузил/заменил файл — пишется в общий журнал аудита.

**Почему это самый важный пункт функционала.** Госрешение — юридический акт; система
учёта и аудита обязана держать сам документ, а не только его реквизиты. На обследованном
стенде поля вложения не было вовсе — это была крупнейшая функциональная дыра модуля.

### 2.4. Журнал аудита

Единый журнал на запись, отображается вкладкой «История» как таймлайн с иконками по типу
события. Фиксируются: создание, изменение, загрузка/замена файла, каждый переход статуса,
удаление. Состав записи: **кто, когда, действие, причина**.

Принципиально: журнал **один**. История переходов, история файлов и таймлайн карточки —
одна и та же сущность, отдельными журналами не дублируются.

## 3. Состояния и переходы

### 3.1. Шесть статусов

| Статус | Смысл |
|---|---|
| **Черновик** | Создано и редактируется автором, ещё не отправлено |
| **На рассмотрении** | Отправлено согласующему, ожидает решения |
| **На доработке** | Возвращено автору с замечаниями |
| **Действует** | Одобрено и вступило в силу |
| **Отклонён** | В согласовании отказано (только из «На рассмотрении») |
| **Закрыт** | Действовавшее решение отменено или утратило силу (только из «Действует») |

### 3.2. Одиннадцать переходов

| Из статуса | Действие | В статус | Кто |
|---|---|---|---|
| — | Создать | Черновик | Автор |
| Черновик | Отправить на согласование | На рассмотрении | Автор |
| Черновик | Удалить | удалено (soft-delete) | Автор |
| На рассмотрении | Отозвать | Черновик | Автор |
| На рассмотрении | Одобрить | Действует | Согласующий |
| На рассмотрении | Отклонить | Отклонён | Согласующий |
| На рассмотрении | Вернуть на доработку | На доработке | Согласующий |
| На доработке | Отправить повторно | На рассмотрении | Автор |
| Действует | Закрыть | Закрыт | Согласующий / уполномоченный |
| Закрыт | Вернуть на рассмотрение | На рассмотрении | Администратор |
| Отклонён | Вернуть на рассмотрение | На рассмотрении | Администратор |

```
[*] ──Создать──> Черновик ──Отправить──> На рассмотрении ──Одобрить──> Действует
                    ▲  │                      │  │  │                      │
          Отозвать  │  └──Удалить──> [*]      │  │  └──Вернуть──> На доработке
                    └─────────────────────────┘  │                      │
                                                 │           Отправить повторно
                                    Отклонить    │                      │
                                                 ▼                      │
                                            Отклонён ──админ-возврат──> На рассмотрении
                                                                        ▲
                     Действует ──Закрыть──> Закрыт ──админ-возврат──────┘
```

### 3.3. Почему статусов шесть, а не три

Исходно в системе было три статуса: «На стадии рассмотрения», «Одобрен», «Закрыт».
Целевая модель добавляет три недостающих (**Черновик**, **На доработке**, **Отклонён**)
и переименовывает «Одобрен» → «Действует».

Что именно ломалось на трёх статусах:

- **Нет черновика** — запись попадала в очередь согласования сразу при создании, отредактировать
  её «до отправки» было нельзя.
- **Нет доработки** — у согласующего было только «да/нет», вернуть автору на правку нечем.
  Единственный путь исправить опечатку в номере акта — отклонить.
- **«Закрыт» значил два разных исхода одновременно.** Отклонение вело в «Закрыт», и отмена
  действовавшего решения вела туда же. По статусу нельзя было отличить «регистрацию не
  приняли» от «акт утратил силу» — а это разные юридические факты с разными последствиями
  для программ, выросших из решения.
- **Необратимость.** «Закрыт» был терминальным: один мис-клик «Отклонить» навсегда убивал
  правовое основание, и восстановить запись через интерфейс было невозможно (проверено на
  стенде — запись «РКМ 508-р» при проверке ушла в «Закрыт» и обратно не вернулась).

**Миграция данных:** существующие записи со статусом «Закрыт», означающие отказ в согласовании,
переводятся в «Отклонён». В целевой модели «Закрыт» — только отмена действовавшего решения.

## 4. Роли и права

### 4.1. Роли

| Роль | Назначение |
|---|---|
| **Автор** | Создаёт и редактирует решения, отправляет на согласование, дорабатывает |
| **Согласующий** | Одобряет, отклоняет, возвращает на доработку, закрывает |
| **Администратор** | Служебный возврат «Закрыт»/«Отклонён» → «На рассмотрении» с причиной в журнал |
| **Наблюдатель** *(опционально)* | Только просмотр; введение роли — открытый вопрос |

Названия ролей в спецификации условные и подлежат замене на фактические роли системы.
Доступ технически реализуется штатной безопасностью Jmix: **ресурсные роли** (пункты меню,
экраны, кнопки, поля) и **роли уровня строк** (какие записи видит пользователь, JPQL-фильтр).

### 4.2. Матрица прав по статусу

| Статус | Автор | Согласующий |
|---|---|---|
| Черновик | Изменить · Удалить · Отправить на согласование | только просмотр |
| На рассмотрении | Отозвать | Одобрить · Отклонить · Вернуть на доработку |
| На доработке | Изменить · Отправить повторно | только просмотр |
| Действует | только просмотр | Закрыть |
| Отклонён | только просмотр | только просмотр |
| Закрыт | только просмотр | только просмотр |

Действие «Создать» в матрицу не входит: оно не зависит от статуса и доступно роли Автор
всегда. Админ-возврат — вне матрицы Автор/Согласующий.

**Принцип матрицы: в каждом статусе активна ровно одна роль, вторая наблюдает.**
Ответственность за решение в каждый момент времени лежит на одном участнике — это и есть
разделение «создатель / проверяющий» (maker-checker), ради которого одобрение вынесено
из формы создания в отдельное действие.

### 4.3. Поведение тулбара

Тулбар единый для всех ролей; видимость и активность кнопок вычисляются по **двум условиям
одновременно** — роль пользователя и статус выбранной строки:

- кнопки, недоступные роли **в принципе**, — **скрываются** (согласующий не видит «Изменить»
  и «Удалить»);
- кнопки, доступные роли, но **недопустимые при текущем статусе**, — показываются
  **неактивными** с подсказкой при наведении.

Правило формулируется так: **скрываем по роли** (полномочия постоянны), **гасим по статусу**
(допустимость зависит от текущего момента).

## 5. Правила и инварианты

1. **Обязательные поля** при сохранении: Наименование, Краткое наименование, Номер решения,
   Вид решения, Дата решения. При нарушении — уведомление «Заполните все обязательные поля!»
   и подсветка незаполненных. «Код» в этот набор не входит — он не вводится вручную.

2. **Код генерируется системой** при создании; поле только для чтения (§2.2).

3. **Дата решения: будущие даты запрещены.** По умолчанию — текущая дата. Валидация
   **на клиенте** (календарь не даёт выбрать будущее) **и на сервере** (чтобы не обойти
   через API). Сообщение: «Дата решения не может быть в будущем». Нижней границы нет.

4. **Начальный статус — «Черновик».** Статус меняется только действиями жизненного цикла,
   ручной правкой формы — никогда.

5. **Редактирование содержимого** возможно только в статусах «Черновик» и «На доработке».
   Действующее решение не редактируется — его можно только закрыть.

6. **Удаление** возможно только в статусе «Черновик». Удаление — **soft-delete** (запись
   помечается удалённой, остаётся в БД, действие пишется в журнал), с обязательной причиной
   в диалоге подтверждения. Плюс **серверная проверка ссылок**: удаление запрещено, если на
   решение ссылается хотя бы одна программа или иная downstream-сущность, с внятным
   сообщением вида «Нельзя удалить: на решение ссылаются N программ».

7. **Переход в «Действует» требует основного документа** (§2.3). Нет PDF — нет вступления
   в силу.

8. **Отклонение**: подтверждение + **обязательная** причина (без причины действие
   недоступно) + запись в журнал; ведёт в «Отклонён», не в «Закрыт».

9. **Закрытие** доступно только из «Действует» и означает отмену действовавшего решения,
   а не отказ в согласовании.

10. **Обратимость: «Закрыт» и «Отклонён» не терминальны.** Администратор возвращает запись
    в «На рассмотрении» с обязательной причиной в журнал. **Других выходов из этих статусов
    нет.** Механизма «Дублировать» в модели нет — возврат покрывает оживление записи.

11. **Журнал аудита един** (§2.4): переходы, файлы, удаление — в одном журнале, отдельными
    сущностями не дублируются.

12. **Ссылаться на решение можно только в статусе «Действует»** — правило принадлежит
    модулю программы, но обеспечивается серверной проверкой (см. §6).

## 6. Швы с соседними модулями

### 6.1. Госрешение → Кредитная программа (1:N)

| Направление | Что передаётся | Правило |
|---|---|---|
| вниз | ссылка на госрешение как на правовое основание | программа ссылается **ровно на одно** решение; выбрать можно **только решение в статусе «Действует»** (серверный enforcement, не только фильтр в выпадающем списке) |
| вверх | обратные ссылки | вкладка «Кредитные программы» карточки решения показывает список выросших из него программ; этот же список — источник для проверки при удалении (§5 п. 6) |

**Незакрытый вопрос шва:** что происходит с уже созданными программами, когда решение
уходит в «Закрыт» или админ-возвратом в «На рассмотрении». Правило «ссылаться можно только
на действующее» описано **для момента выбора**; поведение существующих ссылок при смене
статуса решения в спецификации не зафиксировано.

### 6.2. Госрешение ← справочник «Вид решения» (N:1)

Внешний справочник АСУБК. Модуль его не ведёт, только читает. Короткие коды видов
(`ПОСТ`/`РАСП`/…) участвуют в генерации кода записи (§2.2) — значит справочник обязан
держать не только название вида, но и его короткий код.

## 7. Экраны и операции

| Экран | Маршрут | Содержание |
|---|---|---|
| Список | `/gov-decisions` | Таблица всех решений; панель действий (видимость по роли, доступность по статусу); встроенный, но **снимаемый** фильтр по статусу; конструктор фильтра «Добавить условие поиска»; настройки столбцов, пагинация |
| Создание | `/gov-decisions/new` | **Отдельная страница** (не модальный диалог) с формой; сохранение создаёт запись в «Черновике» |
| Детали | `/gov-decisions/<id>` | Отдельная страница в режиме «Просмотр + действия» с вкладками; редактирование — отдельным режимом по кнопке «Изменить» |

Колонки списка: Наименование · Краткое наименование · Статус · Код · Номер решения ·
Вид решения · Дата решения.

Страница деталей: слева — дерево навигации модуля (Кредиты → Программы и решения →
Решение правительства); шапка — хлебные крошки, наименование/номер, бейдж статуса;
футер — «Изменить» и «Назад», в режиме редактирования — «OK / Отмена». Вкладки:

- **Общая информация** — просмотр «подпись → значение», без редактируемых инпутов;
  для статуса «Отклонён» дополнительно показывается «Причина отклонения»;
- **Кредитные программы** — таблица связанных программ;
- **Документы** — таблица вложений;
- **История** — таймлайн журнала аудита.

Действия жизненного цикла доступны **и в списке, и на странице деталей** — одинаково.

**Почему страница, а не диалог.** Прежняя модель показывала запись в модальном окне поверх
списка. Карточка решения несёт четыре вкладки, включая таблицы программ и вложений и журнал
аудита — в диалоге они не размещаются, а «просмотр» в редактируемой форме не отличим от
редактирования, из-за чего статусные ограничения §5 п. 5 визуально не читаются.

## 8. Ключевые решения и их причины

| Решение | Причина |
|---|---|
| Код генерируется системой, ручной ввод убран | код — ключ для downstream-ссылок; ручной ввод давал дубли и пустые значения |
| Вложение PDF отдельным блоком, основной документ обязателен для «Действует» | акт — юридический документ; система аудита обязана держать первоисточник, а не только реквизиты |
| «Отклонён» ≠ «Закрыт» | это два разных юридических факта: не приняли регистрацию vs. акт утратил силу; при склейке по статусу их не различить |
| Оба исхода обратимы админ-возвратом | мис-клик не должен навсегда уничтожать правовое основание; проверено на стенде — восстановить было нечем |
| Обратимость сделана возвратом, а не «Дублировать» | дубликат породил бы вторую запись об одном акте и разошёлся бы с журналом аудита |
| Один журнал аудита вместо нескольких | иначе «кто и когда» приходится собирать из трёх мест, и они расходятся |
| soft-delete вместо физического удаления | на решение ссылаются программы; физическое удаление рвёт цепочку происхождения средств |
| Флаг «Действующее решение» хранится отдельно от статуса | заказчик подтвердил, что это разные вещи; семантика флага пока не определена (§9) |
| Запрет будущих дат — на клиенте **и** на сервере | клиентская валидация обходится через API |
| Одобрение вынесено из формы создания в отдельное действие | разделение создателя и проверяющего (maker-checker) |

## 9. Открытые вопросы и долги

1. **Семантика флага «Действующее решение (Да/Нет)»** при статусе «Действует»: кто ставит,
   значение по умолчанию, что означает «Нет» при статусе «Действует». Зафиксировано только
   то, что флаг хранится отдельно и из статуса не выводится. — **Требует решения заказчика.**
2. **Обязательность комментария-причины** при действии «Вернуть на доработку». Для
   «Отклонить» причина уже принята обязательной; для «Вернуть» — не зафиксировано.
3. **Роль «Наблюдатель»** (только просмотр) — вводить ли её.
4. **Кто уполномочен закрывать решение**: согласующий или отдельная уполномоченная роль.
5. **Поведение существующих ссылок программ** при уходе решения из «Действует» (§6.1) —
   в спецификации не описано.
6. **Официальные расшифровки ведомственных видов актов** (РКМКР, РПКР, ПКМКР) — перечень
   собран со стенда, не из нормативной базы.
7. **Серверная проверка ссылок при удалении** на живой системе не проверялась (чтобы не
   разрушать данные) — реализована она или нет, неизвестно.
8. **Прототипа с живой логикой у модуля нет.** Спецификация воркфлоу есть, есть образец
   вёрстки — но нет самопроверяемого макета, как у более поздних модулей системы.
